# Codex接続

Codex接続には `openai-codex-cli-bin==0.167.0` に同梱されたランタイムを使用します。Python SDKは使用せず、公開app-serverプロトコルの標準入出力で接続します。

認証情報はCodexランタイムが管理します。既定では標準のCodex homeに保存されたChatGPT認証を利用します。GIGASの設定には資格情報を保存しません。APIキー認証は現在未対応です。

モデルと推論レベルは接続時のモデル一覧に照合します。空欄は一覧の既定値を使い、無効な値を別モデルや別推論レベルへ自動変更しません。無効な既定値でも接続・ログインは維持し、入力欄のモデル・推論レベルから選び直せます。有効な選択まで送信・Goal開始はできません。一覧の取得が拒否された場合は、接続状態と診断詳細を確認して明示的に再接続してください。自動再取得は行いません。設定の保存だけでは認証やターンの成功になりません。

「設定 → Codex」の認証行でアカウント識別情報、利用状況で利用枠を確認できます。期間ごとの残利用量の割合とリセット日時を一行に表示します。残割合は公開値の使用済み割合を100から引いた値で、期間・リセット日時・追加クレジットは公開値を使い、未提供の値は補いません。表示は選択・コピーでき、更新中も閲覧位置を保持します。接続メニューは接続・切断だけで、切断はログアウトではありません。サンドボックスの設定・更新も「設定 → Codex」の「サンドボックス環境」で行います。

利用枠は認証後と公開更新通知の受信時に取得します。取得失敗だけでは実行を止めず、最後に取得した値と取得不能の状態を表示します。通常利用不可が明示された場合、または現在ターンの最終失敗では、入力・Goal・ターンを既存の停止経路で止めます。残高ゼロや使用率、回復時刻だけから利用可否を推測しません。一度利用不可を確認した後は、利用許可を再取得するまで新規送信・Goal開始・再開を拒否します。許可が戻ってもGoalを自動再開せず、課金先も変更しません。

## Python API

`gigas.runtime.codex.launch.create_connection(options, emit, *, prepare_turn, on_thread_started, codex_home=None)` はアプリ用の接続を作成します。`options` は `models.ConnectionOptions`、`emit` は `models.ConnectionEvent` を受け取る短い同期コールバックです。準備と初回thread対応のコールバックは必須です。作成時にプロセスは起動しません。

同じasyncioループで `open()`、必要なら明示的に `login()`、認証後に `send(prompt)` を呼びます。`open()` は初期化・認証状態・モデル一覧を確認します。未認証時の `LoginEvent.url` は `login()` の開始後にだけ届き、ブラウザを開く操作は利用側で行います。`account/login/completed` とアカウントの再取得によって認証結果を確認します。

`AccountInfo`は公開アカウント情報、`UsageEvent`は利用枠の取得結果です。`UsageEvent.available`は直近取得の成否、`ordinary_usage_allowed`は通常利用の明示的許可を表します。取得失敗後の`buckets`は最後の取得値です。利用不能を確認済みなら、不明値・取得失敗で許可へ戻しません。利用枠の取得は受信処理を塞がない所有タスクで行い、切断時に回収します。部分更新通知から値を推測せず、完全な情報を再取得します。

`SandboxEvent(readiness, setting_up, detail, reconnect_required)`はWindows実行環境の状態です。`readiness`は`ready`、`notConfigured`、`updateRequired`、取得不能の`None`です。接続後に非同期で取得し、認証や候補の取得とは分けます。`setup_windows_sandbox()`は、ターンとactive Goalがない接続で明示的に準備を開始します。認証は不要です。管理者権限での準備をruntimeへ依頼し、Windowsの確認操作は利用者が行います。

同メソッドは開始受付だけでは完了せず、完了通知と準備状態の再取得を待ちます。準備失敗・状態取得不能の場合は`CodexConnectionError`を返し、接続は維持します。ランタイムが公開した準備失敗の理由は例外と`SandboxEvent.detail`へ保持し、通知詳細から再確認できます。理由が返らない場合は原因を補いません。準備成功後に取得できた状態が非readyなら、例外ではなく`reconnect_required=True`を通知して正常に戻ります。明示的に切断・再接続してください。受付不明のときは`setting_up=True`と理由を通知し、自動再送せず完了通知を待ちます。待機中も`close()`できますが、切断をWindows側の準備処理の取消しとは扱いません。

新規送信・Goal開始・再開は、実行環境が`ready`でなければ開始前に拒否します。初回の状態取得中なら既存の取得だけを待ち、その間に停止された場合はthreadやGoalを提出しません。追加問い合わせや自動再試行はしません。既存Goalの目的更新、途中指示、回答・承認、停止にはこの条件を追加しません。`ready`の確認後もthread応答の書込範囲を検証します。

`send()` は配布物内の `play.md` を開発者指示として配送し、人間による承認・永続スレッドで通常ターンを開始します。書込先は準備した記録先の`memory/`に固定します。利用者のMCP設定は接続用に無効化し、アプリが明示したMCP設定だけを重ねます。本文・公開計画・公開推論要約・ツール活動を型付きイベントへ変換し、生のプロトコル応答やstderrを表示イベントへ流しません。

`prepare_turn(prompt, thread_id)`は通常の`send()`、新規Goal開始、保持Goalの明示再開で呼ぶasyncコールバックです。自律ターンごとやGoalの目的更新では呼びません。`prompt`は依頼または再開する目的、`thread_id`は初回に`None`、以後は採用済みの実thread IDです。`models.ThreadConfiguration(cwd, mcp_config)`を返し、`cwd`には原記録先の準備済み絶対パスを指定します。`cwd / "memory"`も事前に作成しておきます。threadのcwdと作業領域はこのmemoryへ限定し、追加書込先・一時領域・ネットワークは許可しません。応答の設定が一致しない場合は開始を拒否します。プロセスの`ConnectionOptions.cwd`とは分離します。接続・ログイン時には呼ばないため、保存先の準備失敗で認証は失われません。

コールバックから得た設定は、初回には`thread/start`へ渡します。次の送信では`thread/unsubscribe`の完了後に同じIDを`thread/resume`し、その設定を読み込みます。返されたID・モデル・承認設定・sandboxを確認してから`turn/start`へ進みます。アプリはこの経路で[ゲームI/O MCP](observation-mcp.md)の公開情報を更新し、プロトコル切替後も同じ会話を維持します。

`on_thread_started(thread_id)`は初回に返されたthread IDをアプリへ渡すasyncコールバックです。アプリはIDを採用し、記録を非同期投入してからrunを開始します。永続化の完了をturn/startの条件にせず、保存失敗は通知へ残します。再開時には呼びません。

アプリが記録先を準備する場合、開発者指示には`observations/<観測ID>.png`と`events.jsonl`の参照方法を追加します。画像保存は非同期なので、応答直後にファイルが存在することや、障害時に全画像が残ることは保証しません。MCPのURL・認証値は表示イベントやこの案内へ含めません。

`send()`は公開の開始応答で確認したturn IDを返します。threadの準備・再開中に中断された場合はturnを開始せず`None`を返します。`TurnStarted`だけでは送信応答の成功を意味しません。応答より先にturnが完了しても、開始応答を確認できればそのIDを返します。ターン失敗の終端では失敗理由と`failure_id`を通知し、接続が継続していれば次の明示送信を許可します。

`set_goal(objective)`は公開Goalを開始または更新します。開始は`thread/goal/set`だけで行い、通常ターンを重ねて開始しません。未完Goalの目的更新では状態と利用量を維持し、追加指示を同時には送りません。新規Goal開始と明示再開は旧ターンの終了後に呼び、実行中の呼出しは拒否します。完了Goalから新しい目的へ進む場合は旧Goalを破棄して開始します。`resume_goal()`は保持Goalを同じthreadで再開し、準備コールバックの新MCP設定を読み込みます。両メソッドは公開成功応答で`True`、提出前の中断で`False`を返します。明確な拒否は`CodexConnectionError`、提出後に受付が不明なら`MessageDeliveryError`で、自動再送しません。

`clear_goal()`はGoalを破棄し、実行中ターンの中断も独立して試みます。`stop()`はGoalを保持して一時停止します。どちらも戻り値だけでターン終端と判断せず、公開状態と`SessionStatus`を確認します。active Goalのターン間に`send()`は使えません。paused中の通常会話はGoalを再開せず、製品サービスもゲーム入力を許可しません。

Goalが`complete`になると入力・追加指示・質問への回答受付を閉じます。完了時に実行中だったturnの最終応答は自動中断せず、自然終端後に一回だけ公開端末を回収し、その成功を確認して`ready`に戻ります。終端待ちの間は端末の書込が続く場合があります。完了後に始まった別turnは中断します。待機中にも`stop()`・`clear_goal()`で明示的に中断でき、この場合は終了確認後`stopped`になります。

`select_model(model, effort)`は公開候補を検証し、受理した選択を`ModelSelection`で通知します。通常送信は次の`turn/start`から使用します。Goalがある場合は公開`thread/settings/update`も完了してから選択を通知し、受理後に始まる自律ターンへ適用します。実行中ターンや`steer()`の設定は変えません。

`steer(prompt, expected_turn_id)`は実行中の指定turnへ追加指示を一度だけ送ります。通常送信のthread準備やMCP更新は行わず、質問を回答済みにしたり入力権を再取得したりしません。現在turnが一致しない場合は拒否します。公開成功応答で確認したturn IDを返し、モデルが指示に従ったことは保証しません。明確な拒否は`CodexConnectionError`、送信後の通信断など受付不明は`MessageDeliveryError`です。自動再送はしません。

`CodexConnectionError` は表示可能な短い理由を持ちます。通信で受付を確認できなかった要求を自動再送しません。最後に `close()` を待ち、所有するapp-serverとイベント受信処理を終了してからasyncioループを停止してください。

失敗の`SessionStatus`と同じ失敗を返す`CodexConnectionError`には、共通の`failure_id`が入ります。接続内で一意の番号なので、接続世代と組み合わせて二重表示を防げます。同じ理由でも別の試行には別の番号が付きます。既定の`None`は対応付ける番号がないことを表し、成功を意味しません。

質問・承認は `HumanRequest` として届きます。回答にはその `token` を使い、質問は `answer(token, answers={質問ID: 回答})`、承認は `answer(token, decision=判断)` を呼びます。判断は `decisions` に含まれる値から明示的に選びます。自動許可や永続許可への変換はありません。`RequestResolved(token)` が届いた要求は回答操作を無効にしてください。解決済み、停止後、ターン完了後の回答は送信しません。MCPの追加情報要求は現在未対応として拒否します。質問に`isSecret=true`が一つでも含まれる場合も要求全体を未対応として返し、`HumanRequest`は通知しません。通常入力への置換や一部質問だけの回答はしません。採用runtimeはこのエラーを空回答として処理するため、拒否をturnの中断とは扱わないでください。

`RequestResolved`は送信前にも届くため、回答送信の成功通知として扱わないでください。`answer()`の正常終了は通信への書込完了だけを表します。送信前の無効な要求は`CodexConnectionError`、通信への送信結果が不明な失敗はその派生型`AnswerDeliveryError`になります。取消しも送信結果不明として扱い、自動再送しません。これらの結果は許可対象の実行成功を保証しません。

コマンド承認はコマンド本文と作業フォルダーを確認できる一回限りの実行に対応します。環境IDがある場合は `local` を受け付け、確認対象に表示します。追加権限・ネットワーク固有の承認・既存端末への入力・別実行環境・継続的な書込許可は未対応として拒否します。ファイル承認では変更種別、パス、移動先、差分を表示対象に含め、対象情報が不足している場合や提示後に変更された場合は許可しません。`cancel` は応答送信前に他の回答受付も閉じます。

`stop()`と`clear_goal()`は終了要求をローカルに受け付け、入力・追加指示・質問の回答受付を閉じて戻ります。戻りはRPCの受付、Goal変更、実停止の完了を意味しません。active Goalのpauseまたはclearと既知ターンの中断は独立に試み、ターン終端後に公開端末を回収します。回収は`thread/backgroundTerminals/list`の全ページ取得、各processIdの終了、空一覧の確認を一組として行います。停止時に空回答は送りません。

終了中は`stopping`で、新規送信・再開はできません。必要なGoal操作と終端・回収を確認した`SessionStatus.phase == "stopped"`が停止完了を表します。通常ターンの失敗・中断も回収成功後に`stopped`となり、次の明示送信を受け付けます。終了操作が失敗すれば`error`を保持し、明示切断・再接続で復旧します。失敗後の遅いturnで中断・回収を自動再試行しません。公開一覧に属さない子孫プロセスの全終了は保証しません。

開始処理中の停止も保持します。まだ準備中ならturnを送らず、送信済みなら開始通知・応答で得たIDを中断します。通知が応答に先行して終端した場合も、`send()`は受付応答のIDを返します。終端が来ない通常停止は`stopping`のままです。`send()`の取消しや受付不明の通信失敗では接続を閉じ、自動再送しません。

`TextEvent` は `item_id` ごとに扱います。`replace=False` は本文への追記、`replace=True` は確定本文への置換です。開始応答より先に届く質問・本文・ターン終端も処理します。`LoginEvent` のURLは `SessionStatus.phase` が `authenticating` でなくなった時点で破棄してください。

`PlanEvent(turn_id, steps, explanation)`は公開計画の全一覧です。`steps`は`PlanStep(step, status)`の組で、空ならそのturnの計画を消します。ランタイム起動時に`tools.update_plan.enabled=true`を指定しますが、毎turnの計画出力を保証する設定ではありません。

`ReasoningEvent(turn_id, item_id, summary)`は公開要約の段落だけを持つ全置換イベントです。生のreasoning本文は含みません。`ActivityEvent(turn_id, item_id, kind, title, status, details)`はコマンド・ファイル変更・MCP呼出しの公開対象とテキスト結果を持ち、MCPの引数・画像・メタデータは含みません。結果はruntimeによって切り詰められる場合があります。本文・Plan・公開要約・活動の表示と記録は`turn/completed`受信で締め、同turnの後続更新は無視します。受信済み履歴は残しますが、遅い活動の最終状態は補いません。表示通知自体はゲーム入力の許可や成功を意味しません。

`TurnStarted(turn_id)`は、通常ターンまたは同じthreadの自律ターンを`turn/started`または自分の`turn/start`成功応答から採用したときに一度届きます。開始通知→質問・本文・終端→開始応答の順でも処理します。未知turnのitem・質問・終端だけでは採用せず、表示・要求を発行しません。開始要求の提出だけでは届かず、ターンの成功や継続中であることを保証する通知ではありません。要求IDの重複は同turn内で抑止し、終端でその記録を破棄します。

`GoalEvent(goal)`は公開Goalの確定値です。`goal`は`GoalState(objective, status, tokens_used, time_used_seconds)`、破棄後は`None`です。完了・休止・制限停止はターン終端と区別してください。`DialogueEvent(kind, payload, turn_id)`は保存向けの公開項目スナップショットです。項目完了時には`partial=False`、turn終端・切断時の未確定部分には`partial=True`が入り、一度だけ確定します。内部推論全文や未送信原稿は含みません。

EOFでは要求を失効させ、接続を閉じて短いエラー状態を通知します。並行した `close()` は同じ終了処理を待ちます。呼出し側を取り消しても終了処理は継続するため、ループを閉じる前に再度 `close()` を待てます。

`codex_home` を指定すると認証・履歴の保存先を分離できます。既存の資格情報をこのディレクトリへコピーする処理はありません。作業ディレクトリは絶対パスの既存フォルダーとし、開発リポジトリと分けてください。

ゲーム機器の制御はアプリが公開するMCPツールを通じて行います。Goalの自律継続はランタイムへ委任し、アプリ独自の継続ループは持ちません。APIキー認証は未対応です。

標準入出力のJSON一行は末尾改行を含めて受信2 MiB、送信1 MiBまでです。受信枠はMCP結果通知のpreviewと外側JSON用であり、元画像全体を通知から復元するための枠ではありません。モデルへ渡す画像はMCPのHTTP応答で配送します。
