# 型境界の見直し

## 問題の境界を掴む

`pyproject.toml` の対応Python版と `ty` の設定、対象コードの呼び出し側を確認します。型エラーを直す場合は `uv run ty check --no-progress` の結果を起点にします。

値を作る場所、渡す場所、使う場所を辿り、公開契約の不一致、内部の絞り込み不足、外部依存の型不足のどれかを見ます。型検査を通すためだけに呼び出し側の期待を広げると、問題の位置が隠れることがあります。

境界で実際に受け取る値、返す値、失敗の扱いに合わせて型を選びます。外部JSONの実行時検査と、検査後の内部値を扱う型を混同しません。

## 表現を選ぶ手掛かり

既存の具体的な型で足りるなら使います。次は選択肢であり、境界ごとに新しい型を作る指示ではありません。

| 表現 | 選ぶ場面 |
|---|---|
| `object` と絞り込み | 入力の型がまだ分からず、使用前に確認する |
| 具体的なunion | 成功・失敗など、取り得る形が有限で分岐が必要 |
| `TypedDict` | 辞書として扱うデータのキーと値の型を共有する |
| dataclass | 関連する値を一つの内部データとして扱う |
| `Callable` | コールバックの引数と戻り値だけを表せる |
| `Protocol` | 複数の実装が提供する操作を呼び出し側から定義する |

例えば外部JSONを `TypedDict` へ `cast()` しても、キーや値の検査にはなりません。既存parserで必要な条件を確認し、その後の値を内部で扱える型にします。別の検査層を重ねる前に、既存の境界が何を保証しているかを見ます。

## よくある見直し

- `T | None` は、未接続・未取得・結果なしなどの意味を呼び出し側と揃えます。初期化後だけ使える値なら、注釈だけでなく初期化経路も確認します。
- 外部ライブラリの型不足には、依存側の型定義、薄いアダプタ、限定した抑制などを比較します。`Any` が必要でも、内部の広い範囲へ伝播させない形を探します。
- 型検査の抑制を使う場合は対象の規則へ絞り、コードだけでは分からない制約があれば近くに理由を書きます。
- test fakeは本体が使う操作に合わせます。テストのためだけに公開APIを広げる前に、差し替える境界が適切かを見ます。

標準ライブラリの型を優先し、実行時に不要なimportは `TYPE_CHECKING` へ置きます。注釈の遅延評価は必要な場合に使います。

## 確認

```powershell
uv run ty check --no-progress
uv run ruff check .
```

公開APIでは型・説明・実際の振る舞いを合わせます。修正後は型検査と、振る舞いにも影響した場合の関連テストを確認します。
