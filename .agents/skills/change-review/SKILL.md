# 変更のレビュー

## 対象を掴む

今回の要求と差分を起点に、関連するコード・テスト・仕様を読みます。unitがある場合は変更の意図を知る資料として使い、現在の契約は仕様・アーキテクチャと実装で確かめます。

差分だけでは判断できない場合、変更されたAPIの呼び出し側、状態の更新元、資源の生成・解放まで範囲を広げます。例えば停止処理の変更なら、通常の完了や切断でも同じ経路を通るかを確認します。

## 差分を見る観点

必要な観点を選びます。全項目の評価表を作る手順ではありません。

| 観点 | 着目する箇所 |
|---|---|
| 要求と振る舞い | 完成条件、呼び出し側への影響、設定やデータの扱いの変化 |
| 所有と寿命 | 状態の更新元、task・接続・機器の所有者、失敗や取消し時の解放 |
| 構造の増加 | 新しい層・依存・設定・状態が今回の問題に必要か、既存の責務で扱えるか |
| 検証 | 実際の問題を検出するテストか、重要な境界をモックで消していないか |

構造の見直しでは、例えば次を辿ります。

- 同じ状態を別のフラグへ写しているなら、更新がずれる経路がないか。
- 呼び出し側と受け側で同じ検査をするなら、それぞれが異なる境界を守っているか。
- 新しい抽象化や汎用設定を加えたなら、現在の具体的な利用箇所があるか。
- 失敗時の代替処理を加えたなら、成功扱いで問題を隠したり、資源の所有を曖昧にしたりしないか。

行数やクラス数だけで良し悪しを決めません。小さな重複をまとめるために、変更箇所を跨ぐ複雑な共有状態が必要になるなら、そのままの方が扱いやすい場合もあります。

## 確認と報告

テスト結果は、そのテストが通る経路と合わせて判断します。機器の実際の応答や画面の使いやすさは、模擬機器や文言一致だけでは分かりません。追加確認は差分から生じた疑問に絞ります。

指摘には、問題が起きる条件、影響、該当箇所を示します。例えば「停止中に届いた通知が受付状態を戻し、次の操作を実行できる」のように、修正すべき振る舞いを説明します。

小さく直せる問題と、合意が必要な設計変更を分けます。修正まで依頼されている場合は対応し、レビューのみなら指摘を返します。任意の構造改善は、不具合の修正要求と区別します。

報告は重要な指摘と判断に影響する検証の不足へ絞ります。指摘がなければ短く伝えます。
