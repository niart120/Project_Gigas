# テスト設計の見直し

## 検出したい問題から選ぶ

まず、そのテストで検出したい不具合を具体化します。純粋な計算には小さい単体テスト、部品間のやり取りには結合テスト、機器や公開サービスとの適合には実接続の確認を選びます。

| 確かめること | 検証の例 |
|---|---|
| 値の変換・検査 | 境界値を含む単体テスト。入力と結果の組をパラメータ化 |
| 設定が実行へ渡ること | 保存・読込からサービスへの受け渡しを通す結合テスト |
| 停止と通知の競合 | 制御可能な接続相手や同期点で、順序を再現するテスト |
| 機器との適合 | 実機で送信・解除・映像への反映を確認 |
| 配布物の利用 | 作成した配布物を隔離環境へ入れ、importや起動を確認 |

## トレードオフ

Kent BeckのTest Desiderataを参考に、必要な観点を使います。

| 観点 | 確認すること |
|---|---|
| 対象を代表するか | モックや模擬データで、本当に問題が起きる境界を消していないか |
| 独立し再現できるか | 時刻、順序、共有状態、外部接続が結果を偶然に変えないか |
| 速く原因が分かるか | 日常的に実行でき、失敗から壊れた振る舞いを絞れるか |
| 保守できるか | 内部構造の変更で無関係に壊れず、準備と期待結果を読み取れるか |

すべてを最大化しません。結合テストの準備が増えても実際の競合を検出できるなど、検出したい問題に応じて選びます。

## 改善の手掛かり

- 時間待ちで不安定なら、イベントや制御可能な時計で進行を待てるかを確認します。実際の待機時間そのものが契約の場合は、その測定を残します。
- モックが実装の内部構造をなぞっているなら、置き換える位置をI/O境界へ寄せられるか検討します。偽物が返すイベント順や失敗条件も、実際の契約に合わせます。
- 一つのテストが多くの理由で落ちるなら、独立した振る舞いに分けます。一つの操作が持つ複数の結果は、同じテストで確認する方が読みやすい場合もあります。
- 同じ条件を複数層で確認しているなら、それぞれが異なる問題を検出しているかを見ます。単体で値域を調べ、結合では拒否結果の伝達を確認する、といった分担ができます。

既存テストの改善・統合・削除も候補にします。実機確認でしか分からない性質を単体テストへ無理に置き換えず、必要な検証を選びます。

検出したい問題に対して、テストをどう変えるとよいかを伝えます。
