# M3：製品表示への統合

2026-11-15。[表示改善計画](ACTIVITY_DISPLAY.md)のM3。M1で採用した見た目と更新方式を製品の会話・右側表示へ統合した。実モデル・実映像・機器を接続する受け入れはM4に残る。

## 実装と境界

会話は`ConversationTranscript`の単一文書とし、Qt標準Markdown、見出しのサイズ制御、応答種別の色・ラベル・左線、活動と推論要約の折り畳みを組み込んだ。既存`Transcript`はGoal・Planのプレーンテキスト表示に使い、質問・承認の操作部品と原文保持の仕組みを共有する。質問操作の配置は文書内frameを基準とし、操作部品の高さをframeの下余白へ確保する。

`_markdown.py`が解析と配送、`conversation_transcript.py`が会話文書と選択・閲覧位置、`reasoning_panel.py`が公開要約の最新部分を担当する。受信原文・phase・活動情報はM2の表示データに保持し、表示部品へ別の会話実行状態や保存責務を持たせていない。新しい外部依存は追加していない。

解析は最大1本の専用QThreadPoolで行い、ワーカーからGUIへ文書の所有を移してから反映する。各itemの未送出本文は最新1件にまとめ、50ms基準で配送する。完了本文による訂正と会話切替は古い結果を無効化する。多数の履歴の反映は約8msごとにイベントループへ戻し、停止・入力の受付を連続した一括反映で塞がない。一つの巨大な応答の反映時間を8ms以内に保証する仕組みではない。

時間判定には`perf_counter()`を使う。採用環境のPython 3.12で`monotonic()`の分解能は15.625msだったため、8ms単位の処理分割には使わない。切替試験の反復で差を検出し、高分解能の時計へ変更した。

解析資源はQApplicationが所有し、表示部品が先に破棄されても実行中のワーカーを壊さない。終了時は未送出分を破棄し、開始済み解析と結果の回収を既存の非同期終了処理で確認する。GUIスレッドで解析完了を待つ同期joinは使わない。

反復検査ではワーカーからGUIへ直接`moveToThread()`する箇所で停止を再現した。受け渡しを、ワーカー側でスレッドへの所属を外し、受信したGUI側で所属を設定する二段階へ変更した。所属のないQObjectを現在スレッドへ移す操作は[Qtの仕様](https://doc.qt.io/qt-6/qobject.html#moveToThread)に従う。文書を両側から同時に使わず、破棄前にもGUI側へ所属させる。停止時のスタックは移動箇所を示したが、Qt／Python内部のロック競合の詳細までは断定していない。

右側は「目標／今回の作業／推論」。公開要約の最新区分の末尾3行を表示し、折り返しが変わるリサイズ後も末尾を保つ。終了・中断では最後の本文を残して状態を付け、次turn・会話切替で消す。設定OFFでは右側と会話内の要約を隠し、Planに領域を戻す。非公開の推論、独自の要約・翻訳、サニタイズは追加していない。

## 操作と回帰検証

製品のQt結合試験で、Markdownの見出し・強調・リスト・表・コード・参照リンク、未完の記法から確定本文への更新、履歴再読込、活動詳細、公開要約の区切りを確認した。差分更新と新規解析を途中段階でも比較し、本文だけでなく段落書式・文字書式・リスト番号の一致を確かめている。公開phaseの欠落は既定のCodex表示にし、内容から推測しない。

応答をまたぐ選択・コピー、逆方向選択、訂正文、上方の活動展開と履歴追加、末尾追従、質問・承認の位置と操作、会話の読み込み失敗からの復帰、設定変更を既存試験と組み合わせて検証した。会話切替、空の訂正、履歴の小分け反映の途中での切替、表示部品の終了を実際の解析ワーカーで確認する試験も含む。

受け渡しの修正後、会話表示と埋め込み操作の27試験を15回連続で実行し、停止・失敗なく通過した。解析を一時的に保留して終了要求を出し、GUIが応答したまま結果を破棄・回収する試験も追加した。

単体・結合試験は1,120件成功。Ruff、書式検査、tyも成功した。実行コマンド：

```powershell
$env:QT_QPA_PLATFORM = 'offscreen'
uv run pytest tests/unit tests/integration -q --tb=short -o faulthandler_timeout=30
uv run ruff check .
uv run ruff format --check .
uv run ty check --no-progress --output-format concise
```

## 性能

Windows 11 10.0.26200、Python 3.12、PySide6 6.12.0、Qt windows、150%表示。M1と同じ送信器・計測方法を使い、描画部品だけを製品の`ConversationTranscript`に置き換えた。履歴100／1,000件、本文1万／10万字、20ms間隔の差分と200件の集中送信、33msごとの1280×720合成映像、10msのGUIタイマーを使用。映像の実取得や機器への停止完了を測るものではない。

| 履歴／本文 | GUI更新・描画 p95 | 送信→描画 p95 | GUIタイマー最大間隔 |
|---|---:|---:|---:|
| 100件／1万字 | 9.1ms | 74.4ms | 19.3ms |
| 100件／10万字 | 32.7ms | 175.4ms | 45.7ms |
| 1,000件／1万字 | 11.4ms | 76.7ms | 21.6ms |
| 1,000件／10万字 | 29.4ms | 180.4ms | 44.1ms |

M1の回帰基準（1万字33／150ms、10万字60／400ms、GUIタイマー最大100ms以内）を満たした。全条件で製品に保持した原文が送信内容と完全一致し、未反映差分は0。計測用に別途蓄積した文字列だけでなく、製品の`item_entry()`から取得した本文も照合している。[4条件の計測データ](validation/m3-matrix.json)。

1,000件／10万字を5秒送信×6回繰り返すと、GUI更新・描画p95は29.1〜31.5ms、送信→描画p95は185.3〜199.0ms、GUIタイマー最大49.1ms。停止要求のボタン受付は最大12.8ms。終了時のワーキングセットは256.9〜258.7MiBで、この短時間試験では増え続ける傾向はなかった。数時間のメモリ安定性の証明ではない。[反復計測](validation/m3-repeated.json)。

### 履歴の初回読み込み

上のストリーミング計測と分けて測った。1,000件の一括反映はGUIを約537ms塞ぐことを診断用の再生で確認したため、小分け配送に変更した。変更後のネイティブ画面では1,000件の読み込み全体が約3.9秒、GUIタイマー最大間隔22.6msだった。各結果を反映するたびに強制再描画する計測であり、実際の履歴ページ取得の所要時間ではない。[初回読み込み計測](validation/m3-history-load.json)。

初めて本文を描く1件には約291msかかり、通常フォントでは約250msだった。従来のプレーンテキスト`Transcript`でも同じ内容の初回描画が約254ms、2回目が約3msとなった。初回描画の遅延は残るが、Markdown追加によって初めて生じた現象とは判断しない。Qt・フォント・描画環境のどこに起因するかは未特定で、上記のストリーミング基準には含めない。[通常フォント](validation/m3-history-default-font.json)、[従来表示との比較](validation/m3-first-paint-baseline.json)。

## 実画面

製品のMainWindowへ公開イベントを再生する`product_demo.py`を使用した。M1の描画部品を使わず、サンプル本文だけを共有する。外部のモデル・機器・記録保存は起動しない。ネイティブウィンドウで活動詳細のクリック、ストリーミング開始・中断、終了後のプロセス正常終了を確認した。

| 状態 | 確認結果・画像 |
|---|---|
| 通常・配色 | 進捗の青と回答の紫、通常の本文色、左線、小さい見出しを確認。[150%暗色](validation/m3-150/short.png)、[100%明色](validation/m3-light-100/short.png) |
| 長いPlan・推論 | Plan内スクロールと推論の末尾3行が独立し、高さが本文量で変わらない。[長文](validation/m3-150/long.png) |
| 映像領域 | 1100×760論理pxでは347×195、サイドバーを閉じると446×251論理px。実映像の視認性はM4で確認。[サイドバー非表示](validation/m3-150/sidebar-closed.png)、[寸法](validation/m3-150/dimensions.json) |
| 縮小・展開 | 900×640論理pxでも本文とPlanは各領域内でスクロールし、入力欄と推論欄を維持する。幅変更後も字幕末尾を保持。[150%](validation/m3-150/compact.png)、[100%](validation/m3-100/compact.png)、[活動詳細](validation/m3-150/expanded.png) |

採用モックの左線とサイズ関係を維持する。OS標準の字体・部品を用いるため、画像モックの文字寸法・角丸・引用線との完全一致は対象外。活動を別itemとして表示し、進捗応答と架空の親子関係でまとめない。終了済みPlanを会話に残す既存仕様も維持した。

## M4への引き継ぎ

実モデルのphase・公開要約の出方、実映像の視認性、実機操作中の入力・中断を確認する。M3の合成映像とボタン受付の計測を、実映像取得・実機停止の完了確認には代用しない。初回描画の短い停止は上記の既知の制約として引き継ぐ。数時間の運転、未対応item種別の追加、配信向けサニタイズは今回のM3完了条件に含めない。
