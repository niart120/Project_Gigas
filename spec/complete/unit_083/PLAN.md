# プロジェクト管理の開発計画

状態: 実装・受入完了。M0〜M3を完了した。以下は着手時の計画であり、実施した確認と制約は[受入](ACCEPTANCE.md)、現在の仕様は[プロジェクト管理](../../../docs/design/functions/projects.md)、全体の到達点は[ロードマップ](../../../docs/roadmap.md)を参照する。

## 完成条件

GUIから表示名・1件のプロジェクトフォルダーを編集し、フォルダー欠落時も登録を削除できる。フォルダー変更では全所属チャットが同じID・履歴を保って追従し、再起動後も継続できる。途中失敗・結果不明を成功として隠さず、再取得と明示的な再試行で揃えられる。編集や削除だけでGoal・モデル・ゲーム入力を実行しない。

既存API検証は仕様末尾に要約している。全項目を最初から再調査せず、残る不確実性をM0で解消する。

## 段階と依存関係

| 段階 | 作業 | 完了を判断する状態 |
|---|---|---|
| M0: 管理更新の条件を確定 | activeな保存Goalを動かさずに作業場所を変更する経路、永続化の確認、アーカイブ済みチャット、実行範囲を追加検証する | モデル依頼やダミーturnなしで変更を確認でき、保持する状態・停止条件・拒否する条件が明らか。仕様で未検証とした経路を実装へ渡せる |
| M1: 管理APIとサービスを整える | Projectの更新・削除、全所属チャットの取得、作業場所の追従、資源の解放、再取得・再試行と選択対象の更新を実装する | 通常完了と部分失敗・結果不明・切断をサービス境界で検証し、旧資源を再利用せず、再起動後も未完了を検出できる |
| M2: GUIに統合 | 「…」メニュー、編集画面、削除確認、所在警告、通知からの復旧を組み込む。アクセス失敗は欠落と異なるアイコンにし、更新状態のバッジは追加しない | 合意した項目だけが表示され、フォルダー欠落・失敗後も操作できる。原稿と履歴を保持し、停止・切断を妨げないことを実画面で確認できる |
| M3: 製品として受け入れる | 同梱Codex・GUI・記録先をつないだ検証、必要な実モデル・機器での追従確認、現行文書の更新を行う | 下記の受入を満たし、未検証・制約が明示され、要求・責務・状態・依存の差分レビューを終える |

M0→M1→M2→M3の順に進める。M1では振る舞いを検証するテストを先に置き、通した後に責務・状態・依存を整理する。M2は既存PySide6の部品・配置を使い、今回の管理操作以外を再設計しない。

## M0で追加確認すること

- **管理目的の読込みとGoal**: active・paused・blockedなどの保存Goalと、通常turn・質問待ちを区別する。更新目的のresumeが自律実行を始めない経路を確認し、保証できなければ書込み前に拒否する。Goalの自動停止や状態変更が必要になる場合は、実装前に利用者へ仕様変更を相談する。
- **更新成功の確認**: 待機中の`thread/settings/update`直後に旧`cwd`が返る条件を確認する。購読・ロード状態の解放と再取得による永続化確認、および`runtimeWorkspaceRoots`と書込み範囲を新フォルダーに揃える経路を確定する。確認のためにモデルへ本文を送らない。
- **対象の網羅と保存状態**: 通常・アーカイブ済みの全ページを取得する。アーカイブ済みの作業場所変更はAPIが拒否したため、存在する場合は登録変更前に拒否する方針を利用者と合意した。複数チャット、0件、モデルプロバイダーの異なるチャット、フォルダーが既に消えた対象も扱う。
- **GIGASへの接続条件**: 実際の`workspace-write`設定で新しい作業場所と書込み範囲を検証する。旧MCP・記録資源を閉じて同じthreadを新しい作業場所で準備する手順と、接続世代・選択対象の更新位置を確定する。

M0で公開APIだけでは要件を満たせないと判明しても、DB直接編集、履歴破棄、新規threadへの置換を自動で採用しない。確認できた制約と選択肢を示して合意を取り直す。現時点では履歴を保持して変更できる基本経路を確認済みであり、履歴破棄を前提としない。

## 途中失敗の検証

障害を入れる位置と観測する結果を対応させる。RPCの成功・例外だけでは、保存の成否や旧資源の回収を判定しない。

| 障害・境界 | 確認する結果 |
|---|---|
| 変更前の一覧の2ページ目取得に失敗、旧writerの解放に失敗 | Project更新を送らず、原稿・履歴を保持する。再試行時に資源を二重所有しない |
| Project更新の拒否／サーバー反映後の応答欠落 | チャット更新を止める。再接続・再取得で保存済みrootを判別し、結果不明の要求を自動再送しない |
| 3件中2件目の更新で拒否／反映後の応答欠落 | 更新済みを保持して全体を未完了とする。新旧のどちらのフォルダーでも実行を再開せず、再試行で未完了分だけを処理する |
| 全件更新後の確認失敗、途中で切断・アプリ終了 | 再起動後にProjectと全チャットを読み直して判定できる。ローカルの一時進捗に依存しない |
| 古い接続・選択への遅着結果、外部からの削除・所属変更 | 別の対象へ反映せず、登録・対象を再確認する。消えたIDの代わりに新規threadを作らない |
| 削除反映後の応答欠落、既に削除されたID、一覧取得失敗 | 存在しないことを確認できた場合だけ削除済みを表示する。取得失敗を空一覧にせず、復元不能な「元に戻す」を置かない |

障害注入は制御可能な通信・サービスのテストで行い、永続化と再起動後の状態は隔離した実app-serverでも確認する。文書の説明文、状態名、見出しの固定文字列一致を品質検査には使わない。

## GUI・製品の受入

「…」から編集・削除へ進めることを、マウスとキーボードで確認する。編集対象の名前・絶対パス、長いパス、同名プロジェクトの識別、警告の形・読み上げ名、キャンセルの初期フォーカスを実画面で確認する。未保存値が削除対象へ混ざらず、通常画面に説明文や説明ツールチップを増やしていないことも見る。

フォルダー変更では、同じProjectに本文のある複数チャットを用意する。旧フォルダーが存在する場合と既に移動済みの場合について、同じID・履歴・所属を保持し、新しい作業場所と書込み範囲で明示実行できることを確かめる。再起動後の再開、入力原稿、Goalの目的・予算・利用量、旧記録が残り新しい記録先へ追記されることを確認する。攻略資料と記録のファイルを自動移動したと誤認させないよう、操作ガイドにも区別を書く。

削除では、フォルダー欠落時・チャット0件・追従未完了のいずれも登録を削除できること、所属チャットが本文・保存cwdを保って未所属になること、ファイルと記録が残ることを確認する。選択中の既存・未開始チャットの両方で原稿を保持する。アーカイブ済みチャットは保存状態を維持し、今回専用の閲覧画面は作らない。

実モデル・ゲームI/Oを用いる受入では、停止後のフォルダー変更、同じチャットの明示再開、新しい`records/<thread-id>/`への観測・入力・本文の保存を対象にする。モデルを使わない管理保存中にturnやゲーム入力が始まらず、保存・所在確認中も停止・切断が使えることを確認する。管理API検証だけを実機の受入完了とは扱わない。
