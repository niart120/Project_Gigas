# 管理更新に使うAPIの確認

2026-11-15、同梱Codex 0.167.0と隔離した専用homeで確認した。本文のあるチャットはlocalhostの固定応答で用意し、管理更新中のモデル要求件数を比較した。通常のGIGASデータは変更していない。

## 採用する経路

管理更新では、通常チャットの全ページとアーカイブ済みチャットの有無を調べる。アーカイブ済みがあればフォルダー変更前に拒否する。この範囲を利用者と合意した。表示名変更と登録削除ではチャットをロードしない。

通常チャットは`thread/goal/get`と状態の読込みで事前検査し、activeなGoalや実行中の対象を拒否する。pausedなGoalを持つチャットでは、目的・状態・利用量を保ち、モデル要求を増やさずに作業場所を変更できた。

読込み済みチャットへのresumeは変更指定を無視するため、`thread/unsubscribe`を待ってから`thread/resume`に新しい`cwd`と`runtimeWorkspaceRoots`を指定する。購読解除直後の`thread/read`がidleを返していても、この順序では新しい指定が反映された。settings/updateの直後には、保存済みの`cwd`と現在のenvironmentのパスが一時的に異なる応答があったため、今回の更新処理には使わない。

管理目的の読込みは読取り専用・ネットワーク無効で行い、MCPを有効にしない。管理処理にWindowsの書込み実行環境の準備を要求しない。通常の明示実行では、既存の実行準備でworkspace-write、作業場所、書込み範囲、MCP・記録先を改めて準備・検証する。

## 製品の管理処理を通した確認

`ProjectManagement`と製品の`CodexConnection`を実app-serverに接続し、本文のある3チャットを用意した。旧フォルダーを別名へ移した後、Projectの名前・rootを変更し、3チャットが同じID・所属・履歴を保って新しい場所へ追従した。サーバーを再起動して同じ状態を取得し、登録削除後は3チャットが未所属へ移ることを確認した。旧ファイルは残り、管理中のモデル要求件数は増えなかった。

実行ログはこのチャットと`tmp/project-removal-ux/product-manager-6f131145-aca3-45c7-8e2d-3d6d508ed3ea/summary.json`にある。tmp配下のログは恒久的な参照先とは扱わない。

## 確認範囲の限界

隔離homeのWindows実行環境はnotConfiguredだった。workspace-writeを要求してもreadOnlyが返る条件を確認したため、それを管理更新の成功と読み替えるのではなく、管理更新自身の要求をread-onlyに揃えた。製品の明示実行時の書込み範囲検査は維持する。

実モデル・実機・新しい記録先での再開は[M3の受入](ACCEPTANCE.md)で確認した。複数クライアントから同時変更される場合の原子性は保証しない。事前検査後に状態が変わった場合も、途中失敗として扱い、成功を補わない。
