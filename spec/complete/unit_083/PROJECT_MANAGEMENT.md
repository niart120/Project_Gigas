# プロジェクトの編集・削除と作業フォルダーの追従

状態: 実装・受入完了。以下は2026-11-15の検討時仕様を残す。M0で確定した採用経路は[API確認](M0_API.md)、実装と検証の到達点は[受入](ACCEPTANCE.md)、現在の正本は[プロジェクト管理仕様](../../../docs/design/functions/projects.md)を参照する。

現在の仕様は[会話機能](../../../docs/design/functions/conversations.md)、[デスクトップ画面](../../../docs/design/ui/desktop.md)、[データの配置・所有](../../../docs/design/data/storage.md)を参照する。

## 目的と範囲

利用者がGUIからプロジェクトの表示名・作業フォルダーを編集し、不要なプロジェクトの登録を削除できるようにする。作業フォルダーが既に削除・移動されていても、履歴の閲覧とプロジェクトの管理を可能にする。

フォルダー変更時は、所属する既存チャットも同じ作業場所へ追従させる。同じthread ID、所属、本文・活動履歴を保持し、新しいチャットへの置換や履歴の再構成は行わない。

チャットのアーカイブ操作とその閲覧画面、ピン留め、セクション、複数フォルダーの登録は今回の対象にしない。アーカイブ済みチャットが所属する場合は、フォルダー変更・追従の再試行を登録変更前に拒否する。通常チャットだけを黙って変更しない。表示名の変更と登録削除は可能とする。これは同梱CodexのAPI制約を追加検証したうえで2026-11-15に利用者と合意した範囲である。攻略資料やゲームI/O記録をコピー・移動・削除する機能も含めない。

## サイドバーと管理メニュー

「一覧」は左サイドバーのプロジェクト一覧を指す。各プロジェクト行に「…」を置き、「編集」「プロジェクトを削除」の2項目を提供する。同じメニューを右クリックとキーボードでも開けるようにする。メニューを開くために、そのプロジェクトの新規チャットや所属チャットへ切り替える必要はない。

フォルダーの所在を接続後の一覧取得、編集画面の表示、保存時に非同期で確認する。毎フレームの確認や常駐するフォルダー監視は行わない。実行前にも作業場所の存在・整合を確認する。

| 確認結果 | 表示・受付 |
|---|---|
| フォルダーが存在する | 通常表示 |
| 存在しない、またはフォルダーではない | 名前の左に独立した警告アイコン |
| アクセス拒否などで確認できない | 不存在とは別のアイコンを同じ位置に表示する。状態文言は常設しない |
| 所属チャットの追従に未完了・結果不明がある | 一覧のバッジや更新有無の表示は今回の対象外。失敗通知で詳細と再試行を案内する |

警告には`!`を認識できる形を使い、表示名そのものには加えない。色だけに頼らず、読み上げ名にも状態を含める。名前のコピー・編集には警告記号を混ぜない。警告があってもメニューと履歴閲覧は使える。長い絶対パスをサイドバーへ常設せず、編集画面で確認できるようにする。

通常画面には使い方・操作効果の説明文や説明ツールチップを追加しない。エラーには失敗した操作、影響、復旧操作を文章で示し、詳細を通知から再確認できるようにする。

## 編集画面

タイトルは「プロジェクトを編集」。編集開始時にIDで取得した公開情報を表示する。

| 項目・操作 | 内容 |
|---|---|
| 表示名 | 文字列を編集。前後の空白を除いて空なら保存しない |
| プロジェクトフォルダー | 現在の絶対パスを表示し、フォルダー選択で差し替える。登録は1件とし、追加・個別削除の操作は置かない |
| プロジェクトを削除 | 左下に破壊的操作として置き、別の削除確認を開く |
| キャンセル／保存 | 未保存の編集を破棄／変更を適用する |

現在のフォルダーが存在しなくても開ける。表示名だけの変更や登録削除に、旧フォルダーの存在・モデル・ゲーム機器・記録先の準備を要求しない。フォルダーを変更するときは、選択先が存在するフォルダーであることを保存前に確認し、作成・移動は行わない。書込み権限の確認は既存の実行準備でも行い、存在確認だけで実行可能とは判定しない。

同じフォルダーを指すパスはWindowsのパス比較規則で扱い、表記だけの差で全チャットを再更新しない。追従完了済みのプロジェクトで表示名だけを保存するときは、チャットの作業場所や実行資源を変更しない。追従未完了の場合は同じパスでの保存を再試行として扱い、未更新チャットも処理することを失敗通知で案内する。

保存処理中は二重保存と別の管理更新を防ぐ。画面を閉じても提出済みの要求を取り消したことにはせず、結果は主画面の通知から確認できる。保存前のキャンセルには副作用がない。

編集画面の削除ボタンは未保存の編集を保存せず、保存済みの名前・パスを使って削除を確認する。管理操作だけで現在のチャット選択や入力原稿を破棄しない。

## フォルダー変更と既存チャットの追従

### 保持するものと変えるもの

プロジェクトの登録フォルダーと所属チャットの`cwd`を新しい絶対パスへ変更する。以後の実行は新しい作業場所・`runtimeWorkspaceRoots`・書込み範囲で行い、旧パスを実行資源や画面の選択対象に残さない。チャットID、所属、保存履歴、Goalの目的・予算・累積利用量は保持する。Goalを自動で再開・削除しない。

ファイルは移動しない。旧フォルダーの攻略資料、`records/<thread-id>/`と観測画像はその場所に残り、履歴本文中の旧パスも書き換えない。資料を引き継ぐ場合のファイル移動は利用者が行う。新しい実行の記録は、新フォルダーの`records/<同じthread-id>/`を既存の保存仕様で開く。記録があれば追記し、なければ作成する。異なる記録の自動結合や上書き、旧フォルダーの再作成は行わない。

### 受付と更新手順

フォルダー変更・削除は実行、送信準備、質問・承認への回答配送、停止、入力回収が終わった状態で受け付ける。実行中の保存を自動停止や予約へ変換せず、既存の停止操作へ誘導する。保存中も停止・切断・終了を妨げない。

フォルダー変更は以下の順で扱う。

1. 接続と対象ID、旧登録値、変更先を確認し、当該プロジェクトでの新規作成・実行・別の管理更新を閉じてから所属チャットを全ページ取得する。通常・アーカイブ済みの双方を調べ、未取得ページを残したまま更新を始めない。アーカイブ済みチャットがあれば拒否する。通常チャットの実行状態・Goalと安全な更新経路を確認する。
2. 旧作業場所に結び付くMCP受付、保存待ち、writer、購読などを既存の所有者で回収する。解放が確認できなければ登録変更を送らない。
3. `project/update`で名前と新フォルダーを保存し、公開応答・再取得で登録値を確認する。この登録フォルダーを以後の追従先とする。
4. 所属チャットを同じIDのまま順次更新する。既に追従済みのチャットは省略し、各要求の結果と永続化された作業場所を確認する。更新のために本文やダミーのturnを送らない。
5. 所属一覧を再取得し、全件の作業場所を確認する。選択対象の`cwd`と見出しを更新し、古い要求結果で表示・資源を戻さない。全件の追従と必要な資源の回収を確認してから保存完了を通知する。

編集の保存だけではモデル応答、Goalの継続、ゲーム入力を始めない。管理目的の`thread/resume`でもactiveな保存Goalが動き出す可能性があるため、安全な読込み経路はM0の必須確認とする。安全を確認できない対象があれば、書込み前の検査で保存を拒否して対象と理由を示す。Goalの自動一時停止・再開を代替手段として無断で追加しない。

読込み済みチャットでは`thread/resume`のパス指定だけで変更済みと判定しない。`thread/settings/update`の成功直後にも`thread/read`が旧パスを返す場合があるため、永続化の確認方法と実行資源の作り直しをM0で確定する。新しい作業場所と書込み範囲を確認できるまでは実行を許可しない。

## 途中失敗・切断・再起動

プロジェクトと複数チャットの更新は一括確定できるとは扱わない。更新済みのチャットを自動で旧フォルダーへ戻さず、サーバーの現在値を確認して新フォルダーへ揃える。

| 失敗した段階 | 扱いと復旧 |
|---|---|
| 事前検査・一覧取得・旧資源の解放 | 登録変更を送らない。既存の登録・履歴・原稿を保持し、解放済み資源は次の明示実行で作り直す |
| `project/update`が明確に拒否された | チャットの更新へ進まない。サーバー上の登録値を読み直し、入力値を修正して保存できるようにする |
| `project/update`の応答が失われた | 結果不明として以後の書込みを止める。再取得し、保存済みの登録値を確認してから次の操作を決める。要求をそのまま自動再送しない |
| 登録更新後に一部チャットの更新が失敗・結果不明となった | 更新済みを保持し、処理を止めて失敗を通知する。確認済み件数と失敗・未確認の対象を示す。自動ロールバックや一覧の更新バッジは設けない |
| 全チャット更新後に最終確認が失敗した | 成功済みと推定せず、確認未完了として扱う。再取得だけで整合が確認できれば完了にできる |
| アプリ終了・切断・再起動 | 処理の完了とは扱わない。再接続後に登録と所属チャットを読み直し、未完了を判定する。書込みの再開は利用者の再試行で行う |

結果不明は失敗とも成功とも決め付けない。切断時は旧接続の要求を回収し、新しい接続へ遅着した結果を適用しない。resume後の実行状態を確認できない場合は既存の共通停止・切断で回収し、自動再開しない。

追従先の正本はCodexのプロジェクト登録、各チャットの作業場所の正本は公開metadataとする。GIGAS独自の永続Project台帳や更新進捗ファイルは作らない。再試行では全ページを再取得し、登録フォルダーと異なるチャット、または変更を確認できないチャットだけを対象とする。通知の件数を更新済みの証拠として使わない。

起動直後に全チャットの取得が終わっていなければ整合が確認できたとは扱わない。少なくともプロジェクトの実行・新規チャットの開始前には全件確認し、不一致があればエラーとして保存の再試行へ案内する。一覧へ更新状態のバッジは追加しない。旧`cwd`が存在することを理由にそのまま実行せず、新`cwd`へ表示だけを差し替えて実行することもしない。

未完了のプロジェクトでは、履歴閲覧、編集からの再試行、登録削除を受け付ける。実行・新規開始・別フォルダーへの再変更は完了まで受け付けない。他プロジェクトや未所属チャットまで恒久的に操作不可にはしない。

他クライアントによる更新や対象の削除・所属変更を検知した場合も、現状を上書きせず再取得を求める。同じGIGAS内では更新を直列化するが、公開APIにない複数クライアント間の排他や原子性は保証しない。

## プロジェクトの削除

サイドバーと編集画面から同じ確認を開く。タイトルは「〈保存済みの表示名〉を削除しますか？」とし、保存済みの絶対パスも対象確認に使えるようにする。

本文は次の意味を短く伝える。

> プロジェクトの登録を削除します。既存のチャットは未所属に移ります。コンピューター上のファイルは削除されません。

「キャンセル」と「プロジェクトを削除」を置き、削除を破壊的操作として区別する。初期フォーカスはキャンセルに置き、Enterで削除を誤確定させない。編集画面の未保存値は確認対象へ混ぜない。

削除は保存済みIDを使って`project/delete`を呼ぶ。フォルダー欠落や追従未完了でも受け付ける。要求前に対象の新規作成・実行・管理更新を閉じ、旧MCP・保存待ち・writerなどを回収する。回収が確認できなければ削除要求を送らない。旧フォルダーを作り直さず、所属チャットのresume・個別削除・アーカイブやGoalの変更も行わない。

成功後はプロジェクト一覧から除き、未所属一覧を再取得する。選択中の既存チャットがそのプロジェクトに属していれば、同じID・本文・原稿を保ち、所属だけを未所属へ更新する。未開始の新規チャットを選択していた場合も、原稿を保って未所属へ変える。旧プロジェクトに結び付いた実行資源は再利用しない。

削除後の既存チャットは保存済み`cwd`を保持する。追従未完了の状態で登録を削除しても、チャット間の作業場所の不一致を修復したことにはならない。作業場所が欠けたチャットは履歴を閲覧できるが実行はできない。エラーにはこの影響を含める。

明確な拒否時は一覧を残し、原因を通知する。応答が失われた場合は結果不明として一覧を再取得し、対象IDが存在しないと確認できれば削除済みとして反映する。取得失敗やページ未取得を「削除済み」と解釈しない。削除の連打・自動再送、実際には復元できない「元に戻す」の表示は行わない。

## 責務とデータの境界

| 担当 | 変更後に持たせる責務 |
|---|---|
| GUI・画面の調整役 | メニュー、編集・確認、警告、入力原稿と選択の表示。世代・対象IDを照合して結果を反映する |
| アプリケーションサービス | 管理操作の直列化、受付条件、全ページの取得と再確認、追従の調整、部分失敗と再試行の結果通知 |
| Codex管理・実行境界 | 公開APIの変更要求と応答の検証、管理読込みの寿命、作業場所と書込み範囲の確認 |
| 会話資源の所有者 | 旧MCP・保存・writerの回収、新しい作業場所での再準備 |

Codex専用homeのDB・rolloutを直接編集しない。`GameIoRecordWriter`へプロジェクト管理や移行処理を追加しない。永続的な登録情報と一時的な操作結果を分け、新しいスレッド・汎用の処理基盤・二重の会話状態を前提にしない。

## API検証で確認済みの事実と限界

2026-11-15、GIGAS同梱Codex 0.167.0を隔離した専用homeで動かして確認した。本文生成はlocalhostの固定応答を使い、実モデルの判断やゲーム機器は検証対象にしていない。通常のGIGASデータは変更していない。

| 確認対象 | 結果 |
|---|---|
| `project/update`で名前・rootを変更 | 再起動後も保持。これだけでは既存チャットの`cwd`は変わらない |
| 未読込みチャットの`thread/resume`に新`cwd`と`runtimeWorkspaceRoots`を指定 | 同じID・所属・本文を保持して変更。旧フォルダー欠落時も成功し、再起動後も保持 |
| 読込み済みチャットの`thread/resume`に変更先を指定 | 旧作業場所のまま。変更手段としては使えない |
| 読込み済み・待機中の`thread/settings/update`で`cwd`を指定 | 次turnから新作業場所を使用し、再起動後も保持。直後の履歴読込みでは旧パスが返る例があった |
| 未読込みチャットへ`thread/settings/update` | 拒否された。読込み経路の区別が必要 |
| 更新後の実コマンド | 作業場所を明示しない相対パス参照で、新フォルダー内のファイルを取得して終了コード0 |
| `project/delete` | root欠落時も成功し、再起動後も削除状態を保持。本文のあるチャットは未所属に移り、本文と`cwd`を保持。フォルダー・ファイルは残った |

これらはGUIへの統合、active Goal・処理中turn、アーカイブ済みチャット、複数クライアント、途中失敗からの再試行、実モデルと新しい書込み範囲の受入を証明するものではない。未検証項目を確認済みに置き換えず、[M0と受入条件](PLAN.md)に従って確かめる。
