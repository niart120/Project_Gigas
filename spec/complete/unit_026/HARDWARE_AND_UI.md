# 設定・状態表示変更後の実機と画面確認

[設定・状態表示の再設計仕様](SETTINGS_AND_STATUS_REDESIGN.md)の受入記録。2026-11-11に実施した取得API単体の測定と、Windows上の実GUI操作を分けて記す。過去の[unit023実機記録](../../complete/unit_023/HARDWARE_ACCEPTANCE.md)を今回の変更の検証へ代用しない。製品の観測保存・MCP接続・ゲーム入力は対象外である。

## 環境と根拠

Windows、Python 3.12.10、Qt 6.12.0。機器はLive Gamer 4K 2.1系、OS表示名`USB Video Device`、VID 07CA / PID 0575。列挙結果からDevicePathを完全一致で選び、DirectShow（API番号700）で取得した。取得側の固定依存はOpenCV headless 4.14.0.94、cv2-enumerate-cameras 1.4.0、NumPy 2.5.4。全モードの要求FPSは60である。

根拠は作業用の次のハーネス・JSON・画像と、担当者による実画面の確認である。`tmp/`のログと画像は作業用成果物であり、ゲーム画像をGitの追跡対象へコピーしていない。この記録に測定値と確認範囲を残す。

| 種類 | 根拠 | 確認する範囲 |
|---|---|---|
| 取得API | `tmp/unit026/hardware_modes.py`、`hardware-modes.json` | 自動・固定要求の実寸、独立reader、保持画像、停止 |
| 代替方式 | 同ハーネスの`FirstApiFailure`、`hardware-fallback.json` | 第一方式へ失敗を注入した際のエラーと回収 |
| Windows GUI初回 | `tmp/unit026/native_acceptance.py`、`native-ready.json` | 設定操作、世代切替、表示のみの変更、終了 |
| Windows GUI最終 | 同ハーネスの`--final`、`native-final.json`、`native-final-settings-0..2.png` | FullHDゲーム映像、未保存変更の破棄、OK完了待ち、映像情報、取得中の終了 |
| 画面の内容 | `tmp/unit026/native-generation-3.png`、担当者の実画面確認 | ゲームタイトル・文字、配置、状態表示 |

APIハーネスの入口は`uv run python tmp/unit026/hardware_modes.py`。GUIは`uv run python tmp/unit026/native_acceptance.py`で、通常のWindows画面へ表示する。GUI検証専用のTOMLを使い、Codexへの接続やゲーム入力は実行していない。ハーネス内の一時画像書き出しは、製品の画像保存機能ではない。

## 取得API単体の測定

各要求で最初のFrameを取得後、約6秒間、プレビュー相当のreaderを20ms間隔で参照した。別readerが最初のFrameを保持したまま、取得連番と後続の読み取りが進むことを確認した。Qt描画・画像変換・MCP処理を含まない。

| 要求 | 実Frame寸法 | 最初のFrameまで | 終端snapshotの実測FPS | 連番の進行 | 参照した異なるFrame | 切断要求からidleまで |
|---|---|---:|---:|---|---:|---:|
| 自動（幅・高さを要求しない） | 640×480 | 2.889秒 | 59.67 | 2→360 | 293 | 0.083秒 |
| HD（1280×720） | 1280×720 | 3.652秒 | 59.33 | 1→357 | 288 | 0.105秒 |
| FullHD（1920×1080） | 1920×1080 | 3.310秒 | 59.31 | 1→356 | 284 | 0.062秒 |
| WQHD（2560×1440） | 2560×1440 | 3.670秒 | 58.82 | 1→353 | 278 | 0.063秒 |
| 4K（3840×2160） | 3840×2160 | 3.142秒 | 49.67 | 1→299 | 266 | 0.083秒 |

すべて機器報告は60.00024 FPS、API番号は700、代替診断は空だった。表の実測FPSは停止前に最後に参照した`CaptureSnapshot.measured_fps`である。監視側が最初と最新に観測したFrameの連番差を、そのFrameの単調取得時刻の差で割った累積取得レートであり、ハーネスの6秒の壁時計区間から別途計算した平均や表示レートではない。最初の画像までの時間には子プロセスの起動・列挙・機器openを含む。停止時間は10ms間隔の状態観測を含み、光学的遅延やドライバー内部だけの処理時間を表さない。

全5モードで保持したFrameの画素が不変だった。切断直後の新しいsnapshotは`frame=None`、各回の解放は`graceful`。最後のshutdown後は監視スレッドが停止し、`multiprocessing.active_children()`は空だった。

固定4モードでは要求と実Frame寸法が一致した。自動は640×480になり、最大解像度を自動選択する動作ではなかった。これらはドライバーから届いたBGR画素の寸法であり、HDMI原信号の解像度、機器内部での拡縮の有無、全機器での要求受理を証明しない。要求と異なる有効寸法の受入は、機器非依存の[取得境界試験](../../../tests/unit/test_capture_backend.py)と[サービス結合試験](../../../tests/integration/test_capture_service.py)で確認する。

4Kの49.67 FPSは、この機器・環境・短時間測定で観測した値である。要求60 FPSや機器報告60 FPSを、共有画像が常時60 FPSで更新される保証として扱わない。処理律速の箇所は今回特定していない。

## 代替APIの成立範囲

実環境のOpenCV registryでは、DirectShowの`hasBackend(700)`が`True`、Media Foundationの`hasBackend(1400)`が`False`だった。利用可能な取得方式は`(700,)`であり、MSMFへの実機代替試行はできなかった。

`FirstApiFailure`はDirectShowのopenだけを未接続の`cv2.VideoCapture()`へ差し替える。実行結果は`映像取得元を開けない`、診断は`取得方式 700: 映像取得元を開けない`。有効な次候補がなく、取得に成功せず正常なエラーへ収束した。最後は`graceful`、監視スレッド停止、残存子プロセス0だった。これは「実機でMSMFへの代替取得に成功した」という確認ではない。

同一IDの再列挙、正常release・exit 0・親の資源回収後だけ次候補を開くこと、全候補共通の開始期限、停止後や初回Frame後に代替しないことは、[代替方式の結合試験](../../../tests/integration/test_capture_fallback.py)で故障注入して検証した。実ドライバー固着やMSMFの実動作は、この機器非依存試験と区別する。

## Windows GUI初回の操作と終了

実モニターの拡大率150%（DPR 1.5）、ウィンドウはHDプリセットの1280×720論理px。Qt offscreenではなく、Windowsの通常画面で操作した。取得画像のHD/FHD/4Kとは独立したウィンドウサイズである。

担当者が一般タブの表示設定、I/Oタブの映像入力と機器行付近の操作、設定ダイアログの配置を視認した。初回FullHD取得では`NO SIGNAL`を表示しており、画素を取得できたこととゲーム映像を表示できたことを分ける。その後、ユーザー側で映像出力が復帰し、ポケットモンスター ファイアレッドの導入映像とタイトル文字を確認した。`native-generation-3.png`でもゲーム名、著作権表記、左の映像領域と右のCodex領域、左右下部の状態表示を読取り確認した。

| 接続世代 | 要求 | 実Frame寸法 | 最終の実測FPS | 主画面へ渡した異なる連番数 |
|---|---|---|---:|---:|
| 1 | FullHD | 1920×1080 | 60.00 | 1464 |
| 2 | 自動 | 640×480 | 59.06 | 2387 |
| 3 | 4K | 3840×2160 | 49.84 | 1215 |
| 4 | 自動 | 640×480 | 59.95 | 3987 |

設定から自動→4K→自動へ変更すると、旧取得の停止を経て新しい世代で取得した。最後にプレビューをストレッチへ変更したときは世代4を維持し、取得設定の切替を伴わなかった。メニューから映像を停止し、idle / gracefulへ進み、アプリを終了した。

約467.48秒のセッション終了時に、保持Frame不変、`capture_alive=False`、`cleanup=graceful`、設定I/O・Codex用サービスの停止、残存子プロセス0を記録した。Codex用スレッドの停止確認は、外部Codex接続の実機確認ではない。

GUI側の実測FPSも取得サービスの終端snapshotであり、描画FPSではない。「主画面へ渡した異なる連番数」は`VideoView.set_frame`に渡した連番の集合の大きさで、モニターへの提示回数を測っていない。GUIの処理にはプレビュー変換・Qt描画・20msの計測timer・一時JSON書き出しが含まれ、API単体の負荷とは異なる。両者の近い数値から処理余力や長時間性能を推定しない。

## 最終GUI確認

`uv run python tmp/unit026/native_acceptance.py --final`で別起動し、同じWindows画面・150%・HDウィンドウで確認した。以下の操作結果は担当者による実画面の観測、数値と終了状態は`native-final.json`に基づく。

1. 設定の一般・I/O・Codexタブを開き、入力欄と下部のOK・キャンセル・適用が見えることを確認した。保存画像`native-final-settings-0..2.png`も読取り確認した。Codexのモデル欄へ`cancel-check`を入力してEscで閉じ、再度開くと未保存値が破棄されていた。
2. I/Oタブで`USB Video Device`を選んでOKを押した。接続中はOKが無効になり、最初のFrameが取得されてから設定ダイアログが閉じた。要求FullHD・60 FPSで、ファイアレッドの導入映像とタイトル文字を実画面で確認した。`native-final-generation-1.png`にもゲームの導入映像が写っている。
3. 「表示→映像情報…」を開いた。要求値、実Frame寸法、FPS、取得方式、世代・連番を確認し、情報画面の連番が1890に固定されたまま、プレビューと独立readerが進むことを観測した。常時更新されない情報本文と、進行中の取得を区別できた。
4. 映像情報を開いたまま主画面のXを座標指定で押し、正常終了した。最初のUIAによるX操作は実行できていなかったため、アプリが終了要求を拒否した結果として扱わない。

| 最終セッションの項目 | 結果 |
|---|---|
| 取得 | 世代1、要求FullHD、実Frame 1920×1080、DirectShow 700、代替診断なし |
| FPS | 要求60、機器報告60.00024、最後に参照したsnapshotの実測59.991 |
| 進行 | 最後の取得連番23496、主画面へ渡した異なる連番10377。表示フレームレートの保証ではない |
| 開始 | connecting観測からstreaming観測まで約3.180秒 |
| 終了 | stopping観測からclosed観測まで約0.071秒。20ms間隔の状態観測を含む |
| 回収 | `held_frame_unchanged=True`、`capture_alive=False`、`cleanup=graceful`、`settings_stopped=True`、`codex_stopped=True`、`children=[]` |

セッション全体は約628.43秒、取得中の観測は約391.66秒だった。FullHDでゲーム画素を表示できたこと、情報画面と取得の独立、表示中に所有するサービスを終了できたことを確認した。長時間連続運転やCodex接続・MCP負荷の確認へは拡張しない。実コピーと本文・選択・スクロールの固定は[映像情報の結合試験](../../../tests/integration/test_video_information.py)でも検証している。

## 設定エラーからの復旧

`uv run python tmp/unit026/native_acceptance.py --broken`では、隔離した不正TOMLで起動した。主画面の短い失敗バナーから、設定画面と詳細へ到達できた。一般タブの設定パスは読取り可能、OK・適用と編集項目は無効、キャンセルと詳細は有効だった。詳細では日本語の理由と復旧操作、ファイルパス、TOMLの行・列を確認した。

検証用ファイルを正しいTOMLへ修復した後、ファイルメニューの再読込を操作すると、HD設定が読み込まれ、設定の編集とOKが有効へ戻った。設定内の失敗表示は消え、既存の通知詳細は過去の診断を保持した。設定と通知を開いたまま主画面を終了し、`native-broken.json`で全サービス停止、`graceful`、残存子プロセス0を確認した。この確認ではカメラを接続していない。

最終版の通常設定画面は[一般](assets/settings-general-windows.png)と[I/O](assets/settings-io-windows.png)へ保存した。Windows 150%表示で実アプリのウィジェットを取得した画像であり、設計時のモックとは区別する。

## 小画面・長名とキーボード

`uv run python -X utf8 tmp/unit026/offscreen_final.py`で現在のウィジェットを合成データとMeiryo UI 9ptで描画した。主画面960×540で分割を左右それぞれに寄せても、短い状態は読み取れ、長い機器・モデル名だけが省略された。状態領域の左端は対応ペインと一致した。設定620×380の3タブはスクロールなしで収まり、620×260のI/Oも縦42pxのスクロールでシリアル欄へ到達し、下部の3ボタンは常に画面内に残った。画像9枚を目視し、`tmp/unit026/offscreen-final/metrics.json`で寸法と到達を補助確認した。これはoffscreenの合成検証であり、実モニターのDPI確認とは分ける。

この受入で、Qtの表示後にOKが既定ボタンとなり、編集欄のEnterや、キャンセル・適用にフォーカスしたEnterまでOKへ流れる不具合を再現した。[キーボード回帰](../../../tests/integration/test_settings_keyboard.py)を追加して修正後、各タブの項目と下部ボタンへのTab移動、入力欄のReturn/Enterによる誤適用なし、ボタンの明示操作とコンボの選択確定を確認した。

Windows 150%でも`native_acceptance.py --keyboard`で再確認した。モデル欄へ検証値を入力してReturnを押した時点では、設定画面を保持しTOMLのモデル値は空のままだった。モデル→エフォート→認証方式→OKへTabで移動し、OKのReturnで初めて検証値が保存され画面が閉じた。`native-keyboard.json`でアプリ終了後の全サービス停止、`graceful`、残存子プロセス0を確認した。カメラ・Codex接続・ネイティブIMEの変換はこの再確認に含めていない。

## 未検証・対象外

Linux・macOSの実機とアプリ起動、MSMFによる実取得、他機器、物理抜去、実ドライバー固着時の強制終了、長時間連続運転、複数モニター間のDPI切替、光学遅延は未検証。Windowsの150%以外のnative表示倍率を、この確認の成功に含めない。

画像保存・MCP応答・観測側の加工や実負荷はU04、ゲーム入力・即時停止はU05で扱う。今回のreader保持や検証用PNG書き出しは、それらの実装完了を意味しない。全体の自動試験・型検査・ビルド・品質ゲートは、親仕様の検証欄で別に記録する。
