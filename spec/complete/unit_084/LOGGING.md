# 異常の経過と原因を追うためのロギング設計

2026-11-17のチャットで合意した設計。2026-11-18に実装・検証を完了した。現行仕様は[診断ログ仕様](../../../docs/design/data/diagnostics.md)、利用手順は[診断ガイド](../../../docs/guides/diagnostics.md)を参照する。

## 目的と範囲

通常運用で発生した異常について、発生した処理、その前後の状態、利用者による復旧操作、取得できた原因情報を後から照合できるようにする。

起動・設定、映像取得、入力機器、ゲーム記録の保存、Codex接続・会話実行・Goal、停止・終了を対象とする。診断モードは設けず、必要な情報を常時記録する。外部サービスが返さなかった原因情報の復元や、今回のBad Requestの再現・根本原因特定は完成条件に含めない。

## 記録の所有と責務

| 情報 | 所有者と扱い |
|---|---|
| 会話本文、ターン状態・エラー、保存されたGoal | Codex App Serverを正本とし、公開APIから参照する |
| GIGASで要求した停止・再開・接続などと受付結果 | GIGASの共通診断ログへ保存する |
| GIGASが受信したGoal状態変化、ターン失敗、通信切断 | 受信した事実として共通診断ログへ保存する。会話履歴の別の正本にはしない |
| 映像・入力・保存・GUI・プロセス管理の異常 | GIGASの共通診断ログへ保存する |
| App Server内部の警告・エラー | 標準エラー出力から取得可能な範囲で共通診断ログへ取り込む |
| ゲーム入力・観測・提出本文・確定応答 | 既存の`records/<thread-id>/events.jsonl`と観測画像に保存する |

App Serverの保存済みターン状態・エラーは`thread/turns/list`で取得できる。Goalの現在値と更新通知は取得できるが、過去の状態遷移を一覧取得できる保証は確認できていない。GIGAS側では通知から原因や操作主体を推定せず、自身が行った要求と受信した通知を区別して残す。

`events.jsonl`への実行履歴追加や`execution.jsonl`の常設は行わない。調査には共通診断ログ、App Serverの履歴、既存のゲーム記録を組み合わせる。プロジェクトフォルダー単体で全経過を復元することは今回の要件としない。GIGASによる容量整理はCodex専用homeやゲーム記録には適用しない。

## 保存先と形式

設定ファイルと同じ親フォルダーの`logs/`に、起動ごとの保存先を作る。既定の配置は次のとおり。

```text
%LOCALAPPDATA%/GIGAS/logs/
  20261117T093000Z_12345/
    .lock
    gigas.jsonl
    gigas.jsonl.1
    ...
    gigas.jsonl.9
```

フォルダー名はUTCの開始日時とGIGASのPIDで構成する。独自のUUIDは発行せず、同名フォルダーへの連番付与などの特別な衝突対処も設けない。

UTF-8の1行1件のJSON形式で保存する。基本項目はUTC時刻、重要度、発生箇所、イベント名、メッセージ、PIDとする。開始日時を起動情報として残し、必要に応じてCodex接続・会話・ターン・入力操作の識別子を付ける。分からない識別子は推定しない。子プロセスのPIDを扱う場合は、GIGAS自身のPIDと区別する。

エラーには取得できた例外型、エラーコード、メッセージ、追加情報、スタックトレースを付ける。JSONの具体的なキー名やイベント名は実装時に揃える。時刻と関連IDでApp Serverの履歴およびゲーム記録と照合する。

## 記録対象と粒度

| 対象 | 記録する内容 |
|---|---|
| 起動・終了 | 開始、正常終了、版・実行環境、終了処理の主要な結果 |
| 設定・機器・接続 | 設定適用、映像・入力・Codexの接続と切断、操作結果と失敗内容 |
| 会話実行 | 実行開始・終端、停止・再開要求と受付結果、受信したGoal状態変化 |
| 異常 | 通信・ターン・入力・観測・保存などの失敗、関連IDと取得できた詳細 |

正常系はINFOを基準に節目を残し、警告・エラーは異常の程度に応じて記録する。毎フレーム・毎入力の成功、応答の断片、Goalの利用量だけの更新は共通ログへ重複記録しない。通常の通信本文や画像は収集しない。

RPCのエラー応答やターン失敗について、現在捨てている詳細を診断経路へ渡す。画面用の短い表示と診断用の詳細は分ける。起動境界や非同期処理の例外も、捕捉できる範囲で記録する。OSによる強制終了やネイティブクラッシュの完全な捕捉までは保証しない。

映像取得子プロセスの例外は、既存の64 KiB上限の制御通知へ診断用トレースバックを付ける。長いトレースバックは末尾6,000文字を保持し、先頭を省略した旨を明記する。フレーム転送や通知の容量上限は変更しない。

## App Serverの診断出力

子プロセスに`RUST_LOG=warn`と`LOG_FORMAT=json`を明示し、親環境の設定に左右されず警告・エラーを常時収集する。これは標準エラーへの出力設定であり、Codex内部DBの保存内容や保持方針をGIGASが管理するものではない。

標準エラーには初期化前などの非JSON出力もあるため、それも取り込めるようにする。受信コールバックでディスク書き込みを待たない。UTF-8の途中で分割された受信、改行のない出力、終了時の不完全な末尾を扱い、取り込み処理が標準出力のRPC処理を妨げないようにする。

## 認証情報の扱い

認証ファイル、環境変数一覧、正常な通信本文は収集しない。記録するエラー詳細とApp Server出力には、既知の認証項目、Bearer形式、GIGASが発行した接続用トークンなどの除外処理を適用する。その他のエラー文やパスは調査に必要な情報として保持する。

任意の文章から未知の秘密情報を完全に判定できるとは扱わない。ログは無確認で外部公開できるものではない。除外処理はファイル保存前に適用し、保存失敗の通知や代替出力でも認証情報を露出させない。

## 容量とファイル管理

各起動のログは1ファイル10 MiB、使用中を含め10本とし、約100 MiBまで保持する。標準の`RotatingFileHandler`で`maxBytes=10 * 1024 * 1024`、`backupCount=9`を指定する。

終了済みの起動フォルダーを開始日時順で直近10回分保持し、古いものからフォルダー単位で整理する。稼働中の起動は別枠で保護する。全体は終了済み約1,000 MiBに稼働中の起動分を加えた容量が目安となる。単一レコードや削除失敗による超過があるため、厳密なディスク使用量上限とはしない。

稼働中の判定にはOSのファイルロックを使い、PIDや`.lock`の存在だけで判断しない。多重起動を許容し、他の稼働中プロセスのログへ書き込んだり削除したりしない。

整理は起動時とログ保存を終えた正常終了時に行う。整理同士が競合する場合は一方が見送り、削除できないフォルダーは残して次回に処理する。削除対象はGIGASが管理する起動フォルダーに限定する。異常終了で残ったロックファイルだけを理由に永久保護しない。

日数制限、圧縮、総バイト数による追加整理は設けない。

## 保存処理と失敗時の動作

Python標準の`logging`と`python-json-logger`を採用する。`QueueHandler`、上限なしの`queue.SimpleQueue`、`QueueListener`、`RotatingFileHandler`を組み合わせ、書き込みを別スレッドへ渡す。

独自の優先制御・間引き・詳細な欠落集計は加えない。ディスク処理が戻らない場合や大量の異常発生時にはキューがメモリに蓄積し得る。この制約はファイルの容量上限とは別であり、実測で問題が出た際に見直す。

標準`QueueHandler`による例外情報の整形を踏まえ、必要なトレースバックがJSONに残るようにする。関連IDは書き込みスレッドで推測せず、イベント発生側で渡す。

保存先の作成・書き込み・ローテーションに失敗してもゲーム操作と攻略は継続する。既存の通知経路で、失敗内容、記録できていないこと、対象パスを知らせる。同じ失敗を繰り返し通知せず、保存失敗通知から同じログへ再帰的に書き込まない。復旧した場合は、その事実を残す。失われたログの再構成や正確な欠落件数の保証は行わない。

正常終了時はゲーム入力の停止と機器の解放を優先する。その経過を記録した後、新しいログの投入を終え、保存待ちを回収してハンドラーを閉じる。回収待ちでGUIスレッドを塞がない。強制終了時の末尾の保存や、ディスク処理自体が停止した場合の終了時間は保証しない。

## 利用者への案内

記録レベル、容量、保存先構成はアプリ内の既定値とし、設定画面・設定ファイルの項目は増やさない。保存場所と調査時の参照方法はガイドへ記載する。ログ保存失敗の通知詳細には対象パスを表示する。専用ログビューアーや診断ファイルの書き出し機能は今回設けない。

## 完成条件と検証

異常と復旧の経過が保存され、時刻とIDで関連する処理を照合できることを完成条件とする。

| 検証対象 | 確認する振る舞い |
|---|---|
| ターン失敗・Goal変更・手動再開 | エラー詳細、受信状態、操作要求と結果が区別して残る。App Serverの履歴と照合できる |
| 接続・映像・入力・記録保存の異常 | 対象と取得できた原因情報が残り、既存の停止・復旧動作を妨げない |
| ログ保存失敗 | 作成・書き込み・回転の失敗で攻略を止めず、対象パスを含む通知が出る。通知が再帰しない |
| App Server出力 | JSON・非JSON・分割受信・長い改行なし出力・終了時の末尾を扱い、RPC処理を詰まらせない |
| 認証情報 | 既知の認証項目、Bearer、接続用トークンが保存や失敗通知に出ない。必要なエラー詳細は残る |
| 多重起動と整理 | 書込先が分かれ、稼働中を保護し、終了済み直近10回分を保持する。整理競合・削除失敗を許容する |
| 回転・終了 | 10 MiBと10本の設定が働き、正常終了で保存待ちを回収する。GUIと入力停止を妨げない |

実装時は関連する単体・結合テストに加え、実画面で通知の文言・対象パス・停止操作との両立を確認する。常時記録の出力量と操作への影響も測定する。

## 採用判断の根拠

Loguruは回転・保持を少ない設定で構成できるが、保存失敗のGUI通知には追加の接続処理が必要になる。`enqueue=True`もパイプ飽和時まで呼び出し元を待たせない保証ではなく、終了時には回収待ちが必要になる。今回の要件では標準loggingに小さな通知処理とJSON整形を組み合わせる方が単純と判断した。structlogは構造化処理に強いが、今回必要なファイル保存・回転機構を置き換えるものではない。

VS Codeの起動フォルダー単位の保持と、個々のログのサイズローテーションを参考にした。Codexの共通SQLite方式は、今回GIGASへ新たなDBを導入する根拠にはしない。

- [Pythonのログハンドラー](https://docs.python.org/3.13/library/logging.handlers.html)
- [python-json-logger](https://nhairs.github.io/python-json-logger/latest/)
- [Loguruのキュー・保存処理](https://github.com/Delgan/loguru/blob/0.7.3/loguru/_handler.py)
- [VS Codeの保存先生成](https://github.com/microsoft/vscode/blob/main/src/vs/platform/environment/common/environmentService.ts)
- [VS Codeの起動フォルダー整理](https://github.com/microsoft/vscode/blob/main/src/vs/code/electron-utility/sharedProcess/contrib/logsDataCleaner.ts)
- [Codex 0.167.0の診断ログ整理](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/state/src/runtime/logs_maintenance.rs)

実装内容を[データ配置・所有](../../../docs/design/data/storage.md)、[Codex通信仕様](../../../docs/design/interfaces/codex.md)、関連ガイドへ反映した。本資料は完了時点の設計・検証範囲の記録として扱う。
