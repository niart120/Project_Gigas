# ゲームI/O MCPの操作列実行と経過観測

このunitで実装した5ツールの仕様。現行の呼び出し契約は[ゲームI/O MCP API](../../../docs/design/interfaces/observation-mcp.md)、操作列の形式は[入力API](../../../docs/design/interfaces/input-api.md)を参照。

## 公開ツール

| ツール | 引数 | 応答 |
|---|---|---|
| `observe` | なし | 最新キャッシュの画面1枚と観測情報。入力中も呼べる。 |
| `act_and_observe` | `sequence`、任意の `capture_interval_ms` | 操作列の終了を待つ。間隔の省略時は従来どおり最終画像1枚。指定時は途中記録と最終画像を一括で返す。 |
| `dispatch` | `sequence` | 操作列を検証して受理し、終了を待たずに `dispatch_id` を返す。周期撮影は行わない。 |
| `poll` | `dispatch_id` | 操作列の終了を待たず、実行中なら現在の進捗と最新画面を返す。終了済みなら確定した結果と終了時に取得できた画像を返す。 |
| `cancel` | `dispatch_id` | 指定した実行を中止し、解除処理を終えてから部分結果と画面を返す。すでに終了していれば保持中の確定結果を返す。 |

### 実行の識別

`sequence` は呼び出し側が渡す操作列、`step` はその中の1要素（`press` または `wait`）を指す。`dispatch_id` は `dispatch` が受理した1回の実行を識別する。同じ列を2回実行しても、それぞれのIDで照会・中止できる。非同期ツールが `dispatch_id` として返す値には、入力受付時に発行する既存の `operation_id` を使う。同期ツールの応答と履歴では従来の項目名 `operation_id` を使う。

5ツールは接続ごとに固有のGIGAS MCPサーバーに登録する。Codexのツール設定とGIGASの履歴表示では、サーバー名とツール名の組で識別する。`cancel` の対象は指定した非同期実行1件で、Codexターンは継続する。

## 操作列のステップ実行

`act_and_observe` と `dispatch` は同じ規則で `sequence` を実行する。`press` はそのステップで指定した入力状態を `duration_ms` だけ保持する。次も `press` なら全解除を挟まず、次の入力状態へ直接切り替える。たとえば `右 → 右＋A → 右` では、右を保持したまま、中央のステップでAを押し、最後のステップに入るときにAだけを離す。

両ツールの使用方法には、長押しと押し直しの違いを次の例で明記する。

| 操作列 | 入力の変化 |
|---|---|
| `A (100 ms) → A (200 ms)` | Aを合計300 ms押し続ける。 |
| `A (100 ms) → wait (50 ms) → A (200 ms)` | Aを100 ms押し、50 ms全解除してから、Aをもう一度200 ms押す。 |

`wait` に入るときは全解除し、その状態を `duration_ms` だけ保つ。操作列の正常終了時にも全解除する。どちらも、すでに全解除済みなら解除状態の再送は不要とする。

`cancel` やターン終了などで実行を中断した場合、または入力状態の送信に失敗した場合は、押下が残っている可能性があれば全解除を試みる。たとえば `右 → 右＋A` の切り替えで送信に失敗すると、直前の右入力が残り得る。操作の中止・失敗と解除の成否は、応答と履歴に別々に残す。送信失敗後に全解除が成功した場合も、操作の結果は送信失敗として扱う。

## 受付・停止・結果の寿命

同期・非同期で入力枠は共通とする。有限・非空の列全体を送出前に検証し、実行中の列があれば別の列を `BUSY` で拒否する。実行を切り替える側はキャンセルと解除結果を確認してから次の列を送る。非同期実行は開始元のCodexターンが通常終了・中断・失敗した時点で、まだ動作中なら中止し、必要な解除を行う。

進捗には全要素数、完了要素数、実行中の要素があればその位置を含める。問い合わせ中に観測が失敗しても進捗を返す。問い合わせ時の進捗と、キャッシュされたフレームの取得時刻は個別に扱う。問い合わせの回数で終了結果に付く画像は増えない。

自然終了・中止時には入力解放後の最新キャッシュを読む。新しいフレームの到着は待たず、解除前に撮影された画像が返る場合もある。中止や入力失敗では、完了要素数、途中で止まった位置、送出・解除の結果を返す。画像取得の成否は入力の成否と区別する。

現在の接続で直近に終了した非同期実行1件の結果と観測画像をメモリに保持する。次の非同期実行が動作中の間も前回の結果を参照でき、新しい終了結果が確定したときに置き換える。同期実行はこの枠を使わない。保持中のIDへの再問い合わせや自然終了と行き違ったキャンセルには同じ確定結果を返す。参照対象外のIDは取得不能として返し、別の実行の結果を返したり入力を止めたりしない。

## 同期実行の周期撮影

`capture_interval_ms` は正の整数ミリ秒。操作開始を起点に、1周期後から操作列の予定終了時刻の手前まで撮影を予定する。予定時間を各要素の `duration_ms` の合計とすると、最終画像を含む予定枚数は「予定時間 ÷ 間隔」の切り上げになる。上限は全解像度で32枚。超過時は入力を送る前に拒否し、「予定時間 ÷ 32」の切り上げを指定可能な最短間隔として返す。たとえば20秒に500 msを指定すると40枚になるため、625 ms以上を案内する。

入力送信・解除は途中の撮影や符号化を待たない。途中記録は予定時点順とし、撮れた枠には操作列上の位置と観測情報を、間に合わない枠には未取得であることを残す。遅れた枠を後から連写しない。入力失敗時は実行終了までの部分結果と取得済み画像を返す。終了後に予定されていた枠は撮影失敗に数えない。

たとえば1,800 msの列を500 ms間隔で実行し、2回目の撮影が間に合わなかった場合、応答順は「500 msの画像、1,000 msは未取得、1,500 msの画像、解除後に読んだ最終画像」となる。2,000 msの列でも、2,000 ms地点は最終画像だけとする。

## プレイ履歴

履歴は操作列ごとに1件とし、その項目から途中記録と最終画像を順に確認できるようにする。各画像には従来の観測情報（観測ID、フレーム取得時刻、元映像と返却画像の寸法）を用いる。観測IDとPNG名は既存のUTCミリ秒時刻形式を維持し、操作ID、列内の位置、撮影予定時点との対応を操作記録側に残す。画像IDの時刻とフレーム取得時刻は別の値である。ターンの停止でツール応答を配送できない場合も、保存できた途中記録は履歴から参照できる。
