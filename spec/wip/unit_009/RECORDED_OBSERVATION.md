# U04 記録付き観測とMCP接続 親仕様

## 1. 目的・状態・起点

U03の最新フレームを一つの観測として確定・保存し、同じ画像と観測IDを`observe()`からCodexへ返す。プロジェクトと記録は、この振る舞いに必要な最小範囲を実装する。

状態: **wip（M0調査・設計とM1独立部品完了、M2着手中）**。2026-11-12の依頼で着手し、[M0子仕様](../../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md)へ契約・公開経路の根拠・未確認事項をまとめた。U04全体の製品受入、MCP実接続、実機受入は未完了である。

M0子のcompleteは調査作業の完了を指し、実装前の設計方針はレビュー・実装結果で改訂する。[M1子仕様](../../complete/unit_032/RECORDED_OBSERVATION_IMPLEMENTATION.md)で独立した観測・保存APIを実装・検証した。[M2子仕様](../unit_035/MCP_OBSERVATION_INTEGRATION.md)を作成し着手した。同日の再レビューで、画像監査・重複メタデータ・保存工程別の取消しを簡素化した。

起点は2026-11-11の[工程計画](../../initial/05-implementation.md)、2026-11-12のM0限定依頼と、その後のM1実装・検証依頼。同日の追加指摘に従い、要求受付後の新フレーム待ちを取りやめ、最新画像キャッシュをそのまま採用する方式へ変更した。

利用場面は、保存先を作成・選択し、Codexが現在の最新画像を観測し、後から観測IDで同じ保存画像を参照すること。

## 2. 前提と着手条件

[U03](../../complete/unit_008/VIDEO_CAPTURE.md)の実寸法・不変BGR Frame、世代・連番・時計・停止状態を使う。観測側には`CaptureService.reader()`で得る専用readerを渡し、デバイスの接続・終了は既存所有者へ残す。プレビュー画像を逆取得したり、MCP要求ごとに取得元を開いたりしない。

Codex結合には[U02](../../complete/unit_007/CODEX_CONNECTION.md)の接続とサービス用asyncioループを使う。観測・保存部品はCodex接続から独立して設計・検証できる。MCP公開は採用runtime 0.167.0の`thread/start.config`を使う方針で、同梱版schemaと公開tagの設定型を確認した。組合せの実接続はM2で確認する。

[U02レビュー](../../dev-journal.md)のR02（受理前中断で原稿消失）・R04（failed終端後の明示的次送信が拒否される）は、M0で現在のコードと試験を読み、未修正と確認した。M2-03で再現し、接続・会話UIの拡張前に独立した修正を行った。模擬RPC・実Qtによる回帰確認済みで、実Codexの受入はM2に残す。詳細は[M2子仕様](../unit_035/MCP_OBSERVATION_INTEGRATION.md)を参照する。

UIは[実装整理](../../complete/unit_027/IMPLEMENTATION_SIMPLIFICATION.md)と[主画面方針](../../initial/10-ui-interaction.md)に従い、新設する「プロジェクト」メニューの「新規作成」「開く」と既存の接続・エラー詳細だけを使う。全体対話UIはU06。U06の完成を本工程の前提にしない。

## 3. 対象範囲・対象外

対象は、有効な最新Frameの採用、観測用縮小・PNG符号化、観測ID、最小プロジェクトの作成・読込、画像・JSONL保存、組込みStreamable HTTP、`observe`公開とCodex画像受信である。

対象外は、要求後新フレーム待ち、切り抜き・拡大・汎用編集API、呼出しごとの加工指定、元解像度画像の別保存、常時録画、観測専用UI、全体対話UI、プロジェクトエクスプローラー、入力、Goal、再開、記憶整理、全イベントの先行実装、独立サーバー入口である。

## 5. M0の決定とM1レビューでの見直し

| 対象 | 決定・理由・影響 |
|---|---|
| 観測元 | `observe()`受付時の一度のsnapshotがstreamingでFrameありなら採用する。最新キャッシュでよく、要求前の取得も同じFrameの再観測も許容する。要求後待機・専用期限・年齢監視を追加しない。取得停止時の失効はU03を使う |
| 加工 | 最新Frameから共通設定オリジナル/FullHD（既定）/HDに従い、必要な場合だけ比率維持で縮小し、一度PNG符号化する。小画像は拡大しない。取得・プレビューとは独立し、observeは引数なし。詳細はunit_034。PNG上限32 MiB、保存によるBUSYは禁止 |
| 対応関係 | Observationは加工済みPNG・出力寸法・形式・IDと元FrameのUTC・世代・連番・寸法を持ち、Frame本体を保持しない。同じPNGを保存とMCPへ渡す。未完成ユニットとして保存形式を直接変更し、旧形式識別・移行・互換対応を設けない |
| 保存 | アプリが一つのwriterへ非同期保存する。保存完了・滞留・失敗で次の観測を妨げない。保存見送り・キュー・保持上限は先行設計しない。直列／並列は実装上の選択とし、共有JSONLの整合性を守る。保存失敗は観測成功と分け、通常終了で進行中保存を回収する |
| 案内・UI | 保存先は「プロジェクト」→「新規作成」「開く」、縮小は既存設定の「観測解像度」。既存の通知・詳細・指示経路を使う。全体対話UIはU06 |
| MCP | 接続ごとのloopbackサーバとBearerを一つ持つ。既存サービス用ループと取得readerを使い、アプリが記録先を所有する。MCP公開部はObservationの包装のみ。SDK 2.3.0の製品実接続は未確認 |
| 通知容量 | 採用runtimeのMCP通知結果上限1 MiBは原画像保存の経路に使わない。外側JSONを含む受信2 MiBの有界変更と実通知確認はM2で行う |
| U05への条件 | 旧認証値の失効、新認証値の公開、旧要求の収束を入力公開前に確認する。事後Frameの待機はU05で設計する |

[M1レビュー](../../complete/unit_033/OBSERVATION_STORAGE_REVIEW.md)では、符号化を観測サービス、符号化済み画像の保存をwriterへ分け、未使用のanalysis予約欄を保存・予定するMCP応答から除いた。旧analysisを扱った実績はM1の履歴であり、M2で開発途中データの互換性を維持する要件にはしない。Codex解釈・対話履歴は受信後に別記録へ残し、原観測を更新しない。その記録APIはU06で具体化する。

画像の同一性はGigasの保存・MCP応答bytesの契約であり、Codex内部の画像前処理まで同じbytesと保証しない。撮像時刻・カード内部遅延はホスト時計だけでは分からない。

前回選択したパス一件を既存設定へ保存し、起動時に検査・専有して復元する。復元失敗は既存の通知・詳細に残して未選択で起動し、会話・Goalは自動再開しない。未選択でもアプリ管理の永続記録先をチャットに用意し、会話からobserveを使える。通常会話はephemeralをやめて保持する方針。詳細は[チャット・永続化の改訂](../../complete/unit_034/CHAT_OBSERVATION_PERSISTENCE.md)に従う。2項目の取消し・失敗・接続中の扱いは[M0の選択契約](../../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md#プロジェクト選択と未選択時の契約)に定める。利用者確認と仕様コミットを終え、M2へ着手した。

## 7. 工程全体の受入観点・TDD Test List

| 観点 | 工程全体で確認する振る舞い |
|---|---|
| 最新観測 | snapshot採用時に停止・エラーなら拒否し、古い保持Frameで代替しない。同じFrameでも観測IDを区別し、元時刻を保持する。採用後の取得停止で確定画像を無効化しない |
| 画像と記録 | 保存とMCPのbytes・観測ID・取得時刻が対応し、再読込で画像をたどれる。取得成功と保存成功を区別し、保存失敗を確認できる。応答直後の参照・異常終了時の欠損を保証外として明記する。T05・T09・T19の観測部分 |
| 既存データ | 未知版・不正な記録行を識別して保持し、追記しない。対応版で共通項目が正常な未知イベントは保持できる。過去画像の欠損だけで新規記録を止めない。単一writerの所有が実プロセス間でも成立する |
| 画像配送 | 固定画像を実runtimeが受信し、次に実映像で同一性を確認する。パス返却やFakePeerだけでは合格にしない |
| 応答性と寿命 | 保存・MCP中もプレビューと切断が進む。完全出力の引渡し後は配送取消しでも保存を回収する。保存中も次の観測を返せる。保存滞留は観測のBUSY理由にしない。工程別の取消し状態を作らず、旧tokenを再利用しない |
| 最小結合 | メニューバーに「プロジェクト」を新設して「新規作成」「開く」を配置し、既存のエラー詳細・指示経路を使う。指示資材を変える場合だけT20の配布確認を行う |

既存試験の書換え・統合を先に判断する。要求後待機・汎用加工APIの不在、固定ラベルや文書状態語だけを検査する新規試験は作らない。詳細TDDは着手する実装子仕様が所有する。
