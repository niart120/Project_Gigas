# U04 記録付き観測とMCP接続 親仕様

## 1. 目的・状態・起点

U03の最新フレームを一つの観測として確定・保存し、同じ画像と観測IDを`observe()`からCodexへ返す。プロジェクトと記録は、この振る舞いに必要な最小範囲を実装する。

状態: **wip（M0調査・設計完了、M1/M2未着手）**。2026-11-12の依頼で着手し、[M0子仕様](../../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md)へ契約・公開経路の根拠・未確認事項をまとめた。これは製品実装、MCP実接続、実機受入の完了ではない。

M0子のcompleteは調査作業の完了を指し、実装前の設計方針はレビュー・実装結果で改訂する。次はM1着手時に実装用子仕様を作り、M1の結果を踏まえてM2着手時にその子仕様を作る。同日の再レビューで、画像監査・重複メタデータ・保存工程別の取消しを簡素化した。

起点は2026-11-11の[工程計画](../../initial/05-implementation.md)と、2026-11-12のM0限定依頼。同日の追加指摘に従い、要求受付後の新フレーム待ちを取りやめ、最新画像キャッシュをそのまま採用する方式へ変更した。

利用場面は、保存先を作成・選択し、Codexが現在の最新画像を観測し、後から観測IDで同じ保存画像を参照すること。

## 2. 前提と着手条件

[U03](../../complete/unit_008/VIDEO_CAPTURE.md)の実寸法・不変BGR Frame、世代・連番・時計・停止状態を使う。観測側には`CaptureService.reader()`で得る専用readerを渡し、デバイスの接続・終了は既存所有者へ残す。プレビュー画像を逆取得したり、MCP要求ごとに取得元を開いたりしない。

Codex結合には[U02](../../complete/unit_007/CODEX_CONNECTION.md)の接続とサービス用asyncioループを使う。観測・保存部品はCodex接続から独立して設計・検証できる。MCP公開は採用runtime 0.167.0の`thread/start.config`を使う方針で、同梱版schemaと公開tagの設定型を確認した。組合せの実接続はM2で確認する。

[U02レビュー](../../dev-journal.md)のR02（受理前中断で原稿消失）・R04（failed終端後の明示的次送信が拒否される）は、M0で現在のコードと試験を読み、未修正と確認した。接続・会話画面を拡張する前に独立した修正単位で扱い、Codex結合の受入までに回帰確認を完了する。M0とM1の独立した観測・保存部品はこの修正を待たない。今回、新しい模擬再現や修正は行っていない。

UIは[実装整理](../../complete/unit_027/IMPLEMENTATION_SIMPLIFICATION.md)と[主画面方針](../../initial/10-ui-interaction.md)に従い、保存先の新規作成・選択と既存の接続・エラー詳細だけを使う。全体対話UIはU06。U06の完成を本工程の前提にしない。

## 3. 対象範囲・対象外

対象は、有効な最新Frameの確定、原寸PNG、観測ID、最小プロジェクトの作成・読込、画像・JSONL保存、組込みStreamable HTTP、`observe`公開とCodex画像受信である。

対象外は、要求後新フレーム待ち、画像の切り抜き・縮小等の編集APIと共通設定、常時録画、観測専用UI、全体対話UI、プロジェクトエクスプローラー、入力、Goal、再開、記憶整理、全イベントの先行実装、独立サーバー入口である。

## 5. M0の決定と要否の見直し

| 対象 | 決定・理由・影響 |
|---|---|
| 観測元 | `observe()`受付時の一度のsnapshotがstreamingでFrameありなら採用する。最新キャッシュでよく、要求前の取得も同じFrameの再観測も許容する。要求後待機・専用期限・年齢監視を追加しない。取得停止時の失効はU03を使う |
| 加工 | 原寸PNG一回の符号化とidentityだけ。全画面・文字を保ち、同じbytesを保存と応答へ使う。呼出引数や共通画像設定、汎用変換は必要性が確認できず見送り。PNG上限32 MiB、同時1件、占有中はBUSY |
| 対応関係 | 永続UUID観測ID、画像相対パス、元取得UTC、元Frameの世代・連番・寸法を記録する。原寸PNG・変換なしをschema 1の契約とし、取得サービスUUID・単調時計・hash・重複する出力寸法や変換オブジェクトを必須にしない |
| 保存 | 最小project.json、events.jsonl、observations。画像公開→一行追記・flush/fsync→成功応答。一つのwriterとOSロック。読込時の全画像検査はしない。画像だけの失敗でwriterを閉じず、JSONL追記結果が不明になった場合だけ再読込まで追記を止める |
| 案内・UI | 保存場所は既存developerInstructionsで案内し、guide.mdや空のmemoryはU06へ送る。UIは保存先操作に限定。接続中の保存先差替えや専用再接続を作らない |
| MCP | 接続ごとのloopbackサーバとBearer値を一つずつ持ち、reader/writerを固定参照する。既存サービス用ループで所有し、切断で受付を閉じる。世代履歴表・権限管理サービスは作らない。公式SDK 2.3.0をM2の固定候補とし、実接続は未実施 |
| 通知容量 | 採用runtimeのMCP通知結果上限1 MiBに外側JSONが加わるため、現transportの受信1 MiBは不足し得る。M2で受信2 MiBの有界変更と実通知確認を行う。本observeの通常通知には48 MiBへの拡張は不要 |
| U05への条件 | 旧認証値を新世代へ付け替えず拒否する。新認証値の再公開、旧呼出し収束、操作直前の照合を入力公開前に実接続確認する。操作後Frameの待機はU05で設計し、U04のsnapshotに事後条件を仮定しない |

画像の同一性はGigasの保存・MCP応答bytesの契約であり、Codex内部の画像前処理まで同じbytesと保証しない。撮像時刻・カード内部遅延はホスト時計だけでは分からない。

## 7. 工程全体の受入観点・TDD Test List

| 観点 | 工程全体で確認する振る舞い |
|---|---|
| 最新観測 | snapshot採用時に停止・エラーなら拒否し、古い保持Frameで代替しない。同じFrameでも観測IDを区別し、元時刻を保持する。採用後の取得停止で確定画像を無効化しない |
| 画像と記録 | 保存とMCPのbytes・観測ID・取得時刻が対応し、再読込で画像をたどれる。部分失敗を正常応答にしない。T05・T09・T19の観測部分 |
| 既存データ | 未知版・不正な記録行を識別して保持し、追記しない。対応版で共通項目が正常な未知イベントは保持できる。過去画像の欠損だけで新規記録を止めない。単一writerの所有が実プロセス間でも成立する |
| 画像配送 | 固定画像を実runtimeが受信し、次に実映像で同一性を確認する。パス返却やFakePeerだけでは合格にしない |
| 応答性と寿命 | 保存・MCP中もプレビューと切断が進む。開始済みの保存は一件の処理として回収し、取消し後の応答だけを抑止する。工程別の取消し状態を作らず、旧tokenを再利用しない |
| 最小結合 | 既存UIの保存先操作・エラー詳細、既存指示経路を使う。指示資材を変える場合だけT20の配布確認を行う |

既存試験の書換え・統合を先に判断する。要求後待機・加工APIの不在、固定ラベルや文書状態語だけを検査する新規試験は作らない。詳細TDDは着手する実装子仕様が所有する。
