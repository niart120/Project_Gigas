# U06 Goalによる継続と途中介入 親仕様

## 1. 目的・状態・起点

通常ターンで成立した観測・入力をGoalによる継続攻略へ接続し、依頼・記憶・追加指示・公開状態を対応付ける。攻略判断や継続の再投入をアプリ側へ増設しない。

状態: **planned（未着手）**。本書は2026-11-11の工程計画であり、この工程の方式調査・詳細設計・製品実装・実接続検証を完了した記録ではない。初期設計の既存調査は着手時の材料とし、採用版の動作確認と区別する。

| 起点 | 内容 | 参照 |
|---|---|---|
| 要求 | 2026-11-11の工程再編方針。U01の成果と未実装機能を分け、調査・設計から各工程を始める | [実装計画](../../initial/05-implementation.md) |
| 規約 | plannedから着手する仕様を選び、製品実装と接続検証を区別する | [AGENTS.md](../../../AGENTS.md)・[配置と運用](../../initial/06-repository.md) |

利用場面: 利用者がプロジェクトと依頼を選び、複数ターンの攻略を明示的に開始する。計画を確認し、追加指示や質問への回答を送り、必要なら停止する。依頼完了はターン終了と区別される。

## 2. 前提と着手条件

[U02](../unit_007/CODEX_CONNECTION.md)の接続・要求応答と、[U05](../unit_010/INPUT_AND_STOP.md)の記録付きゲーム操作・即時停止が前提。Goal操作と複数ターン通知の公開経路が採用版で成立することを、本工程の実行管理を組む前に確認する。

親仕様は工程の受入条件を所有する。着手時に本ディレクトリを`spec/wip`へ移し、最初の子仕様を具体化する。子の番号を先行予約せず、作業仕様を複製しない。必要な公開経路・機器条件が成立しなければ、その条件へ依存する実装は進めず設計判断を更新する。

## 3. 対象範囲・対象外

対象: Goalの開始・継続・休止・完了、依頼・実行・スレッドの対応、公開計画・状態、追加指示の配送、質問・承認待ち、利用制限、案内と記憶入口、共通指示、必要な保存項目・イベント、認証方式の残作業を扱う。

対象外: 計画的終了、停止後の攻略再開、別スレッドの記憶整理・復元は後続工程。アプリ独自の攻略計画、毎ターンの再投入、無通知からの停滞診断、自動修復・自動課金切替は行わない。

## 6. 子工程の分割と順序

| 子工程候補 | 開始条件 | 到達点 |

## 7. 振る舞い仕様・TDD Test Listの受入観点

| 観点 | 工程全体で確認する振る舞い | 主な検証 |
|---|---|---|
| 継続と達成 | ターン終了で依頼を完了にせず、Goalによる次ターンの通知を受ける。アプリが独自に続行指示を繰り返さない | T06・T16 |
| 追加指示 | 受付・配送・受付不明を区別し、Goal完了時の未配送分と完了後の指示を破棄・記録・表示する。新Goal化・再送しない | T07・T09 |
| 回答待ちと停止 | 有効な要求へ回答し、待機中は新規入力を保留する。停止後の遅い回答や通知で再開しない | T07・T15 |
| 状態と制限 | 最後の公開計画・状態と更新時刻を表示する。無通知を異常と推定せず、明示的な最終失敗・制限では停止する | T08・T10・T16・T17 |
| プロジェクトと認証 | 既存記憶を初期化せず案内・現状メモを渡し、依頼・実行・観測を追跡できる。両認証方式の確認範囲を記録する | T09・T19該当範囲・T20 |

親では受入観点のみを定める。詳細なTDD Test List、red/greenの履歴、具体的なAPIと故障注入点は、着手する子仕様へ記載する。文書の見出し・状態語・チェック欄の一致を製品テストにはしない。

## 8. 対象ファイル候補

`src/gigas/runtime/codex/`・`app/`・`ui/`・`storage/`・`prompts/`、対応する試験、認証・モデル・利用手順のdocs、必要な依存定義・lock。03の入力意味を変更する場合は関連契約と呼出し元を同じ子仕様で扱う。

公開APIの変更時はdocstringと利用者向けdocsを更新し、型境界・docstringの対応skillを使う。GUIには必要なラベル・状態・エラーとCodex/ユーザー由来の文章を表示し、アプリ独自の説明本文はdocsへ置く。
