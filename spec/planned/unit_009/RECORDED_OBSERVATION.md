# U04 記録付き観測とMCP接続 親仕様

## 1. 目的・状態・起点

取得したフレームを一つの観測として確定・保存し、同じ画像と識別子をobserveからCodexへ返す。プロジェクトと記録はこの振る舞いに必要な最小範囲から実装する。

状態: **planned（未着手）**。本書は2026-11-11の工程計画であり、この工程の方式調査・詳細設計・製品実装・実接続検証を完了した記録ではない。初期設計の既存調査は着手時の材料とし、採用版の動作確認と区別する。

| 起点 | 内容 | 参照 |
|---|---|---|
| 要求 | 2026-11-11の工程再編方針。U01の成果と未実装機能を分け、調査・設計から各工程を始める | [実装計画](../../initial/05-implementation.md) |
| 規約 | plannedから着手する仕様を選び、製品実装と接続検証を区別する | [AGENTS.md](../../../AGENTS.md)・[配置と運用](../../initial/06-repository.md) |

利用場面: 利用者が保存先を作成または開き、Codexが現在画面を観測する。記録を後から開くと、返した観測IDから同じ画像へたどれる。

## 2. 前提と着手条件

接続・会話画面を拡張する前に、[U02完了後レビュー](../../dev-journal.md)のR02（受理前の中断で未送信原稿が消える）とR04（ターン失敗後の明示的な次送信にも再接続が必要）を独立した修正単位で扱う。M0で修正状態を確認し、Codex結合の受入までに回帰確認を完了する。観測保存などの独立部分はこの修正を待たない。

[U03](../../complete/unit_008/VIDEO_CAPTURE.md)の取得元・連番・時計・停止状態が前提。Codexへの結合とサービス用ループの利用には[U02](../../complete/unit_007/CODEX_CONNECTION.md)を必要とする。保存・観測部品の設計と機器非依存試験はCodex接続から分離できる。

U03の[取得API](../../../docs/video-api.md)は変更不能なBGR画像とサービス寿命内の接続世代・連番・UTC・単調時計を提供する。U04で要求受付後の新フレーム待ち、観測画像の確定・保存・永続IDを実装する。U03の最新画像キャッシュをそのまま要求後の観測と扱わず、キャプチャー内部の遅延はホスト時刻だけでは除去できない制約も引き継ぐ。

観測側には`CaptureService.reader()`で得る専用の`CaptureReader`を渡す。デバイスの接続・終了は一つの所有者へ残し、プレビューの画像を取り出して消費したり、MCP要求ごとに別の取得元を開いたりしない。snapshotの受渡し後は取得ロックを保持せず、観測の変換・保存・送信はGUIスレッド外で行う。U03の複数reader試験を出発点とし、実MCPと画像処理負荷の下でもプレビューと切断操作が進むことをU04の結合で確認する。

2026-11-11の追加設計レビューで、取得・プレビュー・観測の画像加工を分離する方針とした。[設定・映像取得の再設計案](../unit_026/SETTINGS_AND_STATUS_REDESIGN.md)では、レターボックスはプレビュー専用、取得解像度は機器への要求とする。U04には観測画像のリサイズ・切り抜き等をカスタムできる仕組みの設計を引き継ぐ。表示設定を変えても観測画像へ黒帯や引き延ばしを持ち込まず、観測の加工要求で取得設定を変更・再接続しない。確定した一つの派生画像を保存とMCP応答に使い、元Frameの世代・連番・取得時刻と変換内容を関連付ける。この追記は製品実装やMCP接続の完了を意味しない。

親仕様は工程の受入条件を所有する。着手時に本ディレクトリを`spec/wip`へ移し、最初の子仕様を具体化する。子の番号を先行予約せず、作業仕様を複製しない。必要な公開経路・機器条件が成立しなければ、その条件へ依存する実装は進めず設計判断を更新する。

## 3. 対象範囲・対象外

対象: 要求後の新しいフレーム待ち、観測画像の確定、最小のプロジェクト管理情報と作成・読込、案内、観測ID・画像・JSONLの保存、Streamable HTTPの組込み、observeの公開、Codexへの画像接続を扱う。

対象外: act_and_observe、実機入力、Goal継続、全イベントの先行実装、再開フロー、記憶の意味的な整理・退避・復元、プロジェクトエクスプローラー、常時録画は作らない。

## 5. 冒頭の調査・設計

| 対象 | 調べる・決めること | 成果と進行条件 |
|---|---|---|
| 観測の確定 | 要求受付と新フレームの境界、待機期限、画像変換・符号化、観測情報を設計する | プレビュー画像をそのまま新観測とみなさず、保存・応答で一つの確定画像を使う契約を決める |
| 観測画像のカスタム | 縮小・切り抜き・比率処理の対応範囲、既定値、呼出引数と共通設定の分担、出力寸法・容量・同時処理数の上限を決める | 切り抜きの座標系と処理順、画像外指定・無効寸法の拒否、元画像への座標対応を定める。共有Frameを変更せず、保存画像と応答画像を一致させる |
| プロジェクトと記録 | 04の形式を起点に最小管理項目、ID生成、作成・読込、追記順、単一の書込口、画像とイベントの部分失敗を設計する | 既存記憶や原記録を無断で初期化しない。破損行を識別・保持し、正常に読める範囲と追記可否を明示する。全将来イベントをここで確定しない |
| MCPの方式 | 採用SDK・依存、localhostへの束縛、サーバと接続の寿命、認証情報、タイムアウト、画像とメタデータの配置を確認する | 公開するobserveの要求・結果・エラーが03と一致する。MCP型をゲームI/Oへ流さず、画像を実ランタイムが受け取る試験を定める |
| 接続世代の準備 | app-serverからのMCP設定・更新または接続再作成を調べる | U05で旧呼び出しを失効できる方式と未確認条件を残す。未成立なら入力の公開へ進めない |

## 6. 子工程の分割と順序

| 子工程候補 | 開始条件 | 到達点 |
|---|---|---|
| M0 観測・保存・MCP設計 | U03のフレーム契約。MCP側はU02の接続方式 | 観測、部分失敗、最小データ、サーバ所有と接続の判断を記録する |
| M1 記録付き観測 | M0の観測と保存判断 | プロジェクト作成・読込、画像・イベント保存、期限・破損・保存失敗を確認する |
| M2 observeと実接続 | M1とU02 | 同じ画像・IDをMCP経由でCodexが受け取ること、終了時の接続解放を確認する |

これは分割方針であり、子仕様・API・全テストの先行作成ではない。調査で変更理由が生じたら本書と影響する初期設計を更新する。

## 7. 振る舞い仕様・TDD Test Listの受入観点

| 観点 | 工程全体で確認する振る舞い | 主な検証 |
|---|---|---|
| 新しい観測 | 受付後のフレームを期限内に確定し、取得停止時に古い画像を新観測として返さない | T04・T05、単体・結合・実機 |
| 画像と記録 | 返した画像・観測ID・時刻が保存物と一致し、再読込でたどれる。保存失敗を正常応答へ変換しない | T09・T19の観測部分 |
| 観測専用の加工 | 加工条件が違う観測でも元Frameとプレビューを変えず、画像・記録・変換情報が一つの観測へ対応する。不正な寸法・領域・過大負荷を期限と上限で扱う | 単体・結合・MCP実接続 |
| 既存データ | 既存プロジェクト・記憶を保持して開き、不正な管理情報や破損行を無言で上書き・切捨てしない | 単体・ファイル結合 |
| 画像配送 | 固定画像の接続試験と実映像の接続確認で、モデルが画像を受け取る。パス返却だけで合格にしない | T05、実ランタイム |
| 共有と応答性 | 観測の変換・保存・MCP配送が進行中も、一つの取得元からプレビューが更新され、切断を受け付ける | 単体・結合・実機 |
| 組込みと案内 | サーバを所有して起動・終了し、保存先と案内を実データへ対応付ける。同梱案内も配布物から利用できる | 結合・T20 |

親では受入観点のみを定める。詳細なTDD Test List、red/greenの履歴、具体的なAPIと故障注入点は、着手する子仕様へ記載する。文書の見出し・状態語・チェック欄の一致を製品テストにはしない。
