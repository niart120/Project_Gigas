# U07 計画的なプレイ終了 親仕様

## 1. 目的・状態・起点

元の攻略Goalを休止・保持し、同じスレッドの通常ターンでプレイ終了処理を行って停止する。攻略達成、終了処理の結果、機器解除を別々に扱う。

状態: **planned（未着手）**。本書は2026-11-11の工程計画であり、この工程の方式調査・詳細設計・製品実装・実接続検証を完了した記録ではない。初期設計の既存調査は着手時の材料とし、採用版の動作確認と区別する。

| 起点 | 内容 | 参照 |
|---|---|---|
| 要求 | 2026-11-11の工程再編方針。U01の成果と未実装機能を分け、調査・設計から各工程を始める | [実装計画](../../initial/05-implementation.md) |
| 規約 | plannedから着手する仕様を選び、製品実装と接続検証を区別する | [AGENTS.md](../../../AGENTS.md)・[配置と運用](../../initial/06-repository.md) |

利用場面: 利用者が攻略途中で計画的終了を選ぶ。Codexが現在画面を確認して必要な区切りや現状メモの更新を行い、アプリは終了結果と停止状況を示す。切替中でも即時停止を受け付ける。

## 2. 前提と着手条件

[U06](../unit_011/GOAL_EXECUTION.md)のGoal管理・介入・記録と、U05の即時停止が前提。U02の公開経路調査を引き継ぐが、Goal休止から通常ターンへ切り替えられることは本工程の冒頭で採用版によって確認する。

親仕様は工程の受入条件を所有する。着手時に本ディレクトリを`spec/wip`へ移し、最初の子仕様を具体化する。子の番号を先行予約せず、作業仕様を複製しない。必要な公開経路・機器条件が成立しなければ、その条件へ依存する実装は進めず設計判断を更新する。

## 3. 対象範囲・対象外

対象: 計画的終了の受付、Goal休止、旧ターン・入力・書込・SDK監視の収束、終了処理用権限への切替、通常ターンの開始、終了結果・未完理由、途中の質問・承認・制限・即時停止、アプリ終了への接続を扱う。

対象外: 元Goalの目的置換、終了用Goalの新設、ゲーム内セーブの全ゲーム共通保証、終了失敗後の自動攻略再開、記憶整理の自動起動、後日の再開実装は行わない。

## 5. 冒頭の調査・設計

| 対象 | 調べる・決めること | 成果と進行条件 |
|---|---|---|
| 公開経路と収束 | Goal休止、旧要求の失効、旧ターンとファイル書込終了の確認、同じスレッドの通常ターン開始を採用版で調べる | pause受付だけで旧処理終了としない。必要な収束を確認できない場合、終了処理ターンを開始しない設計にする |
| 移行と権限 | 利用者の終了意図、移行中に許可する入力、旧権限失効、終了処理用世代、即時停止を設計する | 遅い通知や元Goalの達成が競合しても、旧処理と新処理を重ねない。自分が発行したpauseと外乱のpauseを区別する |
| 結果・待機・UI | 通常ターンの結果形式、未完理由、待機打切り条件、処理中の回答・承認、アプリ閉鎖を設計する | 構造化結果等の候補は公開経路で確認する。自然文の『完了』だけで成功にせず、未確認を示して入力を閉じる |

| 子工程候補 | 開始条件 | 到達点 |

これは分割方針であり、子仕様・API・全テストの先行作成ではない。調査で変更理由が生じたら本書と影響する初期設計を更新する。

## 7. 振る舞い仕様・TDD Test Listの受入観点

| 観点 | 工程全体で確認する振る舞い | 主な検証 |
|---|---|---|
| Goalの保持 | 元の目的と必要な参照を保持して休止し、終了処理成功を攻略依頼の達成として記録しない | T13の終了側 |
| 順序と排他 | 旧ターン・入力・書込・監視の収束確認後に権限を切り替え、通常ターンを開始する | T13・T14 |
| 失敗と即時停止 | 切替失敗や中断では入力を閉じ、元の攻略へ戻らない。解除・収束未確認を停止完了と表示しない | T14・T15・T17 |
| 回答と結果 | 終了処理中の質問へ回答しても同じフェーズを続行し、対応する結果・未完理由を保存する | T07該当範囲・T09・T14 |

親では受入観点のみを定める。詳細なTDD Test List、red/greenの履歴、具体的なAPIと故障注入点は、着手する子仕様へ記載する。文書の見出し・状態語・チェック欄の一致を製品テストにはしない。

## 8. 対象ファイル候補

`src/gigas/app/`・`runtime/codex/`・`ui/`・必要な`storage/`・`prompts/`、対応する試験と終了手順のdocs。SDKの具体メソッドや結果型はM0で確認してから決める。

公開APIの変更時はdocstringと利用者向けdocsを更新し、型境界・docstringの対応skillを使う。GUIには必要なラベル・状態・エラーとCodex/ユーザー由来の文章を表示し、アプリ独自の説明本文はdocsへ置く。

## 9. 検証計画と未実行事項

固定通知でpause・完了・中断の競合を確認し、採用ランタイムでGoal保持と同一スレッドの通常ターン移行を確認する。実機では入力世代切替と途中の即時停止を確認する。終了指示資材を追加・変更する場合はT20も実施する。

| 確認 | 現在の結果 | 実施時の扱い |
|---|---|---|
| 方式調査・設計判断 | not run | 本工程未着手。採用版・機器・根拠と未確認事項を子仕様へ記録する |
| 製品の単体・結合試験 | not run | 実装時に対象のpytest、ruff、tyをAGENTS.mdに従って実行し、検査する契約を記録する |
| Goal休止・通常ターン切替・実機停止 | not run | 採用ランタイムで元Goal保持、旧処理収束、同一スレッドへの通常ターン移行を確認する。実機の権限切替と途中のGUI即時停止も対象にする |
| 依存・公開API・配布 | not run | 変更する子仕様でuv lock --check・uv buildを含める。指示資材変更はT20も確認する |

親仕様の文書検査は工程計画の整合確認であり、上記の製品検証を実行済みにしない。工程完了には本書の必要な実接続・実機確認の根拠が必要で、模擬試験の成功だけで置き換えない。
