# U07 計画的なプレイ終了 親仕様

## 1. 目的・状態・起点

ユーザーの追加指示を受けたエージェントが区切り・必要なセーブ・現状メモ更新を行って終了する経路を確認する。元の攻略Goalは休止・保持する方針とし、攻略達成、終了作業の結果、機器解除を別々に扱う。共通の追加指示・公開通知・停止経路を使う。終了専用ターン・権限・アプリ状態は採用しない。

状態: **planned（未着手）**。本書は2026-11-12の仕様レビューを反映した工程計画であり、この工程の方式調査・詳細設計・製品実装・実接続検証を完了した記録ではない。初期設計の既存調査は着手時の材料とし、採用版の動作確認と区別する。

| 起点 | 内容 | 参照 |
|---|---|---|
| 要求 | 2026-11-11の工程再編方針。U01の成果と未実装機能を分け、調査・設計から各工程を始める | [実装計画](../../initial/05-implementation.md) |
| 規約 | plannedから着手する仕様を選び、製品実装と接続検証を区別する | [AGENTS.md](../../../AGENTS.md)・[配置と運用](../../initial/06-repository.md) |

利用場面: 利用者が攻略途中でMessageから「区切りまで進めて保存して終える」等を送る。Codexが指示を解釈して必要な作業を行い、アプリは確認できた結果と停止状況を記録する。作業中でもpause／stopアイコンによる推論中断・入力遮断を受け付ける。第三の停止ボタンやアプリ側の自然文分類は設けない。

## 2. 前提と着手条件

[主画面とメッセージ操作](../../initial/10-ui-interaction.md)で合意した左右配置、共通Message、Goalトグル、Plan／History、reasoning／activityと、[U06 M0](../../wip/unit_011/GOAL_EXECUTION.md)のAPI・操作契約を引き継ぐ。主画面の一時停止はGoal保持、停止はGoal破棄であり、本工程の計画的終了とは別操作。計画的終了をどちらかのボタンの副作用にしない。M0で終了への入口、終了作業中・停止後の表示、共通入力・質問・承認と両アイコンの効果を具体化する。今回の親仕様更新は本工程M0への着手・接続検証ではない。

[U06](../../wip/unit_011/GOAL_EXECUTION.md)のGoal管理・介入・記録と、U05の即時停止が前提。追加指示による終了作業・Goal休止・結果通知の成立を確認する。未成立なら制約と必要な設計差分を記録する。旧専用ターン案を既定の代替へ戻さず、方式判断を更新してから依存する作業へ進む。

親仕様は工程の受入条件を所有する。着手時に本ディレクトリを`spec/wip`へ移し、最初の子仕様を具体化する。子の番号を先行予約せず、作業仕様を複製しない。必要な公開経路・機器条件が成立しなければ、その条件へ依存する実装は進めず設計判断を更新する。

## 3. 対象範囲・対象外

対象: 終了を求める追加指示の配送、Goal休止と結果の通知、入力・書込の収束、要求の寿命、終了結果・未完理由、途中の質問・承認・制限・pause／stopの割込み、アプリ閉鎖との分離を扱う。必要な指示資材・記録の不足だけを補い、成立済みの共通経路を再実装しない。

対象外: 終了専用ターン・権限・アプリ状態、自然文のアプリ側分類、元Goalの目的置換、終了用Goalの新設、ゲーム内セーブの全ゲーム共通保証、終了失敗後の自動攻略再開、記憶整理の自動起動、後日の再開実装は行わない。

既存経路で受入条件を満たせる場合は、結合検証と利用手順・検証記録で完了できる。新しい制御コードや追加の子工程を作ること自体を完了条件にしない。

これは分割方針であり、子仕様・API・全テストの先行作成ではない。調査で変更理由が生じたら本書と影響する初期設計を更新する。

## 7. 振る舞い仕様・TDD Test Listの受入観点

| 観点 | 工程全体で確認する振る舞い | 主な検証 |
|---|---|---|
| Goalの保持 | 元の目的と必要な参照を保持して休止し、終了処理成功を攻略依頼の達成として記録しない | T13の終了側 |
| 順序と排他 | 共通停止経路で推論・入力・書込の収束と停止意図を守る。Goal休止の受付を入力解除・ターン終了と同一視しない | T13・T14 |
| 失敗と即時停止 | 配送失敗・受付不明は共通配送の結果として残し、終了成功にしない。明示的な実行失敗・中断では共通停止を使い、既に休止・停止したGoalを自動再開しない。解除・収束未確認を停止完了と表示しない | T07・T14・T15・T17 |
| 回答と結果 | 終了作業中の質問へ回答しても指示された作業を続行し、対応する結果・未完理由を保存する | T07該当範囲・T09・T14 |
| 共通画面と停止意図 | Goalを保持する計画的終了と利用者のGoal破棄を区別する。作業中も入力遮断を優先し、破棄した目的や中断した終了処理を遅い回答で自動再開しない。共通入力と閲覧位置を維持する | M0操作レビュー、T14・T15、GUI・実ランタイム |

親では受入観点のみを定める。詳細なTDD Test List、red/greenの履歴、具体的なAPIと故障注入点は、着手する子仕様へ記載する。文書の見出し・状態語・チェック欄の一致を製品テストにはしない。

U06の共通入力・停止試験を再利用し、本工程固有の終了結果・競合に必要な書き換え・統合を優先する。旧カード撤去や表示ラベル削除だけの新規試験は追加しない。

終了を求めるメッセージの配送失敗だけに特別な停止分岐を設けない。本文の意図をアプリが判定せず、共通配送の失敗・受付不明を表示する。利用者のpause／stopは配送結果を待たずに受け付ける。

## 8. 対象ファイル候補

`src/gigas/app/`・`runtime/codex/`・`ui/`・必要な`storage/`・`prompts/`、対応する試験と終了手順のdocs。app-serverの具体メソッドや結果型はM0で確認してから決める。

公開APIの変更時はdocstringと利用者向けdocsを更新し、型境界・docstringの対応skillを使う。GUIには必要なラベル・状態・エラーとCodex/ユーザー由来の文章を表示し、アプリ独自の説明本文はdocsへ置く。

## 9. 検証計画と未実行事項

固定通知でpause・clear・完了・中断の競合を確認し、採用ランタイムで追加指示に従う終了作業・Goal保持・結果を確認する。専用ターン移行の試験は予約しない。同一セッションでの再開はU06の経路を使って確認する。実機では途中の即時入力遮断・解除を確認する。終了指示資材を追加・変更する場合はT20も実施する。

| 確認 | 現在の結果 | 実施時の扱い |
|---|---|---|
| 方式調査・設計判断 | not run | 本工程未着手。採用版・機器・根拠と未確認事項を子仕様へ記録する |
| 製品の単体・結合試験 | not run | 実装時に対象のpytest、ruff、tyをAGENTS.mdに従って実行し、検査する契約を記録する |
| 追加指示・終了作業・Goal休止・実機停止 | not run | 元Goal保持、結果、収束、pause／stop割込みを確認する。U06の同一セッション再開との結合を確認する |
| 依存・公開API・配布 | not run | 変更する子仕様でuv lock --check・uv buildを含める。指示資材変更はT20も確認する |

親仕様の文書検査は工程計画の整合確認であり、上記の製品検証を実行済みにしない。工程完了には本書の必要な実接続・実機確認の根拠が必要で、模擬試験の成功だけで置き換えない。
