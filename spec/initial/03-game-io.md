# 03-game-io.md — 観測・操作

[文書一覧](README.md)

ゲームI/Oは、実機の映像取得と有限時間のコントローラー入力を担当します。画像の意味、攻略上の成功、次に必要な行動はCodexが判断します。本書のMCP名とJSONの項目名は初期実装設計として定めます。公開する機能と観測の意味は採用仕様です。

U01で実装した映像取得元・シリアルポートの設定保存は、機器の識別・接続・有効性を確認する機能ではありません。映像取得をU03、観測画像の非同期保存・MCP公開をU04 M2で実装しました。U04は固定Frameの実モデル試験に加え、WindowsのUSB Video Deviceを使う実映像の観測・保存と実画面での応答性を確認しました。ゲーム入力はU05で扱います。2026-11-11に改訂した工程の依存関係は[05](05-implementation.md)を正本とします。

| 担当工程 | 冒頭に決めること | この工程で確認する結果 |
| --- | --- | --- |
| [U03 映像取得](../complete/unit_008/VIDEO_CAPTURE.md) | 採用版と取得API、機器の列挙・識別、FPS・解像度、フレーム共有、切断・終了 | 保存やCodex接続に依存せず、一つの取得元からプレビューを表示できる |
| [U04 記録付き観測](../complete/unit_009/RECORDED_OBSERVATION.md) | 最新画像からの観測確定、保存・応答の同一性、部分失敗、MCPサーバの寿命・画像形式・接続設定 | 取得中の最新画像を保存し、`observe`経由で同じ画像と情報をCodexへ渡せる |
| [U05 操作と停止](../wip/unit_010/INPUT_AND_STOP.md) | 実デバイスと通信仕様、有限列の検証、取消し・解除、世代失効、記録と事後観測までの排他 | 記録した有限の操作列を実機へ送り、途中停止と解除、`act_and_observe`を確認できる |

U04では観測だけを接続し、U05で操作後観測を追加します。以下の2ツールは初期版全体の契約であり、U04単独で両方が完成する条件ではありません。

# 公開するツール

| 名前 | 要求 | 正常時の結果 |
| --- | --- | --- |
| `observe` | 引数なし | 取得中の最新キャッシュ画像と観測情報 |
| `act_and_observe` | 時間指定入力・待機の操作列 | 列全体の終了後に取得した画像と観測情報 |

操作だけの第三のツール、単発専用のツールは提供しません。単発入力は1要素の操作列です。操作列の途中を見て分岐する場合は、そこで呼び出しを分けます。初期版は実行可能なコードを操作列として受け取らず、データとして渡された入力・待機を実行します。

## 操作列の形式

```json
{
  "sequence": [
    {"kind": "press", "buttons": ["RIGHT"], "duration_ms": 200},
    {"kind": "wait", "duration_ms": 100},
    {"kind": "press", "buttons": ["A"], "duration_ms": 80},
    {"kind": "wait", "duration_ms": 250}
  ]
}
```

これは形式を示す例で、ゲームの確定手順ではありません。`press`は列挙したボタンを同時に押し、指定時間後に解除します。`wait`はニュートラル状態で待ちます。各要素をまたいで押下を持ち越しません。末尾の待機で、操作後の演出を待つ時間を表現できます。

press/waitとも正の整数ms、1要素以上の有限配列です。入力時間・要素数・合計時間の固定上限を設けず、ループや期限なしholdを受け付けません。開始前に列全体と機器の能力を検査し、未対応ボタンや無効時間があれば最初の入力も送らず拒否します。長い待機も途中停止で残りを破棄し解除します。ゲームが1 msの押下を認識する保証ではありません。M1の内部APIはwriteの完了時間にも固定上限を設けません。採用runtimeのMCP要求には既定300秒の期限があるため、長い有限列を制限しない公開方式はM2の公開前に解決します。詳細は[08](08-sdk-compatibility.md)を参照します。

入力は名前付きボタン・方向キーに加え、省略可能な左右stick（各軸整数-100〜100、右/下が正）と3DS用touch（320×240座標）を一つの完全状態として扱います。CH552/PokeCon/3DS S2/T3 New Firmwareの能力差、neutralとbyte変換、protocol別baudは[U05 M0](../complete/unit_036/INPUT_AND_STOP_DESIGN.md)で確定し、[M1](../complete/unit_038/INPUT_EXECUTION_AND_OBSERVATION.md)で内部APIへ実装しました。COMポート名や通信bytesをCodexの引数へ含めません。期限なしhold、keyboard、3DS管理コマンドは対象外です。Bluetoothの追加時も有限列・停止とtransportの変換を分けます。GUI・MCPとの結合とシリアル実機受入はM2です。内部APIの利用方法は[入力API](../../docs/input-api.md)を参照します。

## 正常な観測結果

画像をMCPのimage contentとして返し、付随情報をJSONで表現します。画像ファイルのパスだけを返してモデルが画像を見たと扱うことはありません。

```json
{
  "observation_id": "obs-9283fb5d-b85d-4ca7-b5a9-51cf0431523c",
  "captured_at": "2026-11-10T03:00:00.250Z"
}
```

`observation_id`はプロジェクト内で一意、`captured_at`はPC側でフレームを取得した時刻です。`observe`の要求時刻や保存時刻へ置き換えません。同じFrameが続けて選ばれることはあり、異なる観測IDでも元Frameの世代・連番と取得時刻は同じ場合があります。M1レビューで、未使用の予約欄だった`analysis`を観測保存と予定するMCP応答から除きました。画像の解釈はCodexが応答受信後に行い、その公開応答や対話履歴は原観測と別に記録します。正常応答に入力送出の`success: true`等は追加しません。画像中で目標が達成されたことも保証しません。

MCPは一つのObservationからPNGのimage contentと、観測ID・取得UTC・元Frame情報・出力画像情報のJSON text contentを返します。`structuredContent`への二重配送はしません。M2では採用ランタイムと実モデルが画像中のランダム英数字・四隅の色・観測IDを回答し、保存PNGとの対応を確認しました。詳細と未確認範囲は[08](08-sdk-compatibility.md)に記録します。

# キャプチャーと画像の鮮度

映像取得元を一つだけ開き、継続取得した最新フレームをプレビューと観測で共有します。内部のFrameは画像、連番、UTC時刻、単調増加時計の取得値を持ちます。時刻の前後比較には単調増加時計を使い、ログ表示にはUTC時刻を使います。

取得にはOpenCV-headless 4.14.0.94を使い、保存した機器識別子を接続直前の列挙結果へ解決します。名前や一時的な番号へ自動代替しません。OS別の優先方式はWindowsがDirectShow、LinuxがV4L2、macOSがAVFoundationです。代替は、利用可能なWindowsのMSMF、LinuxのGStreamerで同じ非空の識別子が一意に対応する場合に限ります。macOSには第2方式を設けません。列挙と接続で方式を一致させ、別方式へ同じ番号をそのまま渡しません。

機器識別子はWindowsの機器パス、Linuxの取得可能な`by-id`・`by-path`別名、macOSの`uniqueID`とし、表示名・一時的な番号と分離します。Windowsの既存パスの意味を維持し、別OSの機器へ読み替えません。識別子がない汎用番号探索や、名前・VID/PIDだけによる同一機器の推測は採用しません。取得方式のOS分岐を設けることは、アプリ全体の他OS対応完了を意味しません。設定パスのWindows依存、Linuxの権限・識別子、macOSの権限・OpenCV番号との対応はそれぞれ実機確認が必要です。

代替試行は接続要求から最初の有効なFrameまでに限定します。前候補の正常解放と子プロセス終了を確認してから、未試行の同一機器候補へ進みます。全候補を通じた開始期限を持ち、停止・アプリ終了・終了未確認で連鎖を取り消します。固着した候補を強制終了したことだけを正常解放と同一視しません。取得開始後の自動再接続やダミー映像への切替は行いません。

取得解像度の要求は「自動」、HD（1280×720）、FullHD（1920×1080、既定）、WQHD（2560×1440）、4K（3840×2160）から選びます。「自動」は幅・高さを指定せず、最大解像度の探索はしません。固定値と異なる有効な画像が届いても、実寸法と画素を保って共有し、要求との差を診断へ記録します。取得FPSも要求値・機器報告値・ホスト到着頻度を区別します。

到着画像は幅16〜3840、高さ16〜2160のuint8・3チャンネルBGRに限定します。上限超過を縮小で隠さず、同一世代内で最初の実寸法から変化した場合も取得エラーにします。共有Frameは実寸法と一致する変更不能なBGR bytes、接続世代、連番を持ちます。世代はサービス寿命内の識別子であり、U04の永続的な観測IDを代替しません。実寸法はPCへ届いた画像についての情報であり、HDMI原信号の寸法を保証しません。

機器選択はデバイスの表示名で行い、識別子は内部の保存・照合に使います。同名機器は短い識別情報を添え、保存機器が未検出でも別機器へ自動変更しません。2026-11-11の[実装整理M0](../complete/unit_027/IMPLEMENTATION_SIMPLIFICATION.md)で、選択欄は保存する機器、実際の取得状態は主画面ステータスに分ける契約へ改訂しました。この契約は[M1の設定・機器選択整理](../complete/unit_028/SETTINGS_DEVICE_SIMPLIFICATION.md)で実装しました。模擬機器とWindows Qtで検証済みで、実機の再検証は未実施です。

設定はモーダルとし、メニューと設定の機器選択を同じ保存・反映処理へ統合します。「未接続」の反映では機器を空に保存して取得を終了し、記憶を残す独立した映像停止と設定再読込は撤去します。起動・設定を開く操作・一覧更新だけでは接続しません。OK／適用は全タブの設定を反映するため、停止中に機器Aが選ばれていれば、一般タブだけの変更でもAの接続を試みます。保存失敗なら取得を変えず、保存後の接続失敗では保存値を巻き戻しません。OKは保存成功と反映要求の引渡し後に閉じ、接続成功を待ちません。旧取得の解放確認前に新取得を始めず、取得先・取得FPS・要求解像度が同じなら、要求値と実到着値の差で再接続しません。処理中の変更・キャンセルと復旧操作はM0仕様に従います。

ウィンドウとプレビュー枠は独立した4段階の表示プリセットで切り替えます。「レターボックス」は画像全体を比率維持で枠へ収め、余白を黒にします。「ストレッチ」は縦横それぞれを枠へ合わせます。取得解像度が自動でも表示方式を選べます。表示サイズ・表示頻度・プレビュー方式の変更で取得元を開き直さず、共有Frameへ黒帯・拡縮・切り抜きを加えません。

現行APIは[映像API](../../docs/video-api.md)、今回の契約改訂と受入状態は[設定・映像再設計](../complete/unit_026/SETTINGS_AND_STATUS_REDESIGN.md)を参照します。U03当初のDirectShow固定・要求寸法一致の判断と検証は[方式設計](../complete/unit_020/VIDEO_CAPTURE_DESIGN.md)の履歴として保持します。

取得サービスが接続と終了を所有し、プレビューと後続観測はそれぞれ読み取り専用の`CaptureReader`から状態と不変フレームを参照します。参照を渡す短いロックの外で各読み手が画像を処理するため、観測側が古い画像を保持してもプレビューは新しい画像へ進めます。観測側の変換・保存・配送はGUIスレッド外で行います。U03の共有境界試験とU04の実MCP・画像処理負荷試験を分けます。[レビュー反映仕様](../complete/unit_023/VIDEO_REVIEW_REFINEMENT.md)に実装・検証の状態を記録します。

2026-11-12のU04 M0で、`observe`は要求後の新フレームを待つ設計から、最新キャッシュをそのまま使う設計へ変更しました。単独観測には操作完了との時刻比較が不要であり、U03が既に持つ状態付きsnapshotで成立するためです。続く[M1](../complete/unit_032/RECORDED_OBSERVATION_IMPLEMENTATION.md)で観測・保存APIを実装し、[M2](../complete/unit_035/MCP_OBSERVATION_INTEGRATION.md)で製品MCPと通常チャットへ結合しました。固定Frameと実機映像の双方で実モデルへの配送・保存の対応を確認しました。過去の作業仕様にある新フレーム待機の記述は当時の方針として保持します。

`observe`は専用の`CaptureReader.snapshot()`を一度読み、`phase == "streaming"`かつ`frame`がある場合に、その一枚を観測元として確定します。取得停止・エラー・接続中・画像なしでは`DEVICE_UNAVAILABLE`として拒否します。要求受付後の取得であること、前回観測と異なる連番であることは要求せず、新フレームの待機・待機期限・追加の鮮度監視を設けません。確定前の停止はsnapshotの画像失効によって拒否し、確定後に取得が止まっても保持したFrameを書き換えません。観測の取消し・保存失敗・接続失効は取得停止とは別の条件として扱います。

`act_and_observe`は列の最後のneutral送出・末尾wait完了後にreadを開始した画像を返す設計です。U05 M1でFrameと共有搬送へread開始の単調時計を追加し、同じ取得generationかつ開始時刻が境界を超えるFrameを5秒以内に選ぶ内部APIを実装しました。既存の取得完了時刻は維持します。待機は既存readerによる20 ms間隔の局所再確認とし、取得停止・世代変更・入力停止で打ち切ります。操作前キャッシュを使わず、選んだFrameをU04の共通符号化へ直接渡します。保存と応答は同じObservationを使います。単独observeとの符号化競合は、操作済みの可能性を示す事後観測失敗として返し、入力を再送しません。MCPへの公開と実機の映像反映はM2で確認します。

最新観測と事後観測の入口は同じObservationServiceにまとめ、確定Frameの加工・符号化・保存依頼を共用します。事後観測の会話IDは受付済みrunから明示的に渡します。構成と検証は[U05境界整理](../complete/unit_039/INPUT_OBSERVATION_SIMPLIFICATION.md)に記録します。

Frameの取得完了時刻とread開始時刻はPC側の順序を示し、キャプチャーカードやドライバ内部のバッファ遅延を保証しません。read開始が操作完了後という現条件と、そのためのread_started_ns必須化の妥当性は再検討事項です。今回の境界整理では条件を維持し、M2の鮮度受入条件を確定する前に見直します。`observe`は要求より前に取得した画像も返し、その取得時刻をそのまま示します。入力後の遅延と事後観測の成立はU05の実機試験で確認します。画面の意味や演出終了の自動判定は初期I/Oへ入れません。

U04は[加工済みObservationの契約](../complete/unit_034/CHAT_OBSERVATION_PERSISTENCE.md)に従い、最新Frameを共通設定オリジナル/FullHD（既定）/HDに従い、必要な場合だけ比率維持で縮小して一度PNG符号化します。小画像は拡大せず、切抜き・黒帯・引伸ばしを行いません。取得設定とプレビューは独立です。ObservationはPNG bytes・形式・出力寸法・観測IDと元FrameのUTC・世代・連番・寸法だけを持ち、Frame本体は保持しません。MCPは同じbytesをbase64化し、アプリは非同期保存します。保存中も次の観測を返し、元解像度画像の別保存は対象外です。M2で製品へ結合し、固定Frame・実HTTP・模擬runtimeで検証しました。Windowsの製品サービスと採用runtime・実モデルでも4K固定FrameからFullHD観測を配送し、同じ接続の次ターンで保存PNGを再参照できました。USB Video DeviceのFullHD・60 fps設定による実映像でも、MCP応答と保存PNG・元Frame情報・取得時刻・出力画像情報・観測IDの対応を確認しました。

保存画像とMCPのimage contentには同じPNG bytesを使用し、再符号化しません。一枚のPNG上限32 MiBを超えた場合は暗黙の縮小や切り抜きで回避せず、符号化失敗として扱います。符号化中の別観測はBUSYですが、保存タスクの数や滞留を新たな上限・保存見送り・BUSY条件にしません。M1では原寸画像の保存・復号と、保存中に模擬取得のプレビュー・切断が進むことを確認しました。M2では実MCPでの画像受信と文字の判別、実機映像の保存中のプレビュー描画、実行中のGUI操作、切断後の取得継続と通常終了を確認しました。実保存への遅延注入や他機器・長時間運転は未実施です。計測条件はM2子仕様、公開APIは[記録付き観測](../../docs/recorded-observation.md)を参照します。

# 一つの入力所有者とキャンセル

入力接続は一つの実行部が保持します。同時に複数の操作列を流しません。初期設計では実行中に別の操作列が来たら`BUSY`として返し、後から勝手に実行される長い待ち列を作りません。

`act_and_observe`は事後画像の確定・符号化まで入力実行枠を保持します。その間の別の操作要求も`BUSY`とし、後続の操作が先の呼び出しの事後画像へ混入しないようにします。HTTP応答の配送完了までは占有しません。`observe`単独は入力を行わず、実行中の列と同時なら、その時点の画面を観測するだけです。

操作権は入力サービスの要求受付で確認し、受付済みの列は停止時に取り消します。停止は実行中の待機にも伝え、終了処理でニュートラルを送ります。

操作許可を閉じた後に受け取った要求や、停止前の接続から届いた要求は拒否します。呼び出し元と実行世代の対応はMCPの接続コンテキストで扱い、モデルが引数を指定して操作権を得る仕組みにはしません。UIの停止通知も同じ入力実行部へ届きます。

停止要求の受付と、進行中write・解除の完了は別です。M1は取消し後も開始済みwriteの自然完了を回収してからneutralを送る方式を実装しました。ドライバーが戻らない場合の停止時間は保証しません。通信失敗時の解除とMCU側の押下維持はM2で実機確認します。確認前にハードウェアのデッドマンスイッチ相当の保証はしません。

# 失敗の返し方

MCPの実行失敗を示す結果と、短い機械可読コード・説明を返します。成功応答の形へエラーを混ぜません。以下は初期の内部分類であり、MCPライブラリの例外型とは変換箇所で対応させます。

| 分類 | 意味と後続処理 |
| --- | --- |
| `INVALID_SEQUENCE` | 入力前の検査で拒否しました。入力は送っていません |
| `INPUT_DISABLED` / `BUSY` | 操作権が無効、または別の列を実行中です。自動でキューへ入れません |
| `INTERRUPTED` | 途中で中断しました。完了済み要素数と解除の送出状況を記録します |
| `DEVICE_UNAVAILABLE` | `observe`で取得中の有効画像がない場合、または入力デバイスの切断・送信失敗です。入力後の失敗では実行結果が不明な可能性を残します |
| `OBSERVATION_TIMEOUT` | U05の事後観測で、操作完了後の画像を期限内に取得できませんでした。U04の`observe`には新フレーム待機を設けません |
| `STORAGE_ERROR` | U05の操作前記録など、入力を許可する前提の保存に失敗しました。U04の画像保存失敗はMCP観測成功を変更せず、アプリの記録失敗として報告します |

画像取得や応答転送に失敗しても、既に物理入力が実行された可能性があります。アプリもMCPハンドラも操作列を自動再送しません。結果が不明なら新しい観測から再判断します。内部の操作IDを用い、同じ要求の結果と前後関係をログで追えるようにしますが、実機へのexactly-once実行を宣言しません。

# MCPとゲームI/Oの境界

MCP公開部は、要求の検査、内部の操作型への変換、加工・符号化済みObservationのbase64画像・JSONへの包装を担当します。追加の画像加工はせず、アプリの観測サービスが保存にも同じObservationを渡します。MCPはwriterを所有せず、保存完了を応答の前提にしません。観測の保存をCodexの解釈完了まで遅らせず、後から受信する解釈・対話履歴で原観測を書き換えません。`observe`には非破壊・閉じた対象を示す`destructiveHint: false`・`openWorldHint: false`を公開します。アプリ側の原記録追加があるためreadOnlyHintをtrueとせず、観測IDも毎回変わるため冪等と宣言しません。ゲームI/OはMCPのリクエストオブジェクト、Codexのスレッド、Qtのオブジェクトを受け取りません。入力デバイス用の小さな境界で`connect`、状態送信、`neutral`、`close`を扱い、初期実装をシリアルへ限定します。

act_and_observeのツール説明は適用中のプロトコルと対応入力を示します。設定切替後の次の送信で、新MCP公開とCodex側の再読込を行います。

HTTPサーバは127.0.0.1のOS割当ポートへ束縛します。U04の実装は接続ごとにMCP名とBearer値を作り、thread/start.configへ渡します。U05ではこれを一実行ごとの変更しないGrantへ結び付け、停止・通常turn終端で失効する設計です。次の明示送信では旧処理収束後にthread/unsubscribe→同IDのthread/resumeで新endpointを公開します。loadedのresumeだけでは更新できないことと、正しい副作用注釈・当該actだけのapproval_mode=approveで実モデルが模擬入力を2ターン呼べることをM0で確認しました。製品入力・GUI停止との結合は未実施です。詳細と確認範囲は[08](08-sdk-compatibility.md)を参照します。HTTP認証情報をモデル向け指示や原記録へ保存せず、他の実行や整理用threadへゲーム入力を開放しません。

設定UIはM2で既存I/Oタブのポート・protocol・baudを一つのsnapshotとしてOK／適用で保存し、M1の実効値解決と接続APIへ渡します。独立した入力接続・切断UIは設けず、「未接続」の適用で切断します。同条件で接続済みなら維持し、操作中の異なる条件の適用は旧列の停止・解除・close後に切り替えます。取消しは未適用編集だけを破棄し、保存失敗では旧接続を保持します。専用worker一つがopen/write/neutral/closeを所有します。停止・入力切断・アプリ終了に加え、取得の停止/切替/障害・記録失敗も共通入力停止へ接続します。モーダル内にも同じ停止actionを用意します。保存とCodex応答を待たず権限を閉じ、実行中の操作を取り消し、開始済みwriteの回収後にneutralを送ります。送出済みと実機解除確認を分け、再送・自動再接続は行いません。具体的な設定値と競合条件は[U05 M0](../complete/unit_036/INPUT_AND_STOP_DESIGN.md)、内部APIと検証済み範囲は[M1](../complete/unit_038/INPUT_EXECUTION_AND_OBSERVATION.md)に置きます。

将来の解析は、保存した観測IDを対象に別途呼ぶ機能です。NyX由来の入力・キャプチャー処理へゲーム別解析関数の注入機構を作りません。Bluetooth対応も、共通の操作意味を変えず入力デバイス実装として追加します。
