# 03-game-io.md — 観測・操作

[文書一覧](README.md)

ゲームI/Oは、実機の映像取得と有限時間のコントローラー入力を担当します。画像の意味、攻略上の成功、次に必要な行動はCodexが判断します。本書のMCP名とJSONの項目名は初期実装設計として定めます。公開する機能と観測の意味は採用仕様です。

# 公開するツール

| 名前 | 要求 | 正常時の結果 |
| --- | --- | --- |
| `observe` | 引数なし | 新しい画像と観測情報 |
| `act_and_observe` | 時間指定入力・待機の操作列 | 列全体の終了後に取得した画像と観測情報 |

操作だけの第三のツール、単発専用のツールは提供しません。単発入力は1要素の操作列です。操作列の途中を見て分岐する場合は、そこで呼び出しを分けます。初期版は実行可能なコードを操作列として受け取らず、データとして渡された入力・待機を実行します。

## 操作列の形式

```json
{
  "sequence": [
    {"kind": "press", "buttons": ["RIGHT"], "duration_ms": 200},
    {"kind": "wait", "duration_ms": 100},
    {"kind": "press", "buttons": ["A"], "duration_ms": 80},
    {"kind": "wait", "duration_ms": 250}
  ]
}
```

これは形式を示す例で、ゲームの確定手順ではありません。`press`は列挙したボタンを同時に押し、指定時間後に解除します。`wait`はニュートラル状態で待ちます。各要素をまたいで押下を持ち越しません。末尾の待機で、操作後の演出を待つ時間を表現できます。

時間は正の整数ミリ秒、列は1要素以上とします。許可ボタン、同時押し可否、要素数と合計時間の上限は入力デバイスの能力とアプリ設定から検査します。開始前に列全体を検査し、未対応ボタンや無効時間があれば、最初の入力も送らず拒否します。上限の具体値は入力実装の作業仕様で定めてテストに残します。無制限を既定値にはしません。

初期ボタン表現は、実機の入力プロトコルで提供できるボタンと方向キーを正規化した名前です。COMポート名や通信バイト列をCodexの引数へ含めません。アナログ値や新しい接続方式を追加する場合も、MCPの契約とデバイス実装の変換を分けて変更します。

## 正常な観測結果

画像をMCPのimage contentとして返し、付随情報をJSONで表現します。画像ファイルのパスだけを返してモデルが画像を見たと扱うことはありません。

```json
{
  "observation_id": "obs-000184",
  "captured_at": "2026-11-10T03:00:00.250Z",
  "analysis": {}
}
```

`observation_id`はプロジェクト内で一意、`captured_at`はPC側でフレームを取得した時刻です。`analysis`は解析していない場合も常にオブジェクトとし、初期版は空です。正常応答に入力送出の`success: true`等は追加しません。画像中で目標が達成されたことも保証しません。

MCPの画像とJSONの具体的な配置は採用版に合わせます。`structuredContent`を利用する場合もモデルから情報を読める形にし、必要なら同内容のtext contentを返します。意味の異なる二つの観測情報を作らず、一つの内部Observationから生成します。採用ランタイムが画像とメタデータを受け取ったことは接続試験で確認します。

# キャプチャーと画像の鮮度

映像取得元を一つだけ開き、継続取得した最新フレームをプレビューと観測で共有します。内部のFrameは画像、連番、UTC時刻、単調増加時計の取得値を持ちます。時刻の前後比較には単調増加時計を使い、ログ表示にはUTC時刻を使います。

`observe`は要求受付後、`act_and_observe`は列の最後の解除・待機完了後を境界として、それより後に取得されたフレームを待ちます。最新キャッシュがあるだけでは、事後観測の条件を満たしたとしません。待機中にキャプチャーが止まった場合は期限付きで失敗させ、古い画像を新しい画像として返しません。

この保証はPC側の取得時点についてのものです。キャプチャーカードやドライバ内部のバッファ遅延まで消えるわけではありません。実機試験で取得遅延を確認し、必要ならその取得方式を調整します。画面の意味や演出終了の自動判定は初期I/Oへ入れません。

観測時に画像を確定し、保存・MCP応答・後段解析の参照先で同じ画像を扱います。縮小やゲーム領域の切り出しを入れる場合は、その変換後の観測画像を保存します。モデルへ渡した画像と記録画像が異なるものにならないようにします。観測用画像の解像度は、ゲーム画面と文字が判別できることを実機で確認して設定します。

# 一つの入力所有者とキャンセル

入力接続は一つの実行部が保持します。同時に複数の操作列を流しません。初期設計では実行中に別の操作列が来たら`BUSY`として返し、後から勝手に実行される長い待ち列を作りません。

`act_and_observe`は事後画像を確定するまで入力実行枠を保持します。その間の別の操作要求も`BUSY`とし、後続の操作が先の呼び出しの事後画像へ混入しないようにします。HTTP応答の配送完了までは占有しません。`observe`単独は入力を行わず、実行中の列と同時なら、その時点の画面を観測するだけです。

各列は、受付時と各入力の直前に、その実行に操作権があるか確認します。停止要求は割り込み可能な待機へ伝えます。操作列の後処理ではキャンセル判定より優先してニュートラル状態を送ります。通常の`release()`が中断チェックで例外になる実装を、停止時の解除に使わないようにします。

操作許可を閉じた後に受け取った要求や、停止前の接続から届いた要求は拒否します。呼び出し元と実行世代の対応はMCPの接続コンテキストで扱い、モデルが引数を指定して操作権を得る仕組みにはしません。UIの停止通知も同じ入力実行部へ届きます。

Python内での停止が遅延しないことと、PC故障時の物理入力解除は別です。シリアルのwrite timeout、送信失敗時のニュートラル送信可否、MCU側の押下維持を実機で確認します。確認前にハードウェアのデッドマンスイッチ相当の保証はしません。

# 失敗の返し方

MCPの実行失敗を示す結果と、短い機械可読コード・説明を返します。成功応答の形へエラーを混ぜません。以下は初期の内部分類であり、MCPライブラリの例外型とは変換箇所で対応させます。

| 分類 | 意味と後続処理 |
| --- | --- |
| `INVALID_SEQUENCE` | 入力前の検査で拒否しました。入力は送っていません |
| `INPUT_DISABLED` / `BUSY` | 操作権が無効、または別の列を実行中です。自動でキューへ入れません |
| `INTERRUPTED` | 途中で中断しました。完了済み要素数と解除の送出状況を記録します |
| `DEVICE_UNAVAILABLE` | デバイス切断・送信失敗です。実行結果が不明な可能性を残します |
| `OBSERVATION_TIMEOUT` | 入力完了後を含め、新しい画像を取得できませんでした |
| `STORAGE_ERROR` | 記録・観測画像を保存できませんでした。追跡できない状態で入力を続けません |

画像取得や応答転送に失敗しても、既に物理入力が実行された可能性があります。アプリもMCPハンドラも操作列を自動再送しません。結果が不明なら新しい観測から再判断します。内部の操作IDを用い、同じ要求の結果と前後関係をログで追えるようにしますが、実機へのexactly-once実行を宣言しません。

# MCPとゲームI/Oの境界

MCP公開部は、要求の検査、内部の操作型への変換、結果の画像・JSONへの変換を担当します。ゲームI/OはMCPのリクエストオブジェクト、Codexのスレッド、Qtのオブジェクトを受け取りません。入力デバイス用の小さな境界で`connect`、状態送信、`neutral`、`close`を扱い、初期実装をシリアルへ限定します。

HTTPサーバはlocalhostへ束縛します。操作許可は接続を発行した実行と対応付け、他の実行や整理用スレッドへゲーム入力を開放しません。HTTP認証情報はモデルに見せるログやプロジェクトファイルへ保存しません。具体的なMCP接続設定と更新方式は採用版で確認します。

将来の解析は、保存した観測IDを対象に別途呼ぶ機能です。NyX由来の入力・キャプチャー処理へゲーム別解析関数の注入機構を作りません。Bluetooth対応も、共通の操作意味を変えず入力デバイス実装として追加します。
