# 01-overview.md — 設計概要

[文書一覧](README.md)

**GIGAS — General-purpose Interactive Gaming Agent System（Project GIGAS）** は、Windows上の専用アプリから、既存の汎用AIエージェントに実機ゲームの攻略と操作補助を任せるシステムです。画面観測とコントローラー入力を使い、数時間から数十時間の継続プレイ、途中介入、停止後の再開を目指します。初期対象は利用者が指定したNintendo Switch版ファイアレッド・リーフグリーンです。アプリにゲーム固有の攻略エンジンを組み込む仕様ではありません。

製品要求の初版は2026-11-10です。2026-11-13の[契約整理M0](../wip/unit_054/KISS_SIMPLIFICATION.md)で、専用記憶整理を初期版から外し、接続・停止・表示・保存・入力の保証を縮小しました。本書は採用した利用場面と機能範囲を定めます。接続・停止・表示と責務分離はunit_054 M1で実装・検証済みです。保存・入力のM2は採用設計・未実装であり、設計採用だけでは動作確認済みとしません。

# 文書の位置づけ

製品の要求を「採用仕様」、その要求を実装可能な形へ具体化した内容を「初期実装設計」として扱います。後者は実装で得た事実に応じて変更できます。Codexとの接続で未確認の事項は[互換性と未確認事項](08-sdk-compatibility.md)へ集約し、実機の具体条件は該当する親・子仕様で管理します。各工程の冒頭で調査・設計し、設計判断、実装、接続・実機検証を分けて記録します。

開発を行うCodexと、アプリ内でゲームをプレイするCodexは役割が異なります。開発用のAGENTS.mdやSkillsは[リポジトリ構成](06-repository.md)、プレイ用の指示と記憶は[エージェント設計](04-agent-memory.md)で扱います。

# 目指す使い方

| 場面 | アプリの動作 |
| --- | --- |
| 新しい依頼 | 機器を選び、プロジェクトを開き、自然文の依頼を渡して明示的に開始します |
| 継続攻略 | Codexが目標を分解し、観測と操作を繰り返します。Goalsがターンをまたぐ継続を担います |
| 途中介入 | 追加指示を実行中のCodexが取り込める時点で渡します。即座に止めたい場合は停止操作を使います |
| 回答待ち | 質問・要求を表示し、回答送信で続行します。手動停止した後は明示的な再開を要します |
| 再開 | 同じスレッド、または新しいスレッドで記憶と現在画面を照合して続けます |
| 記憶更新 | 攻略中にCodexがメモを更新し、停止中には利用者が編集できます。専用の整理機能は設けません |

代表例は「起動直後の画面からニビシティのタケシ撃破まで進めて」です。終了後に同じプロジェクトで次の依頼を渡しても、同じセーブ状態から新しいプロジェクトを始めても構いません。プロジェクトは依頼・記憶・会話をまとめる作業単位であり、セーブデータを保存・復元する単位ではありません。

# 採用する構成

| 項目 | 採用仕様 |
| --- | --- |
| PCとUI | Windowsネイティブ、Python、ネイティブGUI。初期実装設計ではPySide6を使います |
| エージェント | 公開app-serverプロトコルの単一stdio接続でローカルのCodexプロセスを制御します。U02でPython SDKの受信停止を確認し、直接接続へ変更しました |
| 攻略判断 | 画面理解、目標分解、計画、進捗判断、検索、記憶更新をCodexへ任せます |
| ゲームI/O | アプリ内で映像取得と入力接続を維持します。初期入力はシリアルデバイスです |
| ゲームMCP | 同じPythonプロセスに組み込み、localhostのStreamable HTTPでCodexへ公開します |
| 公開機能 | 「観測のみ」と「操作列の実行と事後観測」の2つです |
| 観測結果 | 静止画1枚、観測時刻、観測IDと元Frame情報。未使用の解析情報は追加しません |
| 記憶と原記録 | Markdown記憶、JSONLトランスクリプト、観測画像を保持します。プロジェクト未選択のチャットにもアプリ管理の記録先を用意します。会話の永続化と可搬なJSONLの段階は04に従います |
| 認証とモデル | ChatGPTログインを使用します。APIキー対応は今回対象外です。ログイン・接続とモデル・エフォートの選択を分けます。アプリ共通の既定値から開始し、接続を維持したまま次ターンの設定を変更できます |

ゲームI/OはProject_NyXの部品を参考に本プロジェクト側で再構築します。NyXPyへの改修依頼や、NyX全体への実行時依存を前提にしません。MCP部分もCodex接続部やUIの初期化に依存させず、将来の単独起動へ備えます。初期版でSTDIO入口まで実装する必要はありません。

認証と実行設定の分離は2026-11-11の追加要求です。[実行設定の契約](02-runtime.md)を[U06](../complete/unit_011/GOAL_EXECUTION.md)で具体化し、M1/M2で通常・自律ターンの次ターン設定変更を実装、M3で新規ログインと両設定経路の実モデル反映を確認しました。APIキー方式は2026-11-13の合意でU06 M3の実装・受入から外しました。

# 初期版の範囲

ライブプレビュー、公開された計画、接続・実行状態、依頼と追加指示、開始・即時停止・再開、回答・承認の受付を提供します。計画欄はCodexの計画更新通知を表示元とし、アプリが独自に攻略計画を作りません。表示できる進捗や推論要約はapp-serverが公開する範囲です。

U06のUIレビューを経て、右に映像と常設の目標・今回の作業、左に会話と一体型Messageを配置しました。質問・承認は履歴内の要求カードで扱い、通常入力と追加指示はMessageから送ります。[主画面とメッセージ操作](10-ui-interaction.md)を正本とし、U07の専用計画的終了は初期版から外します。公開推論要約はreasoning、ツール活動はactivityと識別し、公開されない内部思考の表示は前提にしません。

共通停止は区切りや保存を待たず、turnの中断と操作列の取消し・押下解除を行います。activeなGoalは目的を保持して休止し、既に非activeならその状態を保ちます。目標欄の削除は目的の取り下げだけで、現在の動作は止めません。再開は目的を変えずactiveを要求する別操作です。会話・記憶・原記録は削除しません。これらの契約は[unit_061](../complete/unit_061/CONVERSATION_EXECUTION_MODEL.md)・[unit_062](../complete/unit_062/GOAL_EXECUTION_MODEL.md)に従います。

計画的終了の専用機能・受入は初期版対象外です。「保存して終えて」も通常指示として扱い、終了専用の状態・手順や、Goal休止・セーブ成功の保証を設けません。保存参照・アプリ再起動後の復帰と、既存スレッドを使わない再構成はU08が担当します。共通停止はゲーム自体の時間停止を意味しません。

許可した作業領域のファイル読み書き、コマンド実行、攻略情報のWeb検索、ゲームMCP利用は自律実行します。対応するコマンド・ファイルの一回限りの承認要求をGUIへ届け、未対応の要求形式は拒否します。公開APIで明示された利用制限・最終失敗は状態として表示し、その通知だけで共通停止を起動しません。通信断では資源を閉じ、操作列を回収します。残高や時刻だけで続行可否を推定せず、枠回復後の自動再開や課金先の自動変更は行いません。

攻略の継続・再試行・休止・完了はCodexの公開状態に従います。アプリ独自の停滞推定・状態整合性修復・自動再投入は行いません。通常指示と追加指示は同じturn/startへ送り、現在turnへの介入か新turnの開始かはapp-serverが決めます。Goalの完了やturn間を理由に通常送信を禁止しません。下書きを保持し、自動配送キュー・自動再送や、記憶整理を開始条件へ追加しません。

# GUIの文言方針

GUIへの文章の記載は原則禁止とします。アプリが使い方やUIの意味を説明する本文、初回案内、空領域の説明、説明用ツールチップは置きません。使い方はREADME/docsへ記載します。ボタン名・項目名・見出し、短い状態名・確認対象・エラー理由、パスや値は必要な識別情報として表示できます。説明文をラベルへ分割して埋め込むこともしません。

Codexが送る応答・公開計画・質問・承認内容などのテキストと、ユーザーがアプリへ投入する文章は例外です。エラーメッセージも文章で説明してよく、失敗した操作、確認できた原因・影響、復旧操作を具体的に伝えます。未確認の原因を断定せず、この例外を通常画面の使い方・機能説明へ広げません。

エラーは一時通知だけで消さず、詳細を再確認できる導線を設けます。主画面へログ全文を常設せず、状態と診断詳細を分けます。確認が必要な操作以外でモーダルを乱発し、中断・切断を妨げません。この方針はU01だけでなく、後続の全GUIへ適用します。

# 初期版に含めないもの

内部メモリの読み取り、エミュレータ固有の状態、セーブステート、フレーム停止、専用モデルの学習、研究用ベンチマークには依存しません。Bluetooth入力、独立MCPサーバのSTDIO入口、後段の画像解析は拡張候補です。専用の記憶整理、自動整理、記憶全体の退避・自動復元・未完整理の復旧は初期版から外します。実需が生じた場合に[U09](../planned/unit_014/MEMORY_MAINTENANCE.md)を再設計し、候補生成や採用APIも先行追加しません。

常時録画、記憶全体の可視化、攻略用Skillsの自己生成・自己管理、大規模な検索基盤は初期範囲に入れません。操作の再利用は短い固定操作列と、判断を含む手順を記憶して参照する範囲です。複数の実機を同時運転する機能は設計しません。

# 開発方針

使い捨てPoCからの増築を前提にせず、正式な小さな実装単位を作って検証します。変更範囲を閉じ込める境界を先に定めますが、未確認のAPIを想像して全体の骨格や汎用プラグイン基盤を作りません。模擬機器は本実装のテストで使い、製品経路に偽の成功応答を残しません。

実装で前提が変われば、影響する部品と仕様を修正します。変更を一切発生させないことではなく、変更理由と影響範囲を追えることを目指します。次の作業単位を一つ選び、仕様・実装・必要な試験を一緒に完成させる運用を[実装計画](05-implementation.md)に定めます。
