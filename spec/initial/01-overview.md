# 01-overview.md — 設計概要

[文書一覧](README.md)

**GIGAS — General-purpose Interactive Gaming Agent System（Project GIGAS）** は、Windows上の専用アプリから、既存の汎用AIエージェントに実機ゲームの攻略と操作補助を任せるシステムです。画面観測とコントローラー入力を使い、数時間から数十時間の継続プレイ、途中介入、停止後の再開を目指します。初期対象は利用者が指定したNintendo Switch版ファイアレッド・リーフグリーンです。アプリにゲーム固有の攻略エンジンを組み込む仕様ではありません。

設計版: 1.0（2026-11-10）。本実装へ引き継ぐ設計初版です。アプリの実装完了や、採用SDK・Windows実機での動作確認を意味しません。

# 文書の位置づけ

製品の要求を「採用仕様」、その要求を実装可能な形へ具体化した内容を「初期実装設計」として扱います。後者は実装で得た事実に応じて変更できます。SDK・実機との接続で未確認の事項は[互換性と未確認事項](08-sdk-compatibility.md)へ集約し、影響するコンポーネントの実装完了条件として確認します。

開発を行うCodexと、アプリ内でゲームをプレイするCodexは役割が異なります。開発用のAGENTS.mdやSkillsは[リポジトリ構成](06-repository.md)、プレイ用の指示と記憶は[エージェント設計](04-agent-memory.md)で扱います。

# 目指す使い方

| 場面 | アプリの動作 |
| --- | --- |
| 新しい依頼 | 機器を選び、プロジェクトを開き、自然文の依頼を渡して明示的に開始します |
| 継続攻略 | Codexが目標を分解し、観測と操作を繰り返します。Goalsがターンをまたぐ継続を担います |
| 途中介入 | 追加指示を実行中のCodexが取り込める時点で渡します。即座に止めたい場合は停止操作を使います |
| 回答待ち | 質問・要求を表示し、回答送信で続行します。手動停止した後は明示的な再開を要します |
| 再開 | 同じスレッド、または新しいスレッドで記憶と現在画面を照合して続けます |
| 記憶整理 | 依頼完了後とユーザーの明示操作で、攻略とは別スレッドに整理を任せます |

代表例は「起動直後の画面からニビシティのタケシ撃破まで進めて」です。終了後に同じプロジェクトで次の依頼を渡しても、同じセーブ状態から新しいプロジェクトを始めても構いません。プロジェクトは依頼・記憶・会話をまとめる作業単位であり、セーブデータを保存・復元する単位ではありません。

# 採用する構成

| 項目 | 採用仕様 |
| --- | --- |
| PCとUI | Windowsネイティブ、Python、ネイティブGUI。初期実装設計ではPySide6を使います |
| エージェント | Python版Codex SDKでローカルのCodex app-serverプロセスを制御します |
| 攻略判断 | 画面理解、目標分解、計画、進捗判断、検索、記憶更新をCodexへ任せます |
| ゲームI/O | アプリ内で映像取得と入力接続を維持します。初期入力はシリアルデバイスです |
| ゲームMCP | 同じPythonプロセスに組み込み、localhostのStreamable HTTPでCodexへ公開します |
| 公開機能 | 「観測のみ」と「操作列の実行と事後観測」の2つです |
| 観測結果 | 静止画1枚、観測時刻、観測ID、解析情報。初期の解析情報は空のオブジェクトです |
| 記憶と原記録 | Markdown記憶、JSONLトランスクリプト、観測画像をプロジェクト内へ保存します |
| 認証とモデル | ChatGPTログインを主に、APIキーにも対応します。モデル・エフォートはアプリ共通設定です |

ゲームI/OはProject_NyXの部品を参考に本プロジェクト側で再構築します。NyXPyへの改修依頼や、NyX全体への実行時依存を前提にしません。MCP部分もCodex SDKやUIの初期化に依存させず、将来の単独起動へ備えます。初期版でSTDIO入口まで実装する必要はありません。

# 初期版の範囲

ライブプレビュー、公開された計画、接続・実行状態、依頼と追加指示、開始・即時停止・計画的終了・再開、回答・承認の受付を提供します。計画欄はCodexの計画更新通知を表示元とし、アプリが独自に攻略計画を作りません。表示できる進捗や推論要約はSDKが公開する範囲です。

一時停止、アプリ再起動、既存スレッドを使わない再開、ゲームの再起動・リセット後の照合を扱います。即時停止はAIの入力を遮断します。計画的終了は元の攻略Goalを休止し、同じスレッドの通常ターンでプレイ終了処理を行ってから停止します。元Goalの目的は置き換えず、ゲーム内セーブは全ゲーム共通の必須条件にしません。いずれもゲームの時間停止を意味しません。

許可した作業領域のファイル読み書き、コマンド実行、攻略情報のWeb検索、ゲームMCP利用は自律実行します。追加権限が必要な場合だけ承認を求めます。利用枠・クレジット不足で続行不能なら停止し、取得できた利用枠と回復予定時刻を表示します。枠回復後の自動再開や課金先の自動変更は行いません。

攻略の継続・再試行・休止・完了はCodexの公開状態に従います。アプリ独自の停滞推定・状態整合性修復・自動再投入は行わず、解消できない停滞はユーザーが停止・明示的再開で扱います。完了した依頼への未配送・完了後の追加指示は破棄し、新しいGoalへ転用しません。記憶整理の失敗・中断時は整理前の記憶へ復元し、復元完了後に次の攻略を許可します。

# 初期版に含めないもの

内部メモリの読み取り、エミュレータ固有の状態、セーブステート、フレーム停止、専用モデルの学習、研究用ベンチマークには依存しません。Bluetooth入力、独立MCPサーバのSTDIO入口、後段の画像解析、頻繁な自動記憶整理は拡張候補です。

常時録画、記憶全体の可視化、攻略用Skillsの自己生成・自己管理、大規模な検索基盤は初期範囲に入れません。操作の再利用は短い固定操作列と、判断を含む手順を記憶して参照する範囲です。複数の実機を同時運転する機能は設計しません。

# 開発方針

使い捨てPoCからの増築を前提にせず、正式な小さな実装単位を作って検証します。変更範囲を閉じ込める境界を先に定めますが、未確認のAPIを想像して全体の骨格や汎用プラグイン基盤を作りません。模擬機器は本実装のテストで使い、製品経路に偽の成功応答を残しません。

実装で前提が変われば、影響する部品と仕様を修正します。変更を一切発生させないことではなく、変更理由と影響範囲を追えることを目指します。次の作業単位を一つ選び、仕様・実装・必要な試験を一緒に完成させる運用を[実装計画](05-implementation.md)に定めます。
