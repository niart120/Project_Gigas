# 07-verification.md — テスト・実機確認

[文書一覧](README.md)

本実装を小さな単位で作り、各単位の振る舞いを再実行できる試験で確認します。使い捨てのゲーム操作PoCを必須工程にせず、接続確認で得た事実を、その部品の仕様と試験へ残します。対象はアプリの契約と運用であり、ゲーム攻略能力を測るベンチマークは作りません。

初期の確認計画は2026-11-10、担当工程の改訂は2026-11-11です。2026-11-12の[U04 M0](../complete/unit_009/RECORDED_OBSERVATION.md)で、単独観測の対象を要求後の新フレームから取得中の最新キャッシュへ変更しました。本書は受入観点と担当工程を定め、確認済み範囲を末尾に区別して記載します。表中の完了条件だけでは試験実施済みを意味しません。実装順序は[05](05-implementation.md)、品質ゲートの選択は[AGENTS.md](../../AGENTS.md)、処理フローは[09](09-control-flows.md)を参照します。実施した採用版・機器・コマンド・結果は各作業仕様へ記録します。

# 確認の分担

| 段階 | 使うもの | 確認すること |
| --- | --- | --- |
| 単体試験 | 仮想時計、テスト用入力デバイス、固定画像、記録済み通知 | 操作列、停止、状態遷移、ログ保存などの決定的な振る舞い |
| 結合試験 | 本実装のサービスとMCP、テスト用の機器境界、PySide6 | ツールの要求・結果、非同期処理、GUIへの通知、記録との対応 |
| 実ランタイム接続確認 | 採用するCodex SDK・実行ファイルと認証済みアカウント | Goals、画像付きMCP応答、質問・承認、追加指示、計画通知の実際の接続 |
| Windows実機確認 | 対象PC、キャプチャー、入力デバイス、実機ゲーム | 機器接続、事後画像、入力解除、継続運転、再開 |

テスト用の模擬実装は`tests/`内で利用します。製品の実行経路では、未実装の機能を成功として返しません。ゲーム全体のシミュレーターを作らず、境界に必要な画像・入力・通知だけを置き換えます。

停止試験では、正常終了時の解除だけを確認して終えません。押下直後、待機中、最後の要素、結果返却直前に中止が入る場合も扱います。解除が機器へ届かなかった場合は、アプリ内部の「停止済み」と実機の解除確認を混同しない結果にします。

U05の事後観測では、アプリの取得連番・取得時刻と操作完了の順序を確認します。U04の`observe()`では要求前のFrameも有効なため、要求後の連番増加を成功条件にせず、取得状態と保存・応答の対応を確認します。キャプチャーデバイス内部の遅延を含む実際の映像時刻まで、アプリの時刻だけで保証することはできません。U05の実機確認では入力から画像へ反映される遅れも記録します。

入力完了後の最新キャッシュ採用と、既存の停止・符号化・保存の結合を検証します。映像の実機反映とPC側の取得順序は区別します。

M0では公開runtime 0.167.0のunsubscribe→同thread resumeで新MCP公開・旧要求拒否を確認し、実モデル2ターンの模擬act呼出しと固定画像・IDの回答まで成功しました。これはシリアル送出・ゲーム機解除・事後映像・製品GUI停止の受入ではありません。各protocolのファーム適合、baud、open時reset、通信失敗・最短入力・解除と映像反映はU05 M2に残します。

# GUIと並行処理の確認

[10のUI合意](10-ui-interaction.md)はU06・U07へ割り当てます。T07では共通Messageからの自由文回答・追加指示、目標トグルの下書き保持・送信受理、承認との区別を既存試験の書き換えで確認します。T08・T15では実通知との対応とpause／stopの効果を扱い、見出しや仮文言の不在だけを新規テストにしません。画面の読みやすさとGoalの識別は実画面で確認します。削除済み試験の一律復活は予約しません。

閲覧保持の専用試験19件はunit_030で削除済みです。U06 M1で新しい履歴へ追記しながら、選択・コピー、過去位置の維持、末尾だけの追従、reasoning表示切替、長文・長時間の表示を実Qt画面で確認し、結果を子仕様へ記録します。現存しない試験を検証手段に数えず、自動化が必要な代表条件は残るGUI試験への統合を先に検討します。U06 M2ではGoal操作・同一セッション再開、M3では設定変更と工程全体の結合を確認します。

PySide6のGUI試験にはU01で採用した`pytest-qt`を使います。U01の設定I/Oの試験を、SDK受信・サービス用ループ・機器ワーカーの検証として代用しません。SDKや機器の戻りを待っている状態でも、ウィンドウが更新され、停止を受け付けることを各追加工程で確認します。

プレビューは最新フレームを表示できればよく、表示し損ねた全フレームを蓄積しません。負荷をかけた結合試験では、プレビュー通知の滞留、操作要求の重複、終了時に残るスレッド・ポートを確認します。同一画像をUIとMCPが同時に使っても、片方の加工がもう片方へ混入しないことも対象にします。

待ち時間の検査には、テスト用時計やイベント同期を使います。固定時間だけ待って「おそらく処理済み」とする試験を増やしません。実時間の確認が必要な試験は、対象機器と測定値を結果へ残します。

# 実ランタイムと実機で確認する順序

本実装のCodex接続部について、公開APIと採用版の型・ソースを先に調べます。資料から確定する事項と、組み合わせを動かして確認する事項を分けます。Goalsや質問処理の公開経路に不足がある場合は、接続部の設計課題として記録し、アプリ外側へ無断で別の攻略計画機構を追加しません。

画像付きMCP応答は、画像データを返せたことだけで合格にしません。既知の固定画像を使い、モデルが画像を受け取れていることを短い応答で確認します。画像理解の一般的な精度を測る試験にはしません。

実機では、まず観測・短い入力・停止を確認し、その実装のまま短い依頼、複数ターンの継続、停止と再開へ広げます。最終的な受け入れ場面には以下を含めます。

| 場面 | 確認する結果 |
| --- | --- |
| プレイ途中で停止し、手動操作を挟んで再開 | 古い入力を捨て、現在画面から再計画します |
| アプリを再起動し、既存スレッドで再開 | 依頼と記録の対応を維持し、観測から続行します |
| 会話を引き継がず、新しいスレッドで再開 | `guide.md`と記憶、必要な原記録を読んで現在状況を組み直します |
| ゲームをリセットし、保存地点へ戻す | メモ上の進捗をそのまま実機の現在状態とみなさず、知識を利用して続行します |
| 依頼を完了する | 入力を終え、別スレッドで記憶整理を実行します |

最初の連続運転は一つの有意味な依頼を通し、その後に数時間の運転へ伸ばします。経過時間だけを合格条件にはしません。停止応答、操作と観測の整合、ログ量、メモリ使用量、再開できることを確認します。モデルの攻略失敗と、入力や状態管理の不具合を区別して記録します。

アプリを強制終了した場合、PC側の`finally`は実行されないことがあります。MCUが押下時間や通信断をどう扱うかを確認するまで、「プロセスが落ちても必ず解除される」とは記載しません。ソフトウェアの停止試験と、装置側で保持される入力の試験を分けます。

# 自動実行と手動実行

CIはWindowsを主対象にし、認証情報・実機を必要としない単体試験と結合試験を動かします。Linuxでは共通部分を追加確認できますが、Windows対応の代替にはしません。実ランタイムの認証、課金、コントローラー操作を伴う試験は明示的に実行し、通常の`pytest`で開始しない構成にします。

初期の試験配置は`tests/unit/`、`tests/integration/`、`tests/acceptance/`です。`acceptance`のうち実機を使うものは、対象デバイスと現在の画面を確認してから実行します。利用枠不足や承認待ちの分岐は、意図的な課金超過を起こさず、通知の固定データを用いた結合試験で検査します。

実行コマンドは[AGENTS.mdのテストと検証](../../AGENTS.md)から変更範囲に応じて選びます。依存変更時はロックファイル、配布変更時はビルドも確認します。文書だけの変更では、リンク・用語・記述の整合を確認し、無関係な製品試験の成功を文書品質の根拠にしません。

各作業仕様には、採用版、実行コマンド、結果、残る未確認事項を記載します。未実行と対象外を区別し、手動確認では機器構成・停止方法・観測した遅延や問題を残します。測っていない時間精度や停止時間に、数値の保証は置きません。
