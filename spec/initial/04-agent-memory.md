# 04-agent-memory.md — エージェントの動作・記憶

[文書一覧](README.md)

Codexが目標分解、画面の理解、攻略、記憶の読み書きを担います。アプリは指示を渡す入口と保存先を固定し、依頼・操作・応答・観測を原記録として残します。本書のファイル配置と最小項目は初期実装設計です。記憶の内容を細かな規則で管理する仕組みは作りません。

本書は保存・記憶の契約とイベント一覧の正本です。2026-11-11の工程改訂により、保存一式を映像取得より前に完成させる構成は採りません。U01で完成したグローバル設定のTOML保存と、プロジェクト・JSONL・画像保存は別の機能です。2026-11-12の[U04 M0](../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md)で観測保存の契約を決め、[M1](../complete/unit_032/RECORDED_OBSERVATION_IMPLEMENTATION.md)で独立した観測・保存APIを実装・検証しました。保存先GUI・MCP実接続・実機での観測保存はM2の未実施事項です。それ以後の保存・記憶機能は、最初に使う工程で調査・設計・実装・検証します。

# 指示を渡す単位

| 情報 | 渡す内容と管理者 |
| --- | --- |
| アプリ共通指示 | 実画面を観測して操作すること、ツールの意味、停止・質問の扱い、記録の場所をアプリが案内します |
| ゲームの情報 | タイトル、操作上の注意、既知の攻略情報などをプロジェクトの案内から参照します |
| プロジェクト | 保存先、現状メモ、過去の原記録、必要な補足知識を読みます |
| ユーザーの依頼 | 達成したい目的、制約、追加指示を会話とGoalへ渡します |

共通指示にFRLGの進行順やセーブ操作を書き込みません。ゲームの情報も毎ターンすべて再送せず、必要なファイルをCodexが選んで読みます。アプリが長い攻略ルールや外部の中期計画を生成する構成にはしません。

U04では、接続時に選択したプロジェクトの絶対パス、`events.jsonl`、`observations/`と観測IDの対応を、既存の`developerInstructions`経路で案内します。共通指示のテンプレートと個別情報は分離します。保存場所を伝えるためだけの`guide.md`や空の`memory/`は生成しません。U06で継続攻略の入口を提供するときに`guide.md`と`memory/current.md`を具体化します。現在画面とメモが食い違う場合は、画面を確かめて現状の記述を更新するよう伝えます。現在位置の誤りを理由に、有用な攻略知識を一括削除しません。

共通指示は`src/gigas/prompts/`に同梱し、アプリがパッケージリソースとして読み込みます。U06以後に使う案内テンプレートも同じ配布経路を使い、生成した案内と可変の記憶はプロジェクト側に置きます。ゲームをプレイするCodexの作業ディレクトリは開発リポジトリから分離し、開発用AGENTS.mdやSkillsを攻略へ混入させません。同梱・読込の確認方法は[06](06-repository.md)に従います。

U01では短い`play.md`の同梱と配布物からの読込を検証しました。製品側の取得・配送はU02から、観測先の案内はU04、継続攻略に使う記憶の入口と指示はU06、整理指示はU09で具体化します。指示の追加・変更時は、その利用経路と[07のT20](07-verification.md)を確認します。

# プロジェクトと保存先

プロジェクトは記憶・依頼・原記録のまとまりです。同一ゲーム・同一セーブで複数のプロジェクトを作れます。新規プロジェクトで「タケシ撃破後です。ハナダシティまで進めて」と指示しても、以前のプロジェクトの存在を必須にしません。既存の記憶を使う場合はそのプロジェクトを選びます。自動的なプロジェクト横断の記憶統合は初期範囲に入れません。

```text
project/
  project.json
  guide.md
  memory/
    current.md
    notes/
  events.jsonl
  observations/
```

| 保存物 | 内容と更新主体 |
| --- | --- |
| `project.json` | スキーマ版、プロジェクトID、表示名、ゲーム名、現在の依頼、ランタイム参照などをアプリが更新します |
| `guide.md` | 保存場所と読み方の短い入口です。アプリが生成・更新し、ゲーム知識は記憶側へ置きます |
| `memory/current.md` | 目的、最後に確かめた状態、次に試すこと、未解決事項などをCodexが更新します |
| `memory/notes/` | 必要になった知識や判断を含む手順をCodexが保存します。作成数や分類を事前に固定しません |
| `events.jsonl` | 依頼・追加指示・操作・公開応答・状態変化・観測参照をアプリが追記します |
| `observations/` | ツールがモデルへ返した観測画像を、観測IDと対応付けてアプリが保存します |

固定するのは入口と原記録の形式です。すべての知識ファイルを起動時に読むことや、詳細な索引を常に維持することは要求しません。記憶が増えて読みづらくなったときに、Codexがまとめ方を変えられる余地を残します。

上の配置は初期版全体の形です。各工程では実際に使用する項目とファイルを具体化し、使用しない管理項目や空の記憶資材を先に揃えません。

| 追加する機能 | 設計・実装する工程 | 最初に確認する契約 |
| --- | --- | --- |
| 最小プロジェクトと観測記録 | [U04](../wip/unit_009/RECORDED_OBSERVATION.md) | 保存先・ID・管理情報の作成と読込、画像とイベントの対応、既存データの保全、部分失敗 |
| 依頼・実行と操作記録 | [U05](../planned/unit_010/INPUT_AND_STOP.md) | 操作に必要な識別子、入力前の開始記録、完了・中断・失敗・結果不明の区別 |
| Goal・スレッド参照、記憶の入口 | [U06](../planned/unit_011/GOAL_EXECUTION.md) | 継続する依頼との対応、追加指示・公開応答、同一セッション再開の記録、既存記憶を保持した案内と読込 |
| 終了作業の記録・保存参照からの復帰 | [U07](../planned/unit_012/PLANNED_STOP.md)・[U08](../planned/unit_013/RESUME.md) | 元依頼と公開された作業報告の区別、未完記録とランタイム参照の読込。U06の再開経路を共用し、過去操作を再送しないこと |
| 整理の退避・復元と未完状態 | [U09](../planned/unit_014/MEMORY_MAINTENANCE.md) | 書き込みの排他・終了確認、追加・削除・改名を含む復元、再起動後の未完整理 |

保存するデータの追加時に、型・必須項目・ID生成・更新単位・失敗時の原本保持・読込方針を子仕様で決め、確定した契約を本書へ反映します。全イベントの詳細なpayloadを、記録元の設計より先に確定しません。各工程が同じ`storage`の実装を拡張し、保存方式を別々に複製しない方針です。

## U04の作成・読込契約

以下はM0で決め、M1で独立APIとして実装した契約です。接続中の保存先固定とGUIはM2で結合します。詳細な項目と失敗境界は[U04 M0](../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md)を参照します。

新規作成は、存在しない保存先ディレクトリを専有して作ります。`project.json`の必須項目は整数`schema_version: 1`、`project-`にUUIDを続けた`project_id`、UTCの`created_at`です。空の`events.jsonl`と`observations/`を作り、既存ディレクトリの取り込みや上書き初期化は行いません。表示名・ゲーム名・依頼・Goal・ランタイム参照は、その実体が必要になる工程まで追加しません。途中で作成に失敗した資材も無断で再初期化しません。

既存プロジェクトは原本を変更せず読み込みます。対応版の管理情報とJSONLの構文・共通項目・追記順を検査し、検査と書込所有権の取得が成功してから選択を切り替えます。既知の`observation.recorded`はpayloadの項目と観測IDに対応する相対パスを検査しますが、過去のPNGを全件読み込んで寸法や内容を検査することは要求しません。未知のイベント種別は共通形式が有効ならpayloadを解釈せず保持し、追記を妨げません。余剰フィールドも削除・再解釈しません。

未知のスキーマ版、不正なUTF-8・JSON・必須項目・追記順・相対パス、末尾の不完全行は、最初の問題箇所とその前の正常に読めた範囲を報告し、追記を拒否します。原記録を切り詰めたり、破損行より後の行を回復して追記を再開したりしません。部分読込専用の画面や復旧機構は作りません。

書込所有者は`storage`内の一つに限定し、WindowsのOSファイルロックで別アプリからの同時書込も拒否します。外部編集の監視・競合解決や自動修復は提供しません。Codex接続中は選択プロジェクトを固定し、保存先の変更には既存の切断操作を使います。保存先の新規作成・読込と既存の通知詳細で操作・失敗を扱い、観測用の説明パネルや状態表示は追加しません。

観測は同時1件とし、符号化と保存を一つの処理として実行します。M1ではワーカー処理の投入を開始点とし、投入前なら取消し、投入後は途中の保存工程ごとに中断せず、完了または失敗を回収します。スレッドの実行開始を別状態で監視しません。要求が取り消されていた場合は応答を送らず、保存できた記録は保持します。保存完了は配送完了の意味ではありません。実際の処理が収束するまで旧書込所有者とロックを保持し、新しい保存先への切替・次の書込・正常終了の確定を待たせます。終了を確認できなければ成功扱いにせず、自動再試行しません。

グローバル設定はこのディレクトリの外に置きます。キャプチャーデバイス、入力接続先、モデル・エフォートの既定値、認証方式はアプリ共通です。保存する既定値と会話中の選択を分ける契約は[02](02-runtime.md)に定めます。APIキーやHTTP認証情報を記憶・イベントへ保存しません。認証情報はCodexランタイムが管理し、アプリは資格情報を複製しません。APIキー方式の実接続はU06までに確認します。

グローバル設定の形式は、人間による編集を考慮したTOMLです。U01で現在の5項目・保存先・コメントを保持する更新を実装しました。接続先の有効性や認証は保存だけでは確認しません。プロジェクトの`project.json`と原記録のJSONLは、この設定保存機能に含まれません。

初期開発中のグローバル設定は破壊的変更を許容し、旧形式との互換性を担保しません。設定の版番号、旧キーの別名対応、自動移行は設けず、必要に応じて利用者が設定を編集・再作成します。現在の項目の型検証と、読込失敗時に原本を無断で初期化しない扱いは維持します。手編集はアプリ終了中に行い、起動中の外部編集の検出・競合解決は初期範囲に含めません。

# 現状メモと原記録の関係

`memory/current.md`は再開時に短く読める現状の要約です。「目的」「確認した状態」「次の行動」「未解決事項」を初期テンプレートに使えますが、モデルの出力をその見出しへ厳密に制約しません。重要な見立てには、確かめた時点や参照した観測を残せるようにします。

推測を確定状態として扱わないこと、食い違いに気付いたら原記録を確認することを共通指示で伝えます。迷った際の行動はCodexへ任せます。例えば、操作列を短くする、新しく観測する、過去の試行を検索する、攻略情報を調べる、ユーザーへ質問する、といった選択です。アプリ側にゲームごとの迷走判定器や、失敗回数に応じた攻略分岐を実装しません。

同じ画面を何度も観測したことだけでは、迷走と断定できません。長時間運転で同じ失敗の反復が実際に起きた場合は、その記録から指示・記憶・ツールのどこを直すか判断します。初期版で一般的なループ検知を完成させることは要件にしません。

再利用するのは短い固定操作列と、画面を確認しながら進める手順です。初期版の手順は記憶として参照し、必要な操作列をその都度ツールへ渡します。攻略用Skillsの自動生成・登録・更新を組み込みません。

# 検索可能なイベントログ

イベントはアプリ側の一つの書き込み口でJSONLへ追記します。app-server固有の生イベントを唯一の記録形式にせず、依頼・操作・応答をランタイムに依存しない項目へ写します。CodexのスレッドIDなどは任意の付加情報にできます。U04で確定した共通項目は次のとおりです。

| 項目 | 契約 |
| --- | --- |
| `schema_version` | 整数`1` |
| `event_id` | `evt-`にUUIDを続けた、再起動後も重複させない識別子 |
| `sequence` | プロジェクト内の正整数の追記順。空のログでは1、それ以外では正常に読み込んだ末尾の値＋1を使う。読込は前の値より大きいことを確認し、欠番だけでは拒否しない。時刻で並べ替えない |
| `occurred_at` | この観測記録を作る時点のUTC。元Frameの取得時刻とは分ける |
| `type` | U04では`observation.recorded` |
| `project_id` | 選択した`project.json`と同じID |
| `payload` | 下記の観測・画像・元Frameの対応 |

`task_id`・`run_id`・`operation_id`は対応する実体がある場合に記録し、U04では生成しません。この共通形式と観測payloadはM1の保存・再読込試験で確認しています。後続のイベントは未実装です。

観測payloadは`observation_id`、`captured_at`、`image_path`、`source_frame`、`analysis`とします。`observation_id`は`obs-`にUUIDを続けた永続識別子、`captured_at`は元FrameのUTC、`image_path`は`observations/<observation_id>.png`形式のプロジェクト相対パスです。`source_frame`には元Frameの`generation`・`sequence`・`width`・`height`を保存し、`analysis`は空オブジェクト`{}`とします。取得世代と連番はサービス寿命内の補助情報であり、アプリ再起動後も一意なFrame識別子としては扱いません。

スキーマ版1の観測画像は、元Frameの寸法を保った、空間的な加工のないPNGと定義します。画像の出力寸法や変換オブジェクトを重ねて記録せず、取得サービス用UUID、単調時計、画像hash、符号化容量の保存も必須にしません。プレビューの拡縮・黒帯・引き延ばしを持ち込まず、観測のために取得設定を変更しません。符号化後の上限は32 MiBとし、超えた画像を暗黙に縮小・切り抜きして返しません。上限はアプリの資源制約であり、Codexで32 MiBの画像応答を受け取れることを実接続確認した値ではありません。

保存とMCP応答には一度だけ符号化した同じbytesを使います。画像を同階層の一時ファイルへ書き込み、flush・fsync後に既存ファイルを上書きしない方法で確定します。その後、JSONLへ改行で終わる一行を追記し、flush・fsyncが成功した場合だけ、同じ画像と観測IDを成功応答に載せます。画像とJSONLをまとめた原子的更新や、電源断の瞬間までの永続化を保証するものではありません。

符号化や画像保存の失敗でJSONLへまだ追記していない場合は、その観測を失敗として返します。既存ログの追記位置は変わらないため、それだけで書込所有者を使用不能にしません。当該処理が作った未公開の一時ファイルは削除できますが、既存資材や公開済みPNGは削除しません。

画像確定後にJSONLの追記・flush・fsyncが失敗し、追記結果が不明になった場合は、原記録・画像を保全して書込所有者の追記を止めます。明示的な再読込検査が成功するまで次の採番・追記を行わず、不完全行が残れば追記不可のままです。未参照の公開済み画像を自動削除したり、完全な記録へ自動昇格したりしません。保存完了後に応答の配送だけが失敗した場合も記録を保持し、配送成功と混同せず、自動再観測・自動再送を行いません。

イベント一覧は次の表を正本とし、子仕様が具体的な種類名・必須payload・失敗時の扱いを確定したら本書と対応する試験へ反映します。以下は必要な記録の意味・記録元・利用者・追加時期であり、未実装イベントのスキーマを検証済みとする一覧ではありません。既存項目の意味を変える場合はスキーマ版を更新します。

| 記録する意味 | 記録元 | 利用する箇所 | 具体化する工程 |
| --- | --- | --- | --- |
| 観測画像・取得時刻・参照 | ゲームI/Oから保存管理 | MCP応答との対応、Codexの原記録参照 | U04 |
| 依頼・実行の開始、操作要求・開始・結果 | 実行管理、ゲームI/Oから保存管理 | 入力前の記録確認、操作と観測の対応、未完操作の識別 | U05 |
| Goal・ターン・計画・公開応答・質問・承認 | Codex接続部、実行管理から保存管理 | 表示、依頼・ランタイム参照、記憶と再開 | U06。U02の接続試験の診断記録とは区別 |
| 追加指示の受付・配送・未適用、依頼完了 | 実行管理から保存管理 | 二重配送防止、完了後の未適用表示、整理対象の範囲 | U06 |
| 追加指示による終了作業の記録 | 共通のユーザー入力・公開応答・Goal／ターン記録 | 元依頼の保持、作業報告と確認済み結果の区別、後日の再開。本文分類や専用イベントは前提にしない | U07で既存記録との対応を確認し、不足する記録だけを追加 |
| 再開要求・採用した記憶と参照・結果 | 実行管理から保存管理 | 再開の識別、旧実行との区別 | U06で同一セッション再開の記録。U08で保存参照・再起動後の読込と復帰を追加 |
| 整理開始・正常採用・失敗・復元結果 | 実行管理と保存管理 | 再起動後の未完整理、次の攻略を許可する判断 | U09 |

停止・失敗の記録は、それを発生させる各工程で追加します。U05の入力停止を、U07の計画的終了やU09の復元結果の記録が完成するまで待たせません。

ユーザー入力は本文と受付・配送・未適用の結果を記録します。操作は要求された列、受付、開始、完了または中断・失敗を関連付けます。エージェント応答は公開された本文・計画・質問を記録し、内部推論全文や認証情報の採取を目的にしません。観測は画像と時刻を保存し、プレビューの全フレームは記録しません。

操作を始める前に開始記録を書き、操作後の結果記録がない場合は未確認として扱います。PC停止の瞬間までの永続化や、実機への一回だけの配送を保証するものではありません。復旧時に未完記録を見つけても、その操作を自動再実行しません。末尾の不完全なJSONL行などがあれば、破損箇所を識別して原記録を残し、読み取れた範囲を使います。正常な記録を無言で切り捨てる復旧は行いません。

初期版の検索はCodexのファイル読み取り・検索機能を使います。場所と形式が分かれば、別のランタイムでも同じ記録を読めます。専用の検索APIやデータベース、抽象化のためだけのfacadeは必須にしません。JSONLが大きくなって実際に読みづらくなった段階で、項目を絞って読む機能を追加するか判断します。

# 攻略とは別スレッドで行う記憶整理

Dreamingに着想を得た整理処理を設けます。過去のやり取りをそのまま積み上げるだけでなく、役立つ知識を短くまとめ、古い見立てや重複を整理するための処理です。特定製品のDreaming機能そのものを搭載するという意味ではありません。

起動契機はユーザー依頼の完了後と、明示的な「記憶を整理」操作です。単一ターンの終了、計画的終了、時間経過だけでは起動しません。初期UIの手動実行は、攻略が動いていないときに限る設計とします。より高頻度の起動は運用後の拡張候補です。

整理用の別スレッドへ、プロジェクトの案内、現状メモ、対象となる原記録の範囲を渡します。ゲームMCPと攻略Goalは渡しません。目的は記憶の編集であり、実機の操作やゲーム内セーブを行いません。モデル・エフォートは初期版ではアプリ共通の既定値を使います。攻略の会話内だけで変更した選択とは区別し、整理開始時の確定方法はU09で具体化します。

同じMarkdownへ攻略側と整理側が同時に書き込まないよう、実行管理で排他します。整理前に、攻略側の書き込みが終わった時点の`memory/`一式を退避します。退避に失敗した場合は整理を開始しません。**整理が失敗・中断した場合は、整理側の書き込み終了を確認してから、アプリが退避した記憶へ戻し、復元完了後に次の攻略を許可します。** 中途半端な整理結果をそのまま採用する選択肢は初期版に設けません。

復元は既存ファイルの上書きだけではなく、整理で追加・削除・改名されたファイルも含め、`memory/`を整理前の構成へ戻します。依頼の完了記録、`events.jsonl`、観測画像は巻き戻しません。これらは整理の対象としても書き換えません。これはアプリの運用上の分担であり、ファイル権限による完全な隔離が既に実現しているという主張ではありません。

整理の実行中であることと退避先をアプリが永続化し、正常終了または復元の完了まで保持します。アプリ再起動時にも整理の正常終了が確定していなければ、同じ復元手順を適用します。整理側の書き込み終了、退避データ、復元のいずれかを確認できなければ、次の攻略を開始・再開せずに理由を表示します。退避先は復元対象の`memory/`から分離します。退避形式・管理情報の配置・ファイル切替・復元中の失敗からの再試行は、U09の冒頭で整理の起動・排他・終了待ちと一緒に設計します。汎用的な履歴管理機構は作りません。

この整理契約はU09で提供します。それより前の段階では依頼完了後に停止・次の依頼待ちへ進み、自動整理を実装済みとして表示しません。U09ではU06〜U08の完了・開始・再開経路へ整理と復元の条件を接続します。

整理の正常終了時は整理後の記憶を採用し、失敗・中断時は整理前へ復元した記憶を採用します。次の攻略では、その採用した現状メモを読み直します。同じ攻略スレッドを再利用する場合も、別スレッドによる更新や復元が自動的に会話へ反映されたとは扱いません。整理に失敗しても、完了したユーザー依頼を未完へ戻しません。復元完了は攻略の自動開始を意味せず、開始・再開のユーザー操作は別に必要です。

# コンテキストと再開

スレッドは会話・ツール実行の履歴をまとめる単位です。モデルに入るコンテキストは有限で、必要に応じて圧縮されます。スレッドの再開は、すべての過去の画像や記述が常にモデルへ残ることを意味しません。記憶と原記録はスレッド履歴とは独立して保持します。

アプリ再起動後や新しいスレッドでは、対象の依頼、`guide.md`、`memory/current.md`と新しい観測を入口にします。必要な経緯は原記録や補足メモを調べます。ゲームがリセットされていれば実際の画面に合わせて現状を訂正します。アプリ側の再開とゲーム内セーブからの復帰を同一視しません。

Claude Codeなどへの移行時に引き継ぐ対象は、このプロジェクトのファイルと未完の依頼です。Codex固有の会話・Goal・圧縮状態を他のランタイムへ変換する機能は初期版の対象外です。
