# 04-agent-memory.md — エージェントの動作・記憶

[文書一覧](README.md)

Codexが目標分解、画面の理解、攻略、記憶の読み書きを担います。アプリは指示を渡す入口と保存先を固定し、依頼・操作・応答・観測を原記録として残します。本書のファイル配置と最小項目は初期実装設計です。記憶の内容を細かな規則で管理する仕組みは作りません。

本書は保存・記憶の契約とイベント一覧の正本です。2026-11-11の工程改訂により、保存一式を映像取得より前に完成させる構成は採りません。U01で完成したグローバル設定のTOML保存と、プロジェクト・JSONL・画像保存は別の機能です。2026-11-12の[U04 M0](../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md)で観測保存の契約を決め、[M1](../complete/unit_032/RECORDED_OBSERVATION_IMPLEMENTATION.md)で独立した観測・保存APIを実装・検証しました。[M2](../complete/unit_035/MCP_OBSERVATION_INTEGRATION.md)ではプロジェクト操作・非同期保存・永続threadとの対応・製品MCPを結合し、固定Frameを用いた実モデル配送と保存画像の後参照を確認しました。ネイティブダイアログによる作成・読込、通常終了と再起動後の選択復元も確認済みです。WindowsのUSB Video Deviceを使う未選択チャットでも、実映像の観測・保存と実画面での応答性・通常終了を確認しました。それ以後の保存・記憶機能は、最初に使う工程で調査・設計・実装・検証します。

2026-11-12の[チャット・観測・永続化の改訂](../complete/unit_034/CHAT_OBSERVATION_PERSISTENCE.md)で、保存完了前のMCP応答、未選択チャットの記録先、通常会話の永続化を採用した。M2では未完成ユニットの保存形式を新契約へ直接変更し、旧形式識別・移行・互換対応を設けない。部分失敗の保全は維持する。保存開始・完了・進行状況でMCP応答や次の観測を待たせず、保存見送り・キュー・保持上限も先に仕様化しない。応答直後のファイル参照や異常終了時に画像が欠ける制約を受け入れ、保存失敗はID付きの既存通知・詳細で確認できるようにする。

プロジェクトは任意の記憶・会話のまとまり、チャットは実thread、記録先は必須の実フォルダーとして分ける。未選択時の新規チャットはアプリデータ配下chats/に通常と同じ記録を保持する。M2は永続threadと保存先の対応を残し、採用runtimeの再起動後に公開`thread/read(includeTurns=true)`で実会話の2ターンを取得できることを確認した。同じ接続の次ターンでは、観測を再実行せず保存PNGを`imageView`で開き直し、画像中の英数字と観測IDを回答できた。これはアプリの会話再開UIやU08の復帰機能の完成を意味しない。可搬な公開会話JSONLはU06で追加するため、M2で記録先フォルダーだけをコピーして会話全文を移せるとはしない。画像・記憶・公開会話をCodex以外へ引き継ぐ最終要件は維持する。

# 指示を渡す単位

| 情報 | 渡す内容と管理者 |
| --- | --- |
| アプリ共通指示 | 実画面を観測して操作すること、ツールの意味、停止・質問の扱い、記録の場所をアプリが案内します |
| ゲームの情報 | タイトル、操作上の注意、既知の攻略情報などをプロジェクトの案内から参照します |
| プロジェクト | 保存先、現状メモ、過去の原記録、必要な補足知識を読みます |
| ユーザーの依頼 | 達成したい目的、制約、追加指示を会話とGoalへ渡します |

共通指示にFRLGの進行順やセーブ操作を書き込みません。ゲームの情報も毎ターンすべて再送せず、必要なファイルをCodexが選んで読みます。アプリが長い攻略ルールや外部の中期計画を生成する構成にはしません。

U04では、チャットの原記録先（選択プロジェクトまたはアプリ管理先）の絶対パス、`events.jsonl`、`observations/`と観測IDの対応を、既存の`developerInstructions`経路で案内します。共通指示のテンプレートと個別情報は分離します。保存場所を伝えるためだけの`guide.md`や空の`memory/`は生成しません。U06で継続攻略の入口を提供するときに`guide.md`と`memory/current.md`を具体化します。現在画面とメモが食い違う場合は、画面を確かめて現状の記述を更新するよう伝えます。現在位置の誤りを理由に、有用な攻略知識を一括削除しません。

共通指示は`src/gigas/prompts/`に同梱し、アプリがパッケージリソースとして読み込みます。U06以後に使う案内テンプレートも同じ配布経路を使い、生成した案内と可変の記憶はプロジェクト側に置きます。ゲームをプレイするCodexの作業ディレクトリは開発リポジトリから分離し、開発用AGENTS.mdやSkillsを攻略へ混入させません。同梱・読込の確認方法は[06](06-repository.md)に従います。

U01では短い`play.md`の同梱と配布物からの読込を検証しました。製品側の取得・配送はU02から、観測先の案内はU04、継続攻略に使う記憶の入口と指示はU06、整理指示はU09で具体化します。指示の追加・変更時は、その利用経路と[07のT20](07-verification.md)を確認します。

# プロジェクトと保存先

プロジェクトは記憶・依頼・原記録のまとまりです。同一ゲーム・同一セーブで複数のプロジェクトを作れます。新規プロジェクトで「タケシ撃破後です。ハナダシティまで進めて」と指示しても、以前のプロジェクトの存在を必須にしません。既存の記憶を使う場合はそのプロジェクトを選びます。自動的なプロジェクト横断の記憶統合は初期範囲に入れません。

```text
project/
  project.json
  guide.md
  memory/
    current.md
    notes/
  events.jsonl
  observations/
```

| 保存物 | 内容と更新主体 |
| --- | --- |
| `project.json` | スキーマ版、プロジェクトID、表示名、ゲーム名、現在の依頼、ランタイム参照などをアプリが更新します |
| `guide.md` | 保存場所と読み方の短い入口です。アプリが生成・更新し、ゲーム知識は記憶側へ置きます |
| `memory/current.md` | 目的、最後に確かめた状態、次に試すこと、未解決事項などをCodexが更新します |
| `memory/notes/` | 必要になった知識や判断を含む手順をCodexが保存します。作成数や分類を事前に固定しません |
| `events.jsonl` | 依頼・追加指示・操作・公開応答・状態変化・観測参照をアプリが追記します |
| `observations/` | ツール出力と同じ観測画像を、観測IDと対応付けてアプリが非同期保存します。保存成功と配送成功は区別します |

固定するのは入口と原記録の形式です。すべての知識ファイルを起動時に読むことや、詳細な索引を常に維持することは要求しません。記憶が増えて読みづらくなったときに、Codexがまとめ方を変えられる余地を残します。

上の配置は初期版全体の形です。各工程では実際に使用する項目とファイルを具体化し、使用しない管理項目や空の記憶資材を先に揃えません。

| 追加する機能 | 設計・実装する工程 | 最初に確認する契約 |
| --- | --- | --- |
| 最小プロジェクトと観測記録 | [U04](../complete/unit_009/RECORDED_OBSERVATION.md) | 保存先・ID・管理情報の作成と読込、画像とイベントの対応、既存データの保全、部分失敗 |
| 依頼・実行と操作記録 | [U05](../complete/unit_010/INPUT_AND_STOP.md) | 操作に必要な識別子、入力前の開始記録、完了・中断・失敗・結果不明の区別 |
| Goal・スレッド参照、記憶の入口 | [U06](../planned/unit_011/GOAL_EXECUTION.md) | 継続する依頼との対応、追加指示・公開応答、同一セッション再開の記録、既存記憶を保持した案内と読込 |
| 終了作業の記録・保存参照からの復帰 | [U07](../planned/unit_012/PLANNED_STOP.md)・[U08](../planned/unit_013/RESUME.md) | 元依頼と公開された作業報告の区別、未完記録とランタイム参照の読込。U06の再開経路を共用し、過去操作を再送しないこと |
| 整理の退避・復元と未完状態 | [U09](../planned/unit_014/MEMORY_MAINTENANCE.md) | 書き込みの排他・終了確認、追加・削除・改名を含む復元、再起動後の未完整理 |

保存するデータの追加時に、型・必須項目・ID生成・更新単位・失敗時の原本保持・読込方針を子仕様で決め、確定した契約を本書へ反映します。全イベントの詳細なpayloadを、記録元の設計より先に確定しません。各工程が同じ`storage`の実装を拡張し、保存方式を別々に複製しない方針です。

## U04の作成・読込契約

ファイル形式と原本保全はM1で実装済みです。非待機保存・チャットとの対応、以下のUI契約をM2で製品へ結合し、模擬runtimeと実HTTP/Qtで検証しました。実モデルでは未選択チャットの観測・原記録保存・後参照を確認しました。通常権限のネイティブ画面でも新規作成・読込、タイトルの保存先表示、TOMLへの前回選択保存、再起動後の復元、正常終了後の別writerによる再読込を確認しました。USB Video Deviceの実映像でも未選択チャットから観測し、MCP応答と保存画像・観測IDの一致、終了後の原記録の再読込を確認しました。「プロジェクト」メニューの「新規作成」「開く」と接続中の選択固定を使います。未選択時もアプリ管理の永続記録先をチャットに用意し、ゲームMCP経由で観測できます。最後に選択に成功したパス一件を既存のアプリ設定へ保存し、起動時に検査・専有して選択を復元します。復元失敗時は未選択で起動し、既存の通知・詳細へ理由を残します。会話・Goalの自動再開は含めません。未選択チャットの記録はTEMPではなく終了後も保持します。詳細な項目と失敗境界は[U04 M0](../complete/unit_031/RECORDED_OBSERVATION_DESIGN.md)と[M2](../complete/unit_035/MCP_OBSERVATION_INTEGRATION.md)を参照します。

新規作成は、存在しない保存先ディレクトリを専有して作ります。`project.json`の必須項目は整数`schema_version: 1`、`project-`にUUIDを続けた`project_id`、UTCの`created_at`です。空の`events.jsonl`と`observations/`を作り、既存ディレクトリの取り込みや上書き初期化は行いません。表示名・ゲーム名・依頼・Goal・ランタイム参照は、その実体が必要になる工程まで追加しません。途中で作成に失敗した資材も無断で再初期化しません。

既存プロジェクトは原本を変更せず読み込みます。対応版の管理情報とJSONLの構文・共通項目・追記順を検査し、検査と書込所有権の取得が成功してから選択を切り替えます。既知の`observation.recorded`はpayloadの項目と観測IDに対応する相対パスを検査しますが、過去のPNGを全件読み込んで寸法や内容を検査することは要求しません。未知のイベント種別は共通形式が有効ならpayloadを解釈せず保持し、追記を妨げません。余剰フィールドも削除・再解釈しません。

未知のスキーマ版、不正なUTF-8・JSON・必須項目・追記順・相対パス、末尾の不完全行は、最初の問題箇所とその前の正常に読めた範囲を報告し、追記を拒否します。原記録を切り詰めたり、破損行より後の行を回復して追記を再開したりしません。部分読込専用の画面や復旧機構は作りません。

アプリが現在の原記録先のwriterを一つ所有します。MCPは取得結果を返し、アプリ側の記録処理がwriterを使います。WindowsのOSファイルロックは、同じ規約を使う別アプリのwriter取得を拒否します。`project.json`・`events.jsonl`・`observations/`はアプリが管理し、開いている間に別経路で編集しません。このプロセスロック自体は同じアプリ内の並列保存を禁止しません。画像ごとの書込は並列化でき、共有JSONLの採番・追記は整合性を守ります。保存全体を直列にするか並列にするかは実装上の選択です。この排他は原記録の読取やCodexによる`memory/`編集を禁止せず、ファイル権限による完全な隔離でもありません。外部編集の監視・競合解決や自動修復は提供しません。Codex接続中は選択プロジェクトを固定し、保存先の変更には既存の切断操作を使います。接続終了はプロジェクト終了ではありません。接続時の観測サービスをdrainした後も、選択が続く間はwriterを保持します。保存先の切替・アプリ終了で原記録処理が収束した後に解放します。保存先の新規作成・読込と既存の通知詳細で操作・失敗を扱い、観測用の説明パネルや状態表示は追加しません。

M2では加工・符号化済みObservationをアプリへ渡した後、保存完了を待たず応答します。保存中・保存失敗・滞留時も次の観測を妨げません。保存見送り・キュー・保持上限は先行設計せず、実際の必要性から判断します。引受け済み保存は配送取消しと独立して回収し、実処理の終了前にwriterを閉じません。保存先切替と正常終了は回収後とし、保存成功・処理終了・終了未確認を区別します。詳細は[改訂契約](../complete/unit_034/CHAT_OBSERVATION_PERSISTENCE.md)を参照します。

グローバル設定はこのディレクトリの外に置きます。キャプチャーデバイス、入力接続先、モデル・エフォートの既定値、認証方式はアプリ共通です。保存する既定値と会話中の選択を分ける契約は[02](02-runtime.md)に定めます。APIキーやHTTP認証情報を記憶・イベントへ保存しません。認証情報はCodexランタイムが管理し、アプリは資格情報を複製しません。APIキー方式の実接続はU06までに確認します。

グローバル設定の形式は、人間による編集を考慮したTOMLです。U01で当時の5項目・保存先・コメントを保持する更新を実装し、U04で追加した観測解像度・前回プロジェクトの設定も同じ保存経路で扱います。接続先の有効性や認証は保存だけでは確認しません。プロジェクトの`project.json`と原記録のJSONLは、この設定保存機能に含まれません。

初期開発中のグローバル設定は破壊的変更を許容し、旧形式との互換性を担保しません。設定の版番号、旧キーの別名対応、自動移行は設けず、必要に応じて利用者が設定を編集・再作成します。現在の項目の型検証と、読込失敗時に原本を無断で初期化しない扱いは維持します。手編集はアプリ終了中に行い、起動中の外部編集の検出・競合解決は初期範囲に含めません。

# 現状メモと原記録の関係

`memory/current.md`は再開時に短く読める現状の要約です。「目的」「確認した状態」「次の行動」「未解決事項」を初期テンプレートに使えますが、モデルの出力をその見出しへ厳密に制約しません。重要な見立てには、確かめた時点や参照した観測を残せるようにします。

推測を確定状態として扱わないこと、食い違いに気付いたら原記録を確認することを共通指示で伝えます。迷った際の行動はCodexへ任せます。例えば、操作列を短くする、新しく観測する、過去の試行を検索する、攻略情報を調べる、ユーザーへ質問する、といった選択です。アプリ側にゲームごとの迷走判定器や、失敗回数に応じた攻略分岐を実装しません。

同じ画面を何度も観測したことだけでは、迷走と断定できません。長時間運転で同じ失敗の反復が実際に起きた場合は、その記録から指示・記憶・ツールのどこを直すか判断します。初期版で一般的なループ検知を完成させることは要件にしません。

再利用するのは短い固定操作列と、画面を確認しながら進める手順です。初期版の手順は記憶として参照し、必要な操作列をその都度ツールへ渡します。攻略用Skillsの自動生成・登録・更新を組み込みません。

# 検索可能なイベントログ

イベントはアプリ側の一つの書き込み口でJSONLへ追記します。app-server固有の生イベントを唯一の記録形式にせず、依頼・操作・応答をランタイムに依存しない項目へ写します。CodexのスレッドIDなどは任意の付加情報にできます。U04で確定した共通項目は次のとおりです。

| 項目 | 契約 |
| --- | --- |
| `schema_version` | 整数`1` |
| `event_id` | `evt-`にUUIDを続けた、再起動後も重複させない識別子 |
| `sequence` | プロジェクト内の正整数の追記順。空のログでは1、それ以外では正常に読み込んだ末尾の値＋1を使う。読込は前の値より大きいことを確認し、欠番だけでは拒否しない。時刻で並べ替えない |
| `occurred_at` | このイベント記録を作る時点のUTC。元Frameの取得時刻とは分ける |
| `type` | U04では`thread.started`または`observation.recorded` |
| `project_id` | 原記録先の`project.json`と同じID。未選択チャットにも存在する |
| `payload` | 下記のthread対応、または観測・画像・元Frameの対応 |

`task_id`・`run_id`・`operation_id`は対応する実体がある場合に記録し、U04では生成しません。共通形式と観測payloadはU04 M1で、加工後の画像情報とthread対応はU04 M2で保存・再読込を確認しています。`thread.started`のpayloadは`runtime: "codex"`と実`thread_id`です。この記録が成功するまで最初のターンを始めません。操作イベントはU05 M1で追加しました。Goal・公開会話のイベントは後続工程で追加します。

観測payloadは`observation_id`、`captured_at`、`image_path`、`image`、`source_frame`とし、チャットからの観測には実`thread_id`も記録します。単独APIからの観測に架空のthreadを作りません。`observation_id`は`obs-`にUUIDを続けた永続識別子、`captured_at`は元FrameのUTC、`image_path`は`observations/<observation_id>.png`形式の記録先相対パスです。`image`には`mime_type: "image/png"`と出力`width`・`height`、`source_frame`には元Frameの`generation`・`sequence`・`width`・`height`を保存します。取得世代と連番はサービス寿命内の補助情報であり、アプリ再起動後も一意なFrame識別子としては扱いません。

未使用の予約欄だった`analysis`は生成せず、解析結果を後から埋める欄も作りません。旧形式の余剰項目の扱いはM1の実装履歴であり、開発途中データとの互換対応を追加・維持する要件にはしません。

観測画像の保存形式は、加工・符号化済みPNG・形式・出力寸法と元Frameの情報を区別する新契約へ直接変更します。未完成ユニットなので旧形式の識別・移行・開発途中データとの互換性維持は設けません。既存資材を無断で削除・上書きせず、現行形式に対する検証と部分失敗時の保全は維持します。PNG上限32 MiBは一枚の画像に対する既存の安全限界であり、保存キューや保持容量の上限ではありません。取得サービスUUID・単調時計・画像hash・汎用変換リストは必須にしません。

保存とMCP応答には一度だけ符号化した同じbytesを使います。画像を同階層の一時ファイルへ書き込み、flush・fsync後に既存ファイルを上書きしない方法で確定します。その後、JSONLへ改行で終わる一行を追記し、flush・fsyncします。この保存処理の完了はMCP応答の前提にせず、完全な結果の所有をアプリへ渡した後、応答と保存を独立して進めます。画像とJSONLをまとめた原子的更新や、電源断の瞬間までの永続化を保証するものではありません。

符号化失敗は観測失敗、画像保存の失敗は観測結果と別の記録失敗として扱います。JSONLへまだ追記していない場合、既存ログの追記位置は変わらないため、それだけで書込所有者を使用不能にしません。当該処理が作った未公開の一時ファイルは削除できますが、既存資材や公開済みPNGは削除しません。

画像確定後にJSONLの追記・flush・fsyncが失敗し、追記結果が不明になった場合は、原記録・画像を保全して書込所有者の追記を止めます。明示的な再読込検査が成功するまで次の採番・追記を行わず、不完全行が残れば追記不可のままです。未参照の公開済み画像を自動削除したり、完全な記録へ自動昇格したりしません。保存完了後に応答の配送だけが失敗した場合も記録を保持し、配送成功と混同せず、自動再観測・自動再送を行いません。

停止・失敗の記録は、それを発生させる各工程で追加します。U05の入力停止を、U07の計画的終了やU09の復元結果の記録が完成するまで待たせません。

U05の入力サービスは依頼にrequest_id、その実行にrun_id、受け付けた操作列にoperation_idを発行します。Goalのtask_idは生成しません。イベントはinput.run_started / input.operation_started / input.operation_finished / input.run_finishedです。run・操作の開始と終端は同じ記録窓口へ順に非同期投入する。保存完了を入力開始の前提にせず、保存失敗でも入力を止めない。記録が欠けたまま操作される場合を許容し、失敗は診断へ残す。操作記録のresultは入力列の実行結果を示す。入力完了後の観測失敗・応答取消しでもcompletedを維持し、phase=observeと理由を添える。要求全体のcodeとは区別し、正常に返せた画像だけobservation_idを対応付ける。操作内容・実行結果・観測IDを中心に記録し、port・baud・protocolは通常イベントへ含めません。結果行に確定したobservation_idを持たせてU04の観測イベント・PNGへ結び付け、Observation本体へ操作状態を複製しません。開始行だけがある操作は結果不明であり、入力済みとも未入力とも断定せず再送しません。[U05 M1](../complete/unit_038/INPUT_EXECUTION_AND_OBSERVATION.md)で型・writer・入力サービスを実装し、保存と再読込を模擬入力で確認しました。通常送信・MCPへの配線はM2です。

同じwriterへの記録は共通窓口で順序化します。入力は保存の排他区間へ含めません。run・操作の開始と終端は同じ記録窓口へ順に非同期投入する。保存完了を入力開始の前提にせず、保存失敗でも入力を止めない。記録が欠けたまま操作される場合を許容し、失敗は診断へ残す。通常終了・保存先変更は引受け済み保存のdrain後とします。

保存済み入力列は共通入力の形式・値域だけを検査し、現在対応するprotocolの能力では再検査しません。実行受付では選択したprotocolの能力を検査します。開始済みwriteが全byte成功した場合は、press・neutralとも停止後の結果回収で送出済みと記録します。実turn IDはrun開始後に判明した時点で対応付け、以後の操作開始・run終端記録へ使います。古いrunの通知で現在の文脈や操作権を変更しません。

観測の原画像・ID・取得時刻は、加工・符号化済みObservationから非同期保存します。ここで原画像はagentへ渡す画像の原本であり、元解像度画像の別保存は対象外です。保存完了をMCP応答の前提にせず、Codexの解釈も待ちません。Codexが解釈した公開応答・対話履歴は、実際に受信した内容をアプリが後から別記録として保存し、必要な観測IDや会話参照との対応はU06で定めます。Codexの解釈完了まで原観測の保存を保留したり、原観測を解釈結果で更新したりしません。対話記録も同じアプリ所有のwriterを使い、共有JSONLの採番・追記の整合性を守り、観測のBUSYを履歴の破棄条件にしません。通知順・失敗・終了との結合はU06で確定し、今回そのためだけのキューや汎用イベントAPIを先行実装しません。現在のCodex接続はread-onlyであり、memoryの実書込権限はU06の確認事項です。

ユーザー入力は本文と受付・配送・未適用の結果を記録します。操作は要求された入力列と指定時間、実行結果、完了要素数、観測IDを関連付けます。中断・失敗時は理由・入力送出状況・解除結果を残します。port・baud・protocolなどの接続情報は通常のrun・操作記録に含めず、通信障害の調査に必要な場合だけ診断ログで扱います。エージェント応答は公開された本文・計画・質問を記録し、内部推論全文や認証情報の採取を目的にしません。観測は画像と時刻を保存し、プレビューの全フレームは記録しません。

操作を始める前に開始記録を書き、操作後の結果記録がない場合は未確認として扱います。PC停止の瞬間までの永続化や、実機への一回だけの配送を保証するものではありません。復旧時に未完記録を見つけても、その操作を自動再実行しません。末尾の不完全なJSONL行などがあれば、破損箇所を識別して原記録を残し、読み取れた範囲を使います。正常な記録を無言で切り捨てる復旧は行いません。

初期版の検索はCodexのファイル読み取り・検索機能を使います。場所と形式が分かれば、別のランタイムでも同じ記録を読めます。専用の検索APIやデータベース、抽象化のためだけのfacadeは必須にしません。JSONLが大きくなって実際に読みづらくなった段階で、項目を絞って読む機能を追加するか判断します。

# 攻略とは別スレッドで行う記憶整理

Dreamingに着想を得た整理処理を設けます。過去のやり取りをそのまま積み上げるだけでなく、役立つ知識を短くまとめ、古い見立てや重複を整理するための処理です。特定製品のDreaming機能そのものを搭載するという意味ではありません。

起動契機はユーザー依頼の完了後と、明示的な「記憶を整理」操作です。単一ターンの終了、計画的終了、時間経過だけでは起動しません。初期UIの手動実行は、攻略が動いていないときに限る設計とします。より高頻度の起動は運用後の拡張候補です。

整理用の別スレッドへ、プロジェクトの案内、現状メモ、対象となる原記録の範囲を渡します。ゲームMCPと攻略Goalは渡しません。目的は記憶の編集であり、実機の操作やゲーム内セーブを行いません。モデル・エフォートは初期版ではアプリ共通の既定値を使います。攻略の会話内だけで変更した選択とは区別し、整理開始時の確定方法はU09で具体化します。

同じMarkdownへ攻略側と整理側が同時に書き込まないよう、実行管理で排他します。整理前に、攻略側の書き込みが終わった時点の`memory/`一式を退避します。退避に失敗した場合は整理を開始しません。**整理が失敗・中断した場合は、整理側の書き込み終了を確認してから、アプリが退避した記憶へ戻し、復元完了後に次の攻略を許可します。** 中途半端な整理結果をそのまま採用する選択肢は初期版に設けません。

復元は既存ファイルの上書きだけではなく、整理で追加・削除・改名されたファイルも含め、`memory/`を整理前の構成へ戻します。依頼の完了記録、`events.jsonl`、観測画像は巻き戻しません。これらは整理の対象としても書き換えません。これはアプリの運用上の分担であり、ファイル権限による完全な隔離が既に実現しているという主張ではありません。

整理の実行中であることと退避先をアプリが永続化し、正常終了または復元の完了まで保持します。アプリ再起動時にも整理の正常終了が確定していなければ、同じ復元手順を適用します。整理側の書き込み終了、退避データ、復元のいずれかを確認できなければ、次の攻略を開始・再開せずに理由を表示します。退避先は復元対象の`memory/`から分離します。退避形式・管理情報の配置・ファイル切替・復元中の失敗からの再試行は、U09の冒頭で整理の起動・排他・終了待ちと一緒に設計します。汎用的な履歴管理機構は作りません。

この整理契約はU09で提供します。それより前の段階では依頼完了後に停止・次の依頼待ちへ進み、自動整理を実装済みとして表示しません。U09ではU06〜U08の完了・開始・再開経路へ整理と復元の条件を接続します。

整理の正常終了時は整理後の記憶を採用し、失敗・中断時は整理前へ復元した記憶を採用します。次の攻略では、その採用した現状メモを読み直します。同じ攻略スレッドを再利用する場合も、別スレッドによる更新や復元が自動的に会話へ反映されたとは扱いません。整理に失敗しても、完了したユーザー依頼を未完へ戻しません。復元完了は攻略の自動開始を意味せず、開始・再開のユーザー操作は別に必要です。

# コンテキストと再開

スレッドは会話・ツール実行の履歴をまとめる単位です。モデルに入るコンテキストは有限で、必要に応じて圧縮されます。スレッドの再開は、すべての過去の画像や記述が常にモデルへ残ることを意味しません。記憶と原記録はスレッド履歴とは独立して保持します。

アプリ再起動後や新しいスレッドでは、対象の依頼、`guide.md`、`memory/current.md`と新しい観測を入口にします。必要な経緯は原記録や補足メモを調べます。ゲームがリセットされていれば実際の画面に合わせて現状を訂正します。アプリ側の再開とゲーム内セーブからの復帰を同一視しません。

Claude Codeなどへの移行時に引き継ぐ対象は、このプロジェクトのファイルと未完の依頼です。Codex固有の会話・Goal・圧縮状態を他のランタイムへ変換する機能は初期版の対象外です。
