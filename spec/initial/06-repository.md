# 06-repository.md — リポジトリ構成・開発手順

[文書一覧](README.md)

Project GIGASの実装は一つのPythonリポジトリにまとめ、ゲームI/O、MCP公開部、Codex接続部、GUI、保存処理の責務を分けます。複数配布物や汎用プラグイン基盤は初期版では作りません。以下を設計初版の配置とします。必要な部品から実装し、空の階層を一括生成しません。

# 名称と配置

名称は **GIGAS — General-purpose Interactive Gaming Agent System** とします。プロジェクトの表記は **Project GIGAS**、コード上の名称は小文字の`gigas`へ統一します。

| 対象 | 名称 |
| --- | --- |
| プロジェクト・アプリの表示名 | Project GIGAS / GIGAS |
| ローカルのプロジェクトディレクトリ名 | `Project_Gigas` |
| 配布名・`pyproject.toml`の`project.name` | `gigas`（PyPI公開時の登録可否は未確定） |
| Pythonのルートパッケージ | `gigas` |
| ソースの配置 | `src/gigas/` |

PyPIへの公開と名前の確保は未実施です。公開ページの有無だけでは登録可否を確定せず、[PyPIの名称選定ガイド](https://docs.pypi.org/project-management/choosing-a-name/)に従い公開時に確認します。配布名とimport名は別なので、必要になれば配布名だけを見直せます（[Python Packaging User Guide](https://packaging.python.org/en/latest/discussions/distribution-package-vs-import-package/)）。

# 実装コードの責務

以下の配置は`src/gigas/`からの相対パスです。

| 配置 | 所有する処理 | 持ち込まない依存 |
| --- | --- | --- |
| `app/` | 起動時の組立て、依頼の開始・停止・プレイ終了処理・再開、記憶整理の起動と排他、各部品の接続と終了順序 | 独自の攻略計画、Codexの停滞診断・自動修復、シリアル通信の詳細 |
| `ui/` | PySide6の画面、ユーザー操作、公開された計画・状態の表示 | Codex固有イベントを各画面で直接解釈する処理 |
| `runtime/codex/` | Python SDKの公開機能を使う一つの接続実装、スレッド・Goals、質問・承認、通知の変換 | デバイス操作、ウィジェット生成、非公開APIの差し替え、同じ通信の二重受信 |
| `game_io/` | 映像の共有、観測の生成、操作列の実行、取消し・押下解除 | CodexのGoal、会話、UIウィジェット、ゲーム固有の画像解析 |
| `game_io/devices/` | キャプチャーとシリアル入力の実装、機器の接続と解放 | MCPの要求形式やプロジェクトの攻略知識 |
| `mcp/` | ツールの定義、要求の検証、共通ゲームI/Oの呼出し、応答への変換 | デバイスの二重所有、UIやCodex SDKの初期化を前提とする処理 |
| `storage/` | アプリ設定、プロジェクト作成・読込、参照の入口、JSONL、観測画像、記憶の退避・復元、整理の未完状態の保存 | 攻略判断、記憶内容の意味的な整理、Codexの起動・停止 |
| `prompts/` | 配布物に同梱する攻略・記憶整理の共通指示と保存データの案内テンプレート | ゲームごとの進捗、個人の記憶、認証情報 |

ゲームMCPは同じPythonプロセスに組み込みますが、MCP公開部やゲームI/OがGUIとCodexの起動を必須にする依存関係にはしません。将来のSTDIO入口では、同じ実装を別の起動処理から組み立てられる構成にします。初期版でその入口まで実装する必要はありません。

構成部品は起動時に明示的に渡します。グローバルなデバイス取得や、import時にウィンドウ・カメラ・シリアル接続を作る実装は避けます。ゲーム入力を所有する実行部とキャプチャー取得元を一つに保ち、別経路から同じデバイスを開きません。並行処理の具体的な分担は[全体構成と実行管理](02-runtime.md)に従います。

# 変更を閉じ込める境界

外部SDKの型は`runtime/codex/`、MCPの型は`mcp/`、機器ライブラリの型は`game_io/devices/`で受け止めます。アプリ内で使う依頼・状態・観測・操作の型は、利用する部品同士で共有できる最小の形にします。`Protocol`やデータクラスは実際の依存境界に使い、すべてのクラスに抽象インターフェースを追加する方針にはしません。

Codexから別ランタイムへ変更するときは、接続部と必要な実行機能の対応を見直します。MCP、プロジェクトのMarkdown、構造化ログをそのまま利用できることを狙いますが、Goalsや会話再開の意味まで完全互換とは扱いません。初期版にはCodex以外の実装や自動切替えを用意しません。

APIの変更が必要になった場合は、影響する呼出し元と試験を同じ作業仕様に含めます。将来変更しないという前提で契約を過度に一般化するより、現在の仕様を小さく明確に保ちます。

## 分割理由と依存境界

実装コードは`app`、`ui`、`runtime`、`game_io`、`mcp`、`storage`の6区分にします。UIへの依存、Codex SDKへの依存、機器への依存、通信形式、保存形式、利用者の操作フローを混ぜないための分割です。`prompts/`は実行時リソースです。工程U01〜U09とパッケージを一対一に対応させる必要はありません。U02は`storage`の保存・記憶管理を完成させ、後続工程は同じ実装へ接続します。

`app`と`runtime/codex`の境界では、前者が「ユーザーの計画的終了をどの手順で実行するか」、後者が「Goal休止や通常ターン開始をSDKへどう伝えるか」を担当します。`storage`は退避・復元を担当しますが、整理スレッドの起動と終了待ちは`app`とCodex接続部の仕事です。`mcp`に操作列の実行ループを複製せず、取消し・解除は`game_io`の同じ実行部を使います。

`runtime/codex/`はCodex接続の整理場所であり、別ランタイムを動的に登録する基盤は作りません。`storage/`はプロジェクト・ログ・画像・記憶復元を内部モジュールへ分け、別配布物にはしません。共有型は所有する責務の近くへ置き、共通という理由だけで大きな`core`や`utils`へ集めません。

## 共通指示の同梱と読み込み

実行時に必要な共通指示と案内テンプレートは`src/gigas/prompts/`に置き、wheelとソース配布物へ同梱します。読み込みには[Pythonの`importlib.resources`](https://docs.python.org/3.13/library/importlib.resources.html)を使い、カレントディレクトリやリポジトリ直下の相対パスに依存させません。インストール先のリソースは実行中に書き換えず、プロジェクトごとの案内・記憶は保存先へ生成します。

ビルドした配布物を別環境へインストールし、リポジトリ外の作業ディレクトリから共通指示を読み込めることを確認します。編集可能インストールで読めることだけでは、同梱確認の完了としません。

# 開発エージェントの入口

`AGENTS.md`は、このリポジトリを開発するCodex向けの恒常指示です。設計文書の入口、作業単位の選び方、変更範囲に応じた検証、ユーザー変更の保持を記載します。開発用Skillの一覧は`AGENTS.md`に集約し、`.agents/skills/`に手順の実体を置きます。既存テンプレートの内容は参照版を記録して取り込み、本製品の構成に合わないPython版、OS、配布手順、個人PC固有のパスは調整します。

これらはゲームをプレイするエージェントの共通指示ではありません。プレイ用指示は`src/gigas/prompts/`へ同梱し、対象ゲーム・プロジェクト情報・ユーザー依頼を別に渡します。開発用`AGENTS.md`がプレイへ混入しないよう、プレイ中のCodexの作業フォルダーは実装リポジトリから分けます。プロジェクトデータの配置は[エージェントの動作と記憶](04-agent-memory.md)に従います。

開発用Skillの利用は、攻略エージェントがSkillsを自己生成・自己管理する機能の採用を意味しません。操作再利用の初期範囲は、短い操作列と判断を含む手順です。

# 一つの作業単位を進める手順

着手時には`AGENTS.md`、関連する`spec/initial/`、既存の作業仕様、実装・試験を読みます。変更する前にブランチと作業ツリーを確認し、ユーザーの既存変更を保持します。

次の作業を一つ選び、作業単位の連番と機能名を持つ仕様書へ目的、対象範囲、対象外、利用例、振る舞い仕様、対象ファイル、確認方法を記載します。U01のアプリ起動を最初に実装する場合は、`spec/wip/unit_001/APP_STARTUP.md`という配置が使えます。`unit_001`は実際の作業順の連番であり、U01〜U09の工程番号と一対一には固定しません。

実装中に別の課題を見つけても、現在の作業へ無制限に追加しません。必要なら別の作業候補または`spec/dev-journal.md`へ残します。振る舞いが変わる変更と、動作を維持した整理は区別します。TDDを使う場合は振る舞いごとの失敗理由と成功を確認し、対応するテストリストを更新します。

1つの`unit_XXX`には1つの仕様書を置くことを原則とします。親仕様と子仕様に分割する場合も別のunitへ置き、独立した文書として目的・契約・検証・完了条件を記載します。親は工程全体の対象範囲・マイルストーン・依存順・受入条件、子は対象部分の詳細契約・TDD・検証結果を所有します。各unitは自身の完了条件で移動し、参照元のリンクを更新します。親は子の完了だけでなく全体の受入条件を確認してから完了へ移します。レビュー記録は対象仕様内へまとめ、空の雛形を一括生成しません。

完了時は、関連する品質確認のコマンド、結果、未実行理由、残る制約を作業仕様へ記録します。一つのPRでレビューできる範囲に収め、完了記録を`spec/complete/`へ移します。実装と恒常設計が変わった場合は、該当する`spec/initial/`も更新します。

# 依存管理と試験の配置

Pythonの実行・依存管理は`uv`を使い、依存変更に伴う`uv.lock`を保存します。`ruff`、`ty`、`pytest`を品質確認の基準とし、コマンドと実行条件は[実装計画と運用](05-implementation.md)にまとめます。

`tests/unit/`では機器・モデル通信を必要としない振る舞いを確認します。`tests/integration/`では保存、MCP、接続部、GUIへの通知などの境界を扱います。`tests/acceptance/`には実機と実アカウントで確認する利用場面を置き、実行条件を明示します。認証情報、実プレイ画像、個人のプロジェクト記録を固定fixtureとしてcommitしません。

初期のCIは選定したPython版のWindows動作を優先します。OSに依存しない試験を別OSで実行する場合も、Windows実機の接続確認の代用にはしません。ゲーム攻略の成功率を評価するベンチマーク基盤は作りません。
